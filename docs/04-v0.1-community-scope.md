# Modelry V0.1 Community Scope

## Goal

V0.1 proves that Modelry is a usable product, not merely a runtime with an Admin UI.

The release is successful when a developer can build and operate a small real application backend from an empty project through one coherent workflow.

## Fixed technical baseline

- Go
- SQLite only
- React + TypeScript + Vite
- modular monolith
- Contract First
- simple self-hosted distribution
- zero-config-first startup.

PostgreSQL, Enterprise and Cloud are outside V0.1 implementation scope.

## Required product closure

### First run

- running Modelry from an empty valid project root initializes and starts safely;
- first Admin bootstrap is clear and secure;
- restart preserves durable state;
- partial or invalid initialization fails with actionable recovery guidance.

### Collections and Schema

- Normal Collection;
- Auth Collection;
- Fields;
- Relations;
- Indexes / Unique;
- Validation;
- Defaults.

Schema is a Collection workspace with Fields / Relations / Indexes, not three unrelated top-level areas.

### Records

- create / view / update / delete;
- filter / sort / pagination;
- relation expand;
- file values;
- durable results after reload.

Records is the default Collection view.

### Changes

Backend Model mutation uses:

Draft / Proposal
-> ChangeSet
-> Structured Diff
-> Risk + Preconditions + Impact
-> Apply Attempt
-> Migration History.

Higher-risk operations require explicit confirmation.

Failure must leave the runtime in a diagnosable and recoverable state.

### Application API

- REST application API;
- OpenAPI;
- Collection API explorer / runner;
- Global API workspace;
- endpoint discovery;
- structured error model;
- canonical requestId.

Global API includes Endpoints and Requests.

### Application Auth

V0.1 must support at least:

- Auth Collection;
- email + password;
- server-revocable sessions;
- session management.

Additional login identifiers and OAuth should only enter V0.1 if they do not weaken the core closure.

### Record Policy

Policies cover:

- list;
- view;
- create;
- update;
- delete.

Policy is fail-closed.

A usable policy editor and diagnostic/simulation experience is required; users should not need to guess why access was denied.

### Files

- File Field;
- Local Storage;
- single / multiple values where supported;
- size and MIME constraints;
- upload lifecycle with cleanup rules.

### Realtime

- SSE-based application realtime;
- policy-aware subscription;
- best-effort semantics clearly documented.

### Hooks and Secrets

- Lifecycle Hook;
- JavaScript / TypeScript-facing authoring experience;
- controlled runtime APIs;
- timeout / error isolation;
- Secret as first-class Control Plane resource;
- secret plaintext not generally readable after write.

External irreversible side effects are not part of synchronous pre-commit Hook semantics.

### Observability

API Requests:

- application HTTP metadata;
- duration / status / endpoint / requestId;
- no raw credential leakage;
- no unrestricted raw body/header logging.

Audit:

- security and governance facts.

Activity:

- operational cross-module events and diagnostics.

### Admin

Target navigation:

Core
- Overview
- Collections
- API

Control
- Changes
- Hooks
- Access

System
- Settings
- Activity.

Collection workspace:

- Records
- Schema
- Policy
- Auth for Auth Collection
- API.

Collections support Card and List views; Card is the default.

### MCP

MCP is a first-class machine interface to the same Modelry semantics.

It must not bypass ChangeSet, capability, policy or audit rules.

The exact tool list is defined only after the new HTTP/domain contract stabilizes.

## Deferred after core V0.1

Likely V0.1.x / later Community work:

- OAuth providers;
- password reset and email verification delivery stack;
- S3-compatible storage;
- Event Hook / Webhook;
- simple cron/jobs;
- richer backup / restore product UI;
- custom application APIs;
- SDK generation;
- broader import/export.

## Explicit non-goals

- PostgreSQL;
- Enterprise features;
- Cloud Control Plane;
- GraphQL;
- gRPC Data API;
- workflow / DAG;
- Kubernetes-first;
- microservices;
- HA cluster;
- multi-project runtime;
- serverless hostile-code sandbox;
- database trigger/stored-procedure product surface.

## V0.1 exit criteria

The release is not accepted until mandatory Browser Acceptance proves:

- Functional Closure;
- UX Closure;
- Visual Closure;
- Error Closure;
- Business Flow Closure;
- restart persistence;
- cross-surface durable verification.
