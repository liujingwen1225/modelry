# SPEC-0002 — V0.1 Domain Foundation

- **状态：** Accepted — V0.1 Domain Foundation Baseline
- **范围：** Modelry V0.1 Community 的逻辑领域语义
- **依据：** `CONTEXT.md`、`AGENTS.md`、`docs/00-product-vision.md` 至 `docs/06-product-architecture.md`、`docs/specs/0001-admin-product-ux-spec.md`、GitHub Issues #2、#3、#4
- **不定义：** HTTP 路径或 DTO、SQL 表或列、SQLite 专属语义、Go 包、React 组件接口

本文件冻结 V0.1 Domain 层语义。它引用 ADR-0001 的 Runtime / Storage 决策，但不把 Project Root、SQLite 结构或 Go 包定义成领域身份或产品语义。

## 1. 目标与边界

定义 Modelry V0.1 共同使用的 Project Backend Domain，使 Admin、Application API、CLI 与 MCP 面对相同的产品语义。领域对象表达业务事实与状态，不以传输格式或物理存储结构作为身份、关系或生命周期的定义。

V0.1 Community 的部署基线是一个 Runtime 服务一个隐式 Project。该基线是版本拓扑，不是 Modelry 永久产品不变量。Domain 不加入 Organization、Environment、Tenant 或 Cloud Control Plane；未来版本可以在不改变 Project Backend 基本语义的前提下增加这些边界。

### 1.1 已冻结的语义约束

1. Project Backend Model 是 Collection、Field、Relation、Index、Validation、Default 与 Access Rule 的规范产品语义。SQLite 只是一种 V0.1 存储实现，不能定义这些对象的含义。
2. Application Data Plane 与 Modelry Control Plane 分开；Application User 与 Owner / Service Account 是不同身份域。
3. `Principal != Credential`。身份说明“谁”，凭据说明“如何证明身份或授权访问”。
4. Schema Pending Changes 以单个 Collection 为范围。Fields、Relations、Indexes 共用该 Collection 的一个耐久 Schema Pending Change；Access Rule 与 Auth Configuration 不加入其中。
5. `id`、`createdAt`、`updatedAt` 是每个 Collection 始终存在的 V0.1 系统字段，由系统管理，用户不能删除、改名或在 Record Form 中编辑。
6. App User 的 Profile Record 与 Password Credential 是不同领域资源；Admin 创建 App User 是协调两者的一次产品操作。
7. `AppliedMigration` 是成功应用的不可变耐久事实。再次尝试失败变更时产生新的 `ApplyAttempt`，不改写既有尝试。
8. Domain Language 不要求等同 UI Language。UI 使用 Owner、Service Account、App User、Permission、Password、API Key、Session、Pending Change 等产品用语；技术对象只在实现边界或 Technical Details 中出现。

### 1.2 术语

- **ProjectRuntime：** 一个 Project Backend 的逻辑运行实例。V0.1 每个 Runtime 对应一个隐式 Project。
- **Applied Model：** 当前已生效的 Backend Model 语义。
- **Schema Pending Change：** 单 Collection 内已保存、可在刷新或导航后恢复的 Schema 变更意图。
- **Physical Migration / Ledger：** 存储实现用于把变更落实到物理持久化状态并记录结果的机制；它们不是 Domain Model 的替代物。其原子性和不可变事实边界遵从 ADR-0001。
- **派生状态：** 从当前 Runtime、存储或领域事实计算出的当前观察值，不是用户可直接编辑的配置。

## 2. 用户故事

1. 作为开发者，我希望按 Collection 管理 Fields、Relations 与 Indexes，并在刷新或离开页面后仍能看到已保存的待处理变更，以便稍后安全 Apply。
2. 作为开发者，我希望在 Apply 前看到 Runtime 计算的变更、风险、前置条件与影响，并能在失败后恢复，以便理解并验证模型演进。
3. 作为管理员，我希望一次创建 App User 时同时设置 Profile 与 Password，以便不需要分开初始化两种资源。
4. 作为 App User，我希望密码凭据与 Profile 分开管理，并且 Session 可由 Runtime 撤销，以便安全地登录和退出。
5. 作为服务集成维护者，我希望 Service Account、Permission 与 API Key 各自有清晰生命周期，以便只授予所需权限并能撤销访问。
6. 作为 Owner，我希望看到 Runtime 与 Storage 的真实健康状态、请求结果和安全审计事实，以便发现问题并采取恢复行动。

## 3. 通用 Domain 规则

### 3.1 身份与归属

- 每个需要跨操作引用的实体有稳定的逻辑身份。该身份在重命名、刷新、进程重启或存储实现变化时不应因显示名或物理位置改变而改变。
- Collection、Record、Access Rule、Schema Change 等身份至少在所属 ProjectRuntime 内唯一；RecordID 还必须位于一个明确 Collection 的范围中。
- Name、Email、Path、Endpoint、时间戳等业务属性不能仅因方便而充当身份，除非该对象定义明确说明它是用户可变标识。
- 以下各对象表中的“拥有者”说明 Domain 的授权与生命周期归属，不表示数据库外键或表归属。

### 3.2 状态、修改与持久性

- Applied Model 表示已生效语义；Pending Change 表示已持久化但尚未 Apply 的意图。二者不得折叠为一个隐式编辑草稿。
- 结构化变更必须通过对应配置边界显式保存。未保存的本地表单不属于 Pending Change，也不在本 Spec 中被当作耐久对象。
- `RuntimeStatus`、`StorageStatus`、Risk、Precondition 与 Impact 是 Runtime 依据事实生成的观察或评估，不可由调用方伪造为权威结果。
- 对状态事实采用追加或新版本语义：成功 Apply 形成新的 AppliedMigration；失败重试形成新的 ApplyAttempt；不能把历史事实原地改写为另一结果。

## 4. Runtime 与 Storage

本节的逻辑身份与健康语义独立于数据库类型。Project Root 解析、SQLite 生命周期与参数、Local Storage 副作用、事务边界、启动就绪及关闭过程遵从 [ADR-0001](../adr/0001-runtime-storage-architecture.md)；这些实现选择不改变下述 Domain 语义。

### 4.1 ProjectRuntime

- **身份与归属：** 表示一个 Project Backend 的稳定逻辑身份；V0.1 一个 Runtime 对应一个隐式 Project。它归属于被管理的 Project，不归属于某个 HTTP 请求或某一进程 PID。
- **生命周期：** 从合法空项目开始初始化，经启动就绪、运行、关闭，可从同一 Project 的耐久状态重启。进程重启不自动创建新 Project。
- **可变性与持久性：** Project 的 Backend Model、Records、Security 配置及必要运行状态按其各自领域生命周期保存。Runtime 当前进程状态是派生值。首次初始化生成并保存稳定 Project ID；Root 路径不是该 ID，移动或重命名 Project Root 不改变逻辑身份，同一路径重新创建 Project 会获得新身份。
- **安全边界与关系：** 包含单个 Project 的 Project Backend Plane 与其配套 Control Plane；不意味着它可跨 Project 管理资源。它关联一个 Applied Model、各自独立的 Schema / Access Rule / Auth Configuration 变更边界、Records、Identity、RequestRecord 与 AuditRecord。

### 4.2 RuntimeStatus

- **身份与归属：** 是某个 ProjectRuntime 在某个观察时点的状态快照，无需拥有独立业务 ID；由 Runtime 产生。
- **生命周期：** 随启动、就绪、降级、不可用及关闭而变化。`Ready` 只表示 Project Root / Runtime 锁可用、SQLite 版本与连接设置通过验证、内部 Store Migration 完成、Local Storage 可用、Runtime 模块初始化成功且 HTTP Listener 已 bind；Unknown / Unavailable 不能显示成 Ready。运行期必要依赖失效时撤销 Ready。
- **可变性与持久性：** 可观察的当前值随 Runtime 变化而更新，是派生、短暂状态，不是耐久配置或审计事实。`observedAt` 等诊断信息可随快照提供。
- **安全边界与关系：** 仅说明 ProjectRuntime 的可用性，不替代 StorageStatus，也不包含秘密或应用数据。它与 StorageStatus、错误恢复状态共同用于诊断。

### 4.3 StorageStatus

- **身份与归属：** 是 ProjectRuntime 所辖某个存储能力在观察时点的状态。诊断分别表达 SQLite 数据存储与 Local File Storage 的健康情况，并可汇总到 Runtime readiness。
- **生命周期：** Storage 能力初始化、可用、降级或不可用时重新计算。未知状态保持 Unknown / Unavailable，不得伪装健康。
- **可变性与持久性：** 是派生、短暂的健康快照，不是用户修改的配置或存储内容。V0.1 Settings 以只读诊断为主。
- **安全边界与关系：** 只公开解决问题所需的 Provider、受管路径、Health 等诊断信息；不得泄露凭据。SQLite 与 Local File Storage 的生命周期、Project Root 下的路径及 readiness 门禁遵从 ADR-0001；文件存储状态关联 File Field 能力。

## 5. Backend Model

### 5.1 Collection 与 CollectionType

- **身份与归属：** Collection 由稳定 `CollectionID` 标识，属于一个 ProjectRuntime。它拥有 Field、Relation、Index、Record 与 Collection 级 Access Rule；Schema Pending Change 也以它为唯一范围。
- **生命周期：** 初次创建时一次提交 Collection 与初始模型；因没有既有 Records，不要求用户走常规 Migration Review。之后的结构修改通过耐久 Schema Pending Change 与 Apply。Collection 的删除或类型转换不由此 Spec 新增；若产品支持，必须是显式且可审查的操作。
- **可变性与持久性：** Applied Collection 定义与 Pending Schema Change 分开保存。Name、Description 和结构属性依其各自支持的 Model Change 规则变化；显示名改变不改变 CollectionID。V0.1 类型为创建时选择的 `Normal` 或 `Auth`，其转换语义未定义，不能默认为安全变更。
- **安全边界与关系：** 两种类型均属于 Project Backend Model。Normal Collection 不承载 App User Credential；Auth Collection 额外定义应用身份配置与唯一 Auth Identifier，并允许 Profile Record 关联 ApplicationUser。

`CollectionType` 是 Collection 创建时的分类值，而非独立可操作资源。V0.1 取值为 `Normal`、`Auth`；创建后随其 Collection 持久保存。更改类型的转换流程不属于当前语义。

### 5.2 Field 与 FieldType

- **身份与归属：** Field 由稳定 `FieldID` 标识，属于一个 Collection。其名称在该 Collection 的 Applied Model 中满足当前字段命名约束；身份不依赖字段名。Field 可声明 Type、Required / Unique、Validation、Default 与可选 Relation 语义。
- **生命周期：** 新增、修改、删除已存在 Field 均产生 Schema Pending Operation，Apply 成功后才改变 Applied Model。创建 Collection 时的初始 Fields 与 Collection 一起生效。
- **可变性与持久性：** Field 的已应用定义与 Pending 定义分别耐久保存。普通 Field 属性只能经 Schema Change 变更；字段名、Type 和验证兼容性按实际变化计算 Risk 与 Preconditions。
- **安全边界与关系：** Field 定义 Record 值的可接受形状，不授予访问权限。应用读取 Record 仍受 Access Rule 约束。V0.1 系统字段 `id`、`createdAt`、`updatedAt` 始终存在、用户可见、系统管理、锁定且不可删除或改名。

`FieldType` 是 Field 的领域类型，不是 SQL 类型。它决定 Record 值的产品含义以及可用 Validation、Default 和 Relation。V0.1 支持集由社区范围与后续 Contract 约束；类型集合不得暴露 SQLite 专属类型。Single File 是一种 Field 能力；V0.1 仅单文件值，不含多文件或 S3 语义。

### 5.3 Validation 与 Default

- **身份与归属：** Validation 是 Field 上按规则类别区分的约束；其逻辑身份由 Field 与规则类别确定，不需要成为独立用户资源。Default 是 Field 的缺省值或缺省策略，同样归 Field 所有。
- **生命周期：** 两者随 Field 定义建立；修改或移除均通过所属 Collection 的 Schema Pending Change 与 Apply 生命周期。
- **可变性与持久性：** Applied 规则与待应用规则分别可恢复。Validation 在记录创建 / 更新时验证值；Default 仅在产品定义的缺省条件下参与新值初始化，不覆盖用户显式输入。Default 不隐含任意 SQL 函数或存储引擎行为。
- **安全边界与关系：** Runtime 在 Record 写入边界强制 Validation 与 Default。它们不能绕过 Access Rule，也不得包含需要读回展示的 Credential。具体规则种类和默认表达式受 V0.1 范围约束。

### 5.4 Relation

- **身份与归属：** Relation 是一个 `Relation` 类型 Field 所表达的 Collection 间业务关系；其逻辑身份依托来源 FieldID，不是另一份独立 Field 或另一个独立 Draft。它属于来源 Collection，目标是一个目标 Collection，并声明 Cardinality。
- **生命周期：** 新建、修改或删除 Relation 作为来源 Collection 的 Schema Pending Operation；Apply 后成为 Applied Model 的一部分。
- **可变性与持久性：** 来源与目标、基数及受支持关系属性随 Schema Change 版本化。关系在 Applied Model 和 Pending Model 中均可被导航恢复。
- **安全边界与关系：** 关系不复制目标数据，也不隐式授权访问目标。Relation Expand 必须再次检查目标 Collection 的 View Rule。删除行为等详细 Referential Behavior 只在 V0.1 明确支持的字段语义中定义，不借用数据库默认行为。

### 5.5 Index

- **身份与归属：** Index 由逻辑 `IndexID` 标识，属于一个 Collection，并引用一个或多个该 Collection 的 Fields。它表达查询或唯一性约束的产品语义，不含物理索引名或 SQL 实现。
- **生命周期：** 新建、修改、删除均加入所属 Collection 的 Schema Pending Change；Apply 成功后进入 Applied Model。
- **可变性与持久性：** 定义随 Model Change 版本变化并耐久保存。一般单字段 Unique 作为 Field Feature 表达；Domain 语义不得产生两个相互矛盾的唯一性来源。Composite / Advanced Index 作为 Index 配置管理。
- **安全边界与关系：** Index 不是授权对象。Runtime 在 Apply 前检查冲突与 Preconditions；具体索引构建与恢复由 ADR-0001 定义的 Storage / Migration 边界负责。

## 6. Data

### 6.1 Record 与 RecordID

- **身份与归属：** Record 属于一个 Collection，由 Collection 范围内稳定、不可变的 `RecordID` 标识。固定系统字段 `id` 表达此 Record 身份；领域语义不依赖 ID 的物理编码格式。
- **生命周期：** Record 经 Create、View、Update、Delete 管理，不经过 Schema Change 生命周期。创建 / 更新时按 Applied Field、Validation、Default 与 Access Rule 校验；删除是显式 Record 操作。
- **可变性与持久性：** 普通 Field 值可按操作规则改变；成功变更后的 Record 是耐久数据。`id` 和 `createdAt` 不可变；`updatedAt` 由 Runtime 管理，在成功更新时更新。三个系统字段都不允许 Record Form 写入。
- **安全边界与关系：** Record 属于 Application Data Plane。Application API 的 List / View / Create / Update / Delete 均受当前 Collection Access Rule 约束；Control Plane 管理员操作按其独立 Permission 检查。Record 值不是 Schema Pending Change。

`RecordID` 是 Record 的逻辑身份，不是 Field 配置。它在其 Record 生命周期内稳定且不可变，并用于 Relation、Request Detail / Audit 的资源引用（适用时）。

## 7. Change Domain

### 7.1 PendingOperation

- **身份与归属：** 由稳定 `PendingOperationID` 标识；归属于一个 ChangeSet 和唯一 Collection。它表达一个 Field、Relation、Index 或其 Validation / Default 的新增、修改或移除意图。
- **生命周期：** 用户在对应编辑器显式保存后耐久建立；仍可在 Pending 状态中继续编辑或撤销。Apply 成功则被该 ChangeSet 的 AppliedMigration 取代为历史事实；Discard 将其从有效待处理集合移除；Apply 失败时保留原意图供恢复。
- **可变性与持久性：** 活跃 PendingOperation 的意图可修改；已完成 / 丢弃操作不改写为另一历史结果。只要它仍是待处理意图就必须耐久，支持刷新、导航和重启后恢复。
- **安全边界与关系：** 仅属于 Schema Change 边界。未保存的 Field Editor 本地表单不是 PendingOperation。Policy / Access Rule 或 Auth Configuration 不作为 Schema PendingOperation。

### 7.2 ChangeSet

- **身份与归属：** 由稳定 `ChangeSetID` 标识，属于一个 ProjectRuntime，Schema ChangeSet 的范围恰为一个 Collection，并拥有该范围内的 PendingOperations。V0.1 同一 Collection 的 Fields、Relations、Indexes 只有一个共享的有效 Schema Pending Change。
- **生命周期：** 从首个已保存 PendingOperation 建立，历经 Ready、Needs review、Failed 等可见状态，成功后 Applied，或由用户 Discard。其他 Collection 的变更形成不同范围，不能扩大一个 ChangeSet。
- **可变性与持久性：** 活跃变更集因后续保存的操作而变化；未解决时耐久存在。Applied / Discarded 终态不能被改写为另一个 ChangeSet。History 可按 Collection 与全局 Changes Surface 观察。
- **安全边界与关系：** Apply 需要有权执行模型管理操作的 Control Plane Principal。Access Rule 与 Auth Configuration 可以有各自 Pending / Apply 生命周期，但不并入 Schema ChangeSet，也不共享 Collection-wide Schema Draft。

### 7.3 StructuredDiff

- **身份与归属：** 是某 ChangeSet 版本相对于 Applied Model 的规范结构化比较结果；身份由 ChangeSet 版本或对应 ApplyAttempt 确定。由 Runtime 生成。
- **生命周期：** Pending Model 变化后需要重新计算；Apply 前按当前 Applied Model 与数据条件校验。每次 ApplyAttempt 使用其实际评估的 Diff 快照。
- **可变性与持久性：** Diff 本身不可由用户直接编辑，是派生值；与 ApplyAttempt / 成功历史关联的快照耐久保留，以供技术详情和审计。未评估的预览值可重新生成。
- **安全边界与关系：** 描述 Model 变化，不是 SQL Migration 内容、HTTP DTO 或任意 SQL。它是 Risk、Precondition、Impact 的输入，也是用户 Review 的解释来源。

### 7.4 Risk

- **身份与归属：** Risk 是 Runtime 针对 ChangeSet 版本及其 Applied 状态生成的评估，不是独立用户资源；作用范围是对应 Diff / ApplyAttempt。
- **生命周期：** 每次预览或 Apply 前重新评估；至少能区分可直接 Apply 的 SAFE 变化与需要 Review / Confirm 的风险变化。不可安全完成的情况通过明确失败或恢复状态表达。
- **可变性与持久性：** 由 Runtime 计算，用户不能降低或覆盖风险；评估快照随对应 ApplyAttempt / Applied History 保存。Apply 前的陈旧快照不得当作当前事实。
- **安全边界与关系：** Risk 约束确认与执行路径；破坏性或不可逆变化需要符合当前 V0.1 确认及恢复策略。具体评分算法不属于 Domain Contract。

### 7.5 Precondition

- **身份与归属：** 是 Runtime 对一项 Apply 前提的检查结果，属于某次 Diff 评估 / ApplyAttempt。检查项针对变更、Model、数据或存储状态。
- **生命周期：** 在预览和执行时评估；执行前必须验证仍成立。检查失败或警告会影响是否能 Apply、是否需 Review，以及后续恢复提示。
- **可变性与持久性：** 检查结果由 Runtime 生成；按对应 ApplyAttempt 快照保存。输入状态改变后需重算，不由用户编辑为通过。
- **安全边界与关系：** 用于阻止不满足条件的模型变更；不等同于 Access Rule，也不能由 Access Rule 代替。

### 7.6 Impact

- **身份与归属：** 是 Runtime 对 Diff 影响的结构化评估，属于 ChangeSet 版本及一次 ApplyAttempt 的上下文。
- **生命周期：** 随预览与 Apply 前评估生成；按实际 Applied Model / 数据状态重算。可呈现受影响对象、数量或警告，但字段细节由后续 Contract 定义。
- **可变性与持久性：** 派生且不可由用户修改；作为 ApplyAttempt / Applied History 的评估快照耐久保存。未经验证的估值不能保证为事实。
- **安全边界与关系：** 解释变更可能影响什么，辅助 Review；它不是 Risk 的替代物，也不是独立变更对象。

### 7.7 ApplyAttempt

- **身份与归属：** 每次尝试有独立稳定 `ApplyAttemptID`，属于一个 ChangeSet；记录发起该操作的 Control Plane Principal（若有）及执行结果。
- **生命周期：** 从开始执行进入 Succeeded、Failed 或需要恢复等终态。对同一 Pending Change 的 Retry 必须创建新的 ApplyAttempt，以保留前次结果。
- **可变性与持久性：** 执行中的状态可更新；每次 ApplyAttempt 先耐久建立为 In Progress。成功时与物理变更及 AppliedMigration 一起提交；失败时应用事务回滚后单独耐久记录失败诊断。终态记录不能由后一次尝试改写；进程中断留下的 In Progress 在重启时标记为中断 / 待恢复，Retry 必须创建新 ID。
- **安全边界与关系：** 只有拥有相应 Control Plane Permission 的 Principal 可发起 Apply。ApplyAttempt 关联具体 StructuredDiff、Risk、Precondition、Impact 快照，并可产生 AppliedMigration 或 RecoveryState。

### 7.8 AppliedMigration

- **身份与归属：** 由稳定 AppliedMigration / Migration ID 标识，属于一个 ProjectRuntime 的 Applied History；引用成功的 ChangeSet 与成功 ApplyAttempt。
- **生命周期：** 仅在变更成功成为 Applied Model 后创建；创建后不可删除、改写或复用来表示另一变更。后续变更产生新的历史事实。
- **可变性与持久性：** 不可变、耐久。它记录已发生的产品层模型演进事实及足以解释它的规范结果；只在物理变更与 Applied Model 同一 SQLite 事务成功时写入。它不是要求 Domain 公开某种 SQL Migration 文件格式。
- **安全边界与关系：** 属于 Control Plane 的变更历史；允许通过授权的 Changes / Technical Details 观察。它关联 Applied Model 版本，但不能被 UI 术语强迫用户理解为数据库迁移细节。

### 7.9 RecoveryState

- **身份与归属：** 表示失败 Apply 后一个 ChangeSet / ApplyAttempt 当前仍需处理的恢复状态，身份关联其 ChangeSet 和最新相关 ApplyAttempt。
- **生命周期：** 在 Apply 产生需要恢复的情况时出现，随后经受支持的恢复行动更新，直至问题解除；Apply 失败不自动等于已恢复或可安全丢弃。
- **可变性与持久性：** 当前恢复投影随恢复进展变化；未解决状态及重启后仍需要的恢复事实必须耐久。DB 事务回滚时 Pending Change 保留；启动时未结束的 ApplyAttempt 标记为中断 / 待恢复。Local Storage 孤儿文件按 ADR-0001 的安全 reconcile 规则清理。
- **安全边界与关系：** 属于 Runtime 管理的变更恢复边界；向用户提供可行动说明，但不暴露任意文件系统或数据库操作能力。失败时 Schema Pending Change 保留供用户恢复。

## 8. Application Auth 与 Access

### 8.1 ApplicationUser

- **身份与归属：** 是 Application Data Plane 的 App User Principal，属于一个 Auth Collection。每个 App User 关联一条 Profile Record；稳定身份不等于可变 Email。其身份可由 Auth Collection 与 Record 身份关联，但逻辑概念必须与 Record、Credential 分开。
- **生命周期：** Admin 创建时，产品操作协调创建 Profile Record 与 Password Credential；Self Registration 仅在 Auth Configuration 显式开启时建立身份。删除 Profile 时，该身份不得继续成功认证；相关 Credential / Session 的失效处理按 Auth 行为与 ADR 定义。
- **可变性与持久性：** Profile 属性属于 Record，认证身份与 Credential 状态分开耐久保存。Email 是 Auth Identifier Field（Required + Unique），不是身份本身；更新 Email 不应通过改写 Principal 身份解决。
- **安全边界与关系：** 仅代表应用侧身份，受 Application Auth 与 Collection Access Rule 限制；不获得 Owner 或 Service Account 的 Control Plane 权限。它拥有一个 Profile Record、Password Credential 与零到多个 Sessions。

### 8.2 Credential

- **身份与归属：** Credential 是 Principal 证明身份或获得访问的独立凭据概念，有自己的类型与生命周期，归属于一个 Principal；Credential 不是 Principal，也不是普通 Collection Field。
- **生命周期：** 凭据可签发、验证、替换、过期或撤销，具体支持流程随凭据类型定义。撤销或替换不得把旧秘密暴露给调用方。
- **可变性与持久性：** 凭据的状态 / 验证材料按安全要求耐久保存，原始秘密只能在明确的一次性展示流程中短暂出现，不能作为可读回的普通持久值。
- **安全边界与关系：** Credential 必须始终受其 Principal 所属 Plane 限制；应用密码、Owner 登录认证与 Service Account API Key 不能互换使用。

### 8.3 PasswordCredential

- **身份与归属：** 是 ApplicationUser 的 `Credential` 类型，供 Email + Password 认证使用。它与 Profile Record 及任何 Field 分离。
- **生命周期：** 在 Admin 创建 App User 或允许的注册操作中建立；可通过受支持的密码更改替换；验证成功可建立 Session。V0.1 不引入 OAuth、邮件验证投递或密码重置邮件流程。
- **可变性与持久性：** 密码原文只为提交 / 验证短暂存在；耐久状态必须为不可读回的验证表示。修改密码不改写 Profile 或 Schema。具体哈希算法和事务落盘方式不由 Domain 冻结。
- **安全边界与关系：** 只能用于 Auth Collection 对应的 Application Auth；绝不作为 Field、Record API 值或普通 RequestRecord 内容返回。创建 App User 时与 Profile Record 作为一个产品操作协调，二者在一个 SQLite 事务中成功或失败；密码更新与要求失效的 Session 状态变化也按 ADR-0001 的一致性边界提交。

### 8.4 Session

- **身份与归属：** Application Session 由稳定 `SessionID` 标识，关联单个 ApplicationUser；属于 Application Data Plane。此对象不定义 Owner 的管理面 Session。
- **生命周期：** 成功认证时建立；到期或服务端 Revoke 后失效。当前用户可查看 Sessions，撤销后行仍可显示为 Revoked；此后访问必须失败。
- **可变性与持久性：** 建立时身份与创建事实不可变；状态可从 Active 变为 Revoked / Expired，使用时间等运行元数据可更新。为了服务端撤销，必要的 Session 状态必须耐久跨导航 / 重启保留；具体持续时间遵从 Auth Configuration。
- **安全边界与关系：** Session 是 App User 的认证状态，不是 Profile Field。原始 Session Token 不得进入 Record、RequestRecord 或 AuditRecord。

### 8.5 AccessRule

- **身份与归属：** 是一个 Auth / Normal Collection 对某操作的应用访问规则，逻辑身份由 Collection 与操作（list、view、create、update、delete）确定；归属该 Collection 的 Access Configuration。
- **生命周期：** V0.1 默认策略 Fail Closed。编辑形成独立于 Schema 的 Access Rule Draft / Pending Rule Change；Apply 后才成为运行时有效规则。未 Apply 的规则可 Discard，Apply 失败可恢复，不改变已生效规则。
- **可变性与持久性：** Draft、Applied 与历史结果分开；保存后的 Pending Rule Change 需要耐久，但不得并入 Schema ChangeSet。规则可采用 No access、Anyone、Signed-in users、Record owner、Custom 等受支持表达。
- **安全边界与关系：** 规则保护 Application Data Plane 的 Collection 操作。Custom Expression 的可表达能力受 V0.1 合同约束；不得越过 Control Plane Permission。Relation Expand 时重新评估目标 Collection 的 View Rule；V0.1 不要求 Policy Simulation。

### 8.6 AuthenticationConfiguration

- **身份与归属：** 每个 Auth Collection 拥有自己的应用认证配置，以 CollectionID 为逻辑范围；它不是 Field、Credential 或 AccessRule。
- **生命周期：** Auth Collection 创建时 Email + Password 启用，Email 是 Required + Unique Auth Identifier，Self Registration 默认关闭；创建时可直接开启注册。后续认证设置形成独立的 Authentication Configuration Pending Change，并按其自己的 Apply 生命周期生效。
- **可变性与持久性：** Applied Configuration 与已保存但未 Apply 的认证变更分离；受支持的 pending 配置必须在离开或刷新后仍可识别。Session Duration 等配置更新不改变 Schema ChangeSet，也不隐式修改 Credential 或 AccessRule。
- **安全边界与关系：** 只配置 Auth Collection 的 Application Auth 行为，例如认证启用、注册开关与 Session Duration。它关联 ApplicationUser、PasswordCredential、Session 的认证策略，但不存放 Password 原文；修改权限属于 Control Plane，与应用规则的运行时判定分开。
## 9. Modelry Control Plane 与身份

### 9.1 Owner

- **身份与归属：** Owner 是当前 ProjectRuntime 的管理面 Principal，由稳定 Owner 身份标识；不是 App User。V0.1 仅有一个 Current Owner。
- **生命周期：** 首次 Bootstrap 创建，Bootstrap Capability 随成功关闭；Owner 身份在 Runtime Restart 后仍存在。V0.1 不定义额外 Administrator 管理。
- **可变性与持久性：** Owner 身份及必要管理面认证状态耐久。显示 Email 等资料按管理面认证规则管理；是否支持转让、删除或增加 Owner 不由本 Spec 扩展。
- **安全边界与关系：** 拥有 V0.1 管理面 Full Access，受 Admin Authentication 保护；其认证 Credential 与 Application PasswordCredential、Service Account APIKey 均不可混用。Owner 可创建、查看、撤销 Service Account / API Key，并访问授权的 Audit。

### 9.2 ServiceAccount

- **身份与归属：** 由稳定 `ServiceAccountID` 标识，属于一个 ProjectRuntime，是服务或 Coding Agent 使用的 Control Plane Principal。
- **生命周期：** 创建后为 Active，可 Disable；禁用后不得继续使用该身份的 API Key 执行操作。V0.1 可有多个 Service Account，但不借此开放额外管理员身份。
- **可变性与持久性：** Name、Description、Permission 与状态可按授权管理操作修改，变化耐久。身份 ID 不因改名改变。
- **安全边界与关系：** ServiceAccount 拥有一个 Permission Grant，可关联一个或多个 APIKey。它不是 ApplicationUser，也不绕开同一套 Backend Semantics、Access Rule、Change Lifecycle 与 Audit。

### 9.3 APIKey

- **身份与归属：** 由稳定 `APIKeyID` 标识，属于且只属于一个 ServiceAccount；是该 Control Plane Principal 的 Credential，不是 ServiceAccount 身份本身。
- **生命周期：** 创建后 Active；明文只在创建成功时一次性 Reveal；之后可 Revoke。其所属 ServiceAccount Disabled 时不可用于认证。
- **可变性与持久性：** Key 身份、关联、状态与必要的验证表示耐久；明文只短暂展示，不可再读回。Revoke 是耐久、不可逆的安全事实；重新创建新 Key 产生新身份。
- **安全边界与关系：** 只授予关联 ServiceAccount Permission 所允许的操作。明文不得进入 AuditRecord、RequestRecord、Record、Error 或常规列表响应。

### 9.4 Permission

- **身份与归属：** Permission 是针对 Project Control Plane 操作的授权范围 / Grant，归属于 Owner（V0.1 Full Access）或 ServiceAccount。它表达许可集合，不是 Principal，也不是 AccessRule。
- **生命周期：** 创建 ServiceAccount 时配置，随后可按授权变更；更改后影响关联身份的后续操作。已发生的 AuditRecord 不因 Permission 变化被改写。
- **可变性与持久性：** Grant 耐久保存。V0.1 对外只有 Full access、Read only、Custom 等受控表达；Domain 内可表达被允许的管理操作，但不引入通用 Capability Graph 或 Advanced RBAC。
- **安全边界与关系：** Permission 仅管 Modelry 管理面资源，不替代应用 Collection AccessRule。所有管理操作在执行时必须检查有效 Permission；默认不得多授予。

## 10. Observability

### 10.1 RequestRecord

- **身份与归属：** 每次 Application HTTP 请求拥有一个稳定、规范的 `RequestID`，在请求、结构化错误、Runner 结果和 Request Detail 间保持一致。记录属于一个 ProjectRuntime 的 Application Request Observability。
- **生命周期：** 请求完成后形成可查看的记录；处理中的中间值可更新，完成后结果固定。请求详情可从直接 Runner 结果打开，不要求用户复制 RequestID 后再搜索。
- **可变性与持久性：** 最终元数据是耐久、不可由用户编辑的操作记录，至少覆盖 RequestID、时间、Endpoint、Method、Status、Duration，以及安全范围内的认证 / 授权结果。Retention 时限不是 Domain 身份的一部分，需由 Request Contract 明确；不能声称未规定的保留年限。
- **安全边界与关系：** RequestRecord 面向 Application API 运行遥测，不等同 AuditRecord。不得记录或展示 Raw Credential、Raw Authorization Header、完整敏感 Body 或无限制 Raw Header / Query。它可关联相关错误与 Audit 上下文，但关联不授权读取秘密。

### 10.2 AuditRecord

- **身份与归属：** 每项 Control Plane Security / Governance 事件由稳定 `AuditRecordID` 标识，属于一个 ProjectRuntime 的 Audit History；记录 Actor Principal、Action、Resource、Time、Result 及适用的 request correlation。
- **生命周期：** 发生符合 V0.1 Minimal Audit 范围的安全 / 治理行为时追加记录。保存后的事实不可编辑或删除；不同事件产生新记录。
- **可变性与持久性：** 是耐久、追加式事实。审计留存期限属于后续运维边界，不能将其与 API Request Log 合并或假设为完整 Activity Timeline。
- **安全边界与关系：** Control Plane 读取需 Owner / Permission 授权。不得包含明文 Credential、API Key、Password、Session Token 或完整敏感 Body。Actor 关联 Owner / ServiceAccount；审计的内容是管理安全 / 治理动作，不是所有 Application 请求。

## 11. 关系总览

```text
ProjectRuntime
├── RuntimeStatus / StorageStatus                 （运行观察值）
├── Collection
│   ├── Field ── Validation / Default
│   ├── Field(Relation) ── Target Collection
│   ├── Index ── Fields
│   ├── Record ── RecordID
│   ├── AccessRule                                （独立于 Schema Change）
│   └── ApplicationUser（Auth Collection）
│       ├── Profile Record
│       ├── PasswordCredential
│       └── Session(s)
├── Schema ChangeSet（单 Collection）
│   ├── PendingOperation(s)
│   ├── StructuredDiff / Risk / Precondition / Impact
│   ├── ApplyAttempt(s) ── RecoveryState（若需要）
│   └── AppliedMigration（成功后不可变）
├── Owner / ServiceAccount ── Permission
│   └── ServiceAccount ── APIKey(s)
└── RequestRecord(s) / AuditRecord(s)
```

## 12. 安全边界不变量

- **Plane 分离：** Owner Authentication / Backend Model / Changes / Service Accounts / API Keys / Audit 属于 Modelry Control Plane；Records / Application Auth / Application Sessions / Files / Application API 属于 Application Data Plane。
- **身份与秘密分离：** Owner、ServiceAccount、ApplicationUser 是 Principal；Password、API Key、Session Token 是认证材料或状态。任何 Credential 都不能被建模成普通 Field 值。
- **双重授权不混用：** Permission 决定管理面 Principal 可执行哪些 Modelry 管理操作；AccessRule 决定 Application Principal 对 Collection Record 能执行哪些操作。
- **默认拒绝：** Application Access Rule 默认 Fail Closed；Control Plane Permission 也不能因缺省值变为额外授权。
- **敏感遥测最小化：** RequestRecord 与 AuditRecord 只保存完成产品观察 / 治理所需的安全元数据，不保存明文认证秘密或不受限请求内容。
- **统一业务语义：** Admin、HTTP、CLI、MCP 不拥有绕过 Change Lifecycle、Permission、AccessRule 或 Audit 的隐藏路径。

## 13. 范围外

本 Spec 不定义或引入：HTTP Paths / DTO、OpenAPI 表达、SQL Tables、SQL Migration 文件形状、SQLite 专属 Domain 字段、React 页面 / 组件、PostgreSQL 实现、Organization / Environment / Tenant / Cloud Control Plane、多 Project Runtime、Realtime、Lifecycle Hooks、JS / TS Extension Runtime、Secrets UI、Event Hooks / Webhooks、Policy Simulation、额外管理员管理、Generic Activity Timeline、Full Drift Detection、可编辑 Runtime Settings、多文件值、S3、OAuth、邮件验证投递、密码重置邮件、Jobs / Cron、SDK Generation 或 Import / Export。

## 14. ADR-0001 一致性

以下实现事实由 ADR-0001 冻结，Domain 保持其上的逻辑语义：

1. ProjectRoot 依 `--project-root`、`MODELRY_PROJECT_ROOT`、启动时工作目录的优先顺序解析；其绝对路径不是 Project ID。
2. Runtime 与 Storage 生命周期、真实 READY 条件、SQLite 连接设置及 Local Storage 的分项健康诊断均遵从 ADR-0001。
3. ApplyAttempt、AppliedMigration、Physical Migration 与 Ledger 使用 ADR-0001 的原子提交和不可变历史边界；失败后 Pending Change 保留，未结束尝试在重启后可识别为中断 / 待恢复。
4. App User 创建在一个 SQLite 事务内协调 Profile Record 与 PasswordCredential；Credential / Session 状态变化遵从 ADR-0001 的事务边界。
5. Local Single-file Field 的临时上传、绑定、不可变文件移动、清理与失败恢复遵从 ADR-0001 的 reconcile 规则；SQLite 与文件系统副作用不被描述为单一原子事务。
6. Graceful Shutdown 先撤销 READY、停止新请求并有界排空，然后关闭 Storage / SQLite；未提交事务回滚，已提交事实保持有效。
