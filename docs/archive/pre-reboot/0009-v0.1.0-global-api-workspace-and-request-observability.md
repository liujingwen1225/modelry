# Spec 0009 — V0.1.0 Global API Workspace and API Request Observability

- **Status:** Review Candidate — Awaiting User Review
- **Date:** 2026-09-23
- **Issue:** #169
- **Target:** V0.1.0 pre-release API workspace + request observability
- **Applies to:** Admin UI, Application HTTP Runtime, Control Plane read API, SQLite runtime storage
- **Depends on:** Spec 0008 Admin Frontend V2, Frozen Contract 0001, public OpenAPI projection
- **Contract impact:** intentional V0.1.0 contract extension required before Runtime implementation

> 本 Spec 定义 Modelry 的全局 Application API 工作区，以及支撑 API Request Logs 所需的 Runtime 观测能力。
>
> 核心结论：
>
> **API 是整个 Backend 的一等开发入口；Endpoints 告诉用户“暴露了什么”，Requests 告诉用户“真实发生了什么”。**

---

# 1. 背景

当前 Admin 的 API Usage 主要存在于单个 Collection 上下文：

```text
Collections
  -> posts
     -> API
```

这种方式适合调试一个 Collection，但无法快速回答：

- 整个 Backend 暴露了哪些 Application API？
- 某个 Endpoint 属于哪个 Collection？
- Auth API 与 Data API 的整体情况是什么？
- 最近哪些 Application Request 失败？
- 一次真实 API Runner 请求为什么得到 401 / 403 / 404 / 422 / 500？
- Request 与 Authentication / Policy / structured error 之间是什么关系？

同时，现有 Audit / Activity 不应承担 Application API 请求流水：

```text
Audit
-> Control Plane security/governance facts

Activity
-> Runtime/Migration/Hook 等跨模块运行事件

API Requests
-> Application Plane HTTP operational telemetry
```

因此需要一个独立但轻量的全局 API Workspace。

---

# 2. 产品决策

Admin 一级导航调整为：

```text
Core
  Overview
  Collections
  API

Control
  Changes
  Hooks
  Access

System
  Settings
  Activity
```

全局 API 页面固定两个 local view：

```text
API
  Endpoints      <- default
  Requests
```

其中：

- **Endpoints**：Backend-wide Application API catalog + inspect/run entry；
- **Requests**：Application API structured request logs；
- Collection 内现有 `API` 保留，继续承担当前 Collection 上下文的 API Explorer / Runner；
- Global API 与 Collection API 必须复用同一 Endpoint model、Detail、Runner 和 request execution path，不允许形成两套实现。

这条产品决策明确覆盖此前“Admin 不设置独立顶层 API”的旧 IA。

---

# 3. 边界

## 3.1 Global API 只展示 Application Plane

全局 API 默认只包含：

- Collection Data API；
- Auth Collection 对应 Auth API；
- 未来已正式支持并有清晰 HTTP/connection semantics 的 Application capability。

明确排除：

```text
/_modelry/api/v1/*
```

Control Plane API 是 Modelry 自身的管理协议，不进入 Application API Catalog。

现有公共：

```text
GET /api/v1/openapi.json
```

已经冻结为 **Application-only OpenAPI projection**，可以作为 Endpoints inventory 的权威机器来源之一。

## 3.2 第一版 Request Logs 只覆盖有限 HTTP 请求

V0.1 Request Logs MVP 覆盖：

- Application Data API；
- Application Auth API；
- API Runner 发出的真实 Application Request。

以下暂不纳入第一版详细 Request Log：

- 长连接 Realtime/SSE 生命周期；
- Control Plane Admin API；
- static Admin assets；
- OpenAPI 文档读取本身。

Realtime/SSE 后续应使用 connection/session telemetry，而不是硬套 finite HTTP request duration 模型。

# 4. Global API — Endpoints

## 4.1 页面目的

回答：

> 当前 Backend 暴露哪些 Application API？我要如何找到、理解并验证它们？

## 4.2 首屏结构

```text
API
[Endpoints] [Requests]

Search endpoints...

Collection: All ▼
Kind: All / Data / Auth
Method: All ▼
Auth: All ▼

────────────────────────────────────────────────────
Collection   Method   Endpoint                 Kind
posts        GET      /api/v1/posts            Data
posts        POST     /api/v1/posts            Data
posts        GET      /api/v1/posts/:id        Data
users        POST     /api/v1/auth/login       Auth
users        POST     /api/v1/auth/register    Auth
```

默认按 Collection + route 组织，但 Search / Filter 结果必须保持稳定 URL state。

## 4.3 Endpoint Detail

点击 Endpoint 后使用同一页面 detail pane，不弹 Modal：

```text
GET /api/v1/posts/:id

Collection        posts
Kind              Data
Operation ID      dataGetRecord
Authentication    Application Auth / Anonymous allowed

Parameters
Headers
Body
Responses

[Run Request]
```

Secondary actions：

- Open in Collection；
- Copy path；
- Copy curl；
- View OpenAPI；
- View Requests for this Endpoint。

## 4.4 Runner

Global API Runner 与 Collection API Runner 必须是同一个 canonical runner。

Authentication boundary：

- 发送真实 Application Plane request；
- 不自动携带 Admin Control Plane Session/API Key；
- 用户显式选择 Anonymous 或 Application credential/context；
- Application credential 不写入 Project Secret、localStorage 或 Control Plane Credential；
- DELETE 等明显 destructive request 必须确认。

Runner 返回后必须保留：

- status；
- duration；
- response；
- structured error（如有）；
- Runtime canonical requestId。

当 Request Logs 已实现时显示：

`View Request Log`

# 5. Collection API 与 Global API 的关系

Collection Workspace 继续保留：

```text
Records
Schema
Policy
Auth
API
```

Collection API 回答：

> 当前 Collection 的 API 怎么用？

Global API 回答：

> 整个 Backend 有哪些 API，最近这些 API 实际发生了什么？

二者关系：

```text
Global API / Endpoints
      ↓ Open in Collection
Collection / API
      ↓ Run Request
Request ID
      ↓ View Request Log
Global API / Requests
```

推荐 deep link：

```text
/admin/api/endpoints
/admin/api/endpoints?collectionId=<id>
/admin/api/endpoints?operationId=<operationId>

/admin/api/requests
/admin/api/requests?collectionId=<id>
/admin/api/requests?operationId=<operationId>
/admin/api/requests?requestId=<requestId>
```

Collection API 的 `View Request Logs` 必须进入同一个 Global Requests workspace，而不是建立 Collection-specific Logs 页面。

# 7. Request Log Domain Model

第一版每一条 durable request log 只保存结构化 metadata。

建议 domain：

```text
ApiRequestLog
  id
  requestId
  startedAt
  durationMs

  apiKind
  operationId
  method
  routeTemplate
  collectionId?

  statusCode
  responseSizeBytes?

  authState
  applicationPrincipalId?

  policyDecision?
  policyOperation?

  errorCode?
  correlationId?
```

推荐 enum：

```text
apiKind:
  Data
  Auth

authState:
  Anonymous
  Authenticated
  AuthenticationFailed

policyDecision:
  Allowed
  Denied
  NotEvaluated
```

约束：

- `requestId` 唯一；
- `applicationPrincipalId` 仅在身份已成功证明后记录；
- Auth failure 不记录 email/username/password 等输入；
- Policy denied 可以记录 decision + operation，但不得 dump Policy evaluation context。

---

# 8. Request ID

Frozen Contract 已要求 structured error 中的 `requestId` 可追踪。

为了让成功请求也能从 API Runner 直接 deep link Request Log，Contract Extension 应冻结 Application HTTP response header：

```text
X-Modelry-Request-Id: req_...
```

规则：

- Runtime 为每个 Application HTTP request 生成 canonical requestId；
- 不接受客户端通过同名 header 覆盖 Runtime canonical requestId；
- error envelope 中的 `error.requestId` 与 response header 必须一致；
- Request Log 使用同一 canonical requestId；
- API Runner 展示同一 requestId。

---

# 9. 数据采集生命周期

推荐单一 structured request observation path：

```text
HTTP Request
  ↓
Request Context / canonical requestId
  ↓
route resolution
  ↓
authentication
  ↓
policy
  ↓
handler
  ↓
response / structured error
  ↓
ApiRequestLogSink
  ↓
SQLite
```

必须只有一条最终 request record，不从 console text 反向解析。

Request Log 是 operational telemetry：

- 不参与业务 Record transaction；
- Request Log 写失败不得改变原 Application response；
- 日志写失败必须进入 Runtime diagnostic/Activity，而不是递归写另一条 request log；
- 不允许因为 request logging 失败把成功业务请求变成 5xx。

建议新增内部表：

```text
api_request_logs

policy_decision            NULLABLE

```

建议索引：

- `request_id UNIQUE`；
- `started_at DESC`；
- `collection_id, started_at DESC`；
- `operation_id, started_at DESC`；
- `status_code, started_at DESC`；
- `error_code, started_at DESC`。

Request Logs 是 Runtime internal storage，不属于 Application Collection，不进入 Backend Model，不允许通过 Record API 修改。

# 11. 安全与隐私边界

V0.1 **禁止持久化**：

- request body；
- response body；
- raw request headers；
- raw response headers；
- Authorization；
- Cookie / Set-Cookie；
- API Key；
- access token / refresh token；
- password / passwordHash；
- Secret；
- query parameter values；
- raw client IP；
- login email/username on failed authentication。

允许：

- normalized route template；
- query parameter **names**（若实现需要；默认可以不存）；
- authenticated Application Principal ID；
- structured error code；
- Policy decision；
- response size metadata。

原则：

> Request Logs 用于定位请求生命周期，不用于复制业务数据。

任何未来增加 body/header capture 的方案必须单独做安全设计，不得通过“debug mode”隐式打开。

---

# 12. Retention 与容量保护

Request Logs 不永久保存。

V0.1 固定：

```text
Default retention: 7 days
Hard safety cap: 100,000 rows
```

Cleanup 必须：

- Runtime startup opportunistic cleanup；
- Runtime 运行期间周期 cleanup；
- 删除超过 retention 的旧记录；
- 超过 hard cap 时从最旧记录开始删除；
- cleanup failure 不影响 Application Request，但必须形成 diagnostic signal。

第一版不做用户自定义 retention UI。

后续若开放 Settings，必须作为 System Settings 的独立 observability 配置，不与 Audit retention 混用。

# 13. Control Plane Read API

Request Logs 是 Runtime observability resource，需要新增显式 Control Plane API。

计划冻结：

```text
GET /_modelry/api/v1/request-logs
GET /_modelry/api/v1/request-logs/{requestId}
```

## 13.1 List filters

```text
collectionId
operationId
route
method
status
errorCode
principalId
from
to
cursor
limit
```

要求：

- default limit 50；
- max limit 100；
- cursor pagination；
- stable order：`startedAt DESC, id DESC`；
- 不提供 mutation/delete single-log API。

## 13.2 Capability

第一版使用现有 Frozen capability：

```text
runtime:read
```

理由：

- Request Logs 是 Runtime operational telemetry；
- 它不是 Audit Fact；
- 不应滥用 `audit:read`；
- V0.1 不为了这一个功能增加新的 capability vocabulary。

未来若 observability 能力扩大，可独立评估 `logs:read` / `observability:read`，但不属于本 Spec。

# 14. Requests 与 Audit / Activity

必须保持：

```text
API Requests != Audit != Activity
```

### API Requests

- 高频；
- Application Plane；
- request/response execution metadata；
- 7-day retention；
- operational debugging。

### Audit

- Control Plane durable security/governance fact；
- Principal/Capability/critical action trace；
- 不能被 Request Logs 取代。

### Activity

- 跨模块运行事件；
- Migration / Hook / Runtime / Recovery 等；
- 不复制每一条 API Request。

只有聚合/异常事件，例如 Request Log storage failure，才可以进入 Activity。

---

# 15. Error / Partial State

Global API 必须区分：

### Endpoints unavailable

公共 OpenAPI projection 读取失败：

- Endpoints view 显示 Unavailable；
- Requests view 若其 Runtime API 正常，可独立继续使用；
- 不把空数组伪装成“0 endpoints”。

### Requests unavailable

Request Logs Runtime API 不可用：

- Requests local view 显示独立 Error/Permission State；
- Endpoints 不受影响。

### Partial capability

没有 `runtime:read`：

- Endpoints 仍按其实际访问边界工作；
- Requests 显示 Permission State；
- 不让整个 Global API 页面失败。

---

# 16. 非目标

第一版明确不做：

- request body capture；
- response body capture；
- raw header capture；
- raw client IP；
- live tail；
- WebSocket log streaming；
- log export；
- log analytics dashboard；
- P50/P95/P99；
- distributed tracing backend；
- OpenTelemetry collector/exporter；
- user-defined retention；
- Control Plane request log catalog；
- long-lived SSE connection telemetry；
- Custom API 特殊日志模型。

# 17. Contract Extension 要求

Request Logs 不是当前 Frozen Contract 已存在的资源。

因此实施顺序必须是：

```text
Spec 0009 Accepted
  ↓
Explicit Frozen Contract Extension
  ↓
OpenAPI + manifest + frontend mapping update
  ↓
Runtime implementation
  ↓
Admin Requests UI
  ↓
Browser acceptance
```

不能标记为“Contract Gap”，因为它是明确新增产品能力。

Contract Extension 至少应冻结：

- request log list/detail routes；
- DTO；
- filters/pagination；
- `runtime:read` capability；
- `X-Modelry-Request-Id` response header；
- redaction guarantees；
- error responses。

# 20. Definition of Done

- [ ] Admin 一级导航包含 Global `API`；
- [ ] Global API 固定 `Endpoints | Requests`；
- [ ] Endpoints inventory 只包含 Application Plane；
- [ ] `/_modelry/api/v1/*` 不出现在 Application Endpoint Catalog；
- [ ] Global / Collection API 共用 canonical Endpoint Detail 与 Runner；
- [ ] Endpoint 支持 Global <-> Collection deep link；
- [ ] Request Logs 有明确 Runtime domain/storage，而不是解析 console log；
- [ ] 每个 finite Application HTTP request 最多形成一条 final structured request log；
- [ ] 成功/失败请求使用同一 canonical requestId；
- [ ] 成功 Application response 暴露 `X-Modelry-Request-Id`；
- [ ] Request Logs 使用 `runtime:read`；
- [ ] Request Logs 与 Audit / Activity 严格分离；
- [ ] 不保存 body、raw headers、credentials、query values、client IP；
- [ ] Auth failure 不泄漏 login identifier；
- [ ] Policy denied 不泄漏 evaluation context；
- [ ] 默认 retention 7 days；
- [ ] hard cap 100,000 rows；
- [ ] cursor pagination；
- [ ] Runner -> Request Log 闭环成立；
- [ ] Contract Extension 已正式冻结，不以 Contract Gap 名义混入；
- [ ] Spec 0007 恢复时增加对应 Global API / Request Logs Browser Acceptance。
