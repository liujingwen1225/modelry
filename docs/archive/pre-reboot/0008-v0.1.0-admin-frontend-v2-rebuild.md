# Spec 0008 — Modelry Admin Frontend V2 Rebuild

- **Status:** Review Candidate — Awaiting User Review
- **Date:** 2026-09-23
- **Issue:** #167
- **Target:** V0.1.0 pre-release Admin frontend rebuild
- **Applies to:** `frontend/admin`
- **Supersedes:** current Admin UI implementation structure and visual component implementation; Spec 0003 V4 visual reference; Spec 0003 Collection secondary IA for `Relations` / `Indexes`; Spec 0003 user-visible IA naming for `Governance & Security / Hooks & Events / Access & Audit / Project / Project Settings`; Spec 0003 no-top-level-API IA decision
- **Does not supersede:** Frozen V0.1.0 API Contract or Backend/Runtime semantics unless an explicitly accepted dependent Spec extends them; Spec 0003 page responsibilities remain valid except the explicit IA overrides declared here
- **Authoring baseline:** `develop@4d99c2b80b10e4efb5e5e7d02513a8205719e1d2`

> 本 Spec 定义 Modelry Admin Frontend V2。它不是旧前端的样式重构，而是基于既有 Runtime、Frozen Contract 与已确认 Admin IA 的完整前端重建。
>
> 核心原则是：**先定义用户要完成的业务任务，再定义页面内容和操作，再定义组件与技术实现。**
>
> 旧 `frontend/admin` 只作为业务能力、已有交互和边界条件的参考来源，不具有组件结构、CSS、页面布局或视觉实现的继承权。

---

## 1. 背景

当前 Admin 已经覆盖 Collections、Records、Schema、Relations、Indexes、Policy、Auth、API、ChangeSet、Hooks、Access、Audit、Secrets、Settings、Activity 等大量能力，但前端实现经历多轮迭代后存在明显一致性问题：

- 相同业务动作在不同页面采用不同布局、按钮和反馈方式；
- 页面直接写 Tailwind / CSS，绕过统一组件；
- Dialog、Drawer、Table、Form 等复杂组件存在多种实现；
- 页面承担过多布局和视觉决策；
- 业务行为与 UI 结构耦合，难以稳定交给 Agent 持续维护；
- Browser Acceptance 尚未完成，而继续对旧 UI 扩展视觉与交互测试会形成可抛弃基线。

因此在 V0.1.0 正式发布前，利用 pre-release 无历史 UI 兼容义务的窗口，直接建立 Admin Frontend V2。

---

## 2. 目标

Admin V2 必须同时解决以下问题：

1. **业务任务清晰**：每个页面都明确回答一个用户问题。
2. **业务闭环清晰**：用户操作后能明确知道系统状态发生了什么变化。
3. **信息层级一致**：页面先展示决定下一步操作所需的信息，而不是堆叠统计卡片。
4. **模型变更一致**：Backend Model / Runtime Config 变更统一走 ChangeSet。
5. **数据操作与模型操作明确分离**。
6. **Control Plane 与 Application Data Plane 明确分离**。
7. **所有页面使用统一 Design System**。
8. **业务页面不再自由定义 Button / Form / Dialog / Table 的视觉行为**。
9. **Server State、Form State、URL State、Local UI State 各自职责明确**。
10. **为恢复 Spec 0007 Playwright Browser Acceptance 提供稳定页面语义和测试选择器。**

---

## 3. 非目标

本 Spec 明确不做：

- 不改变 Backend Model、Runtime、数据库或 Frozen API Contract；
- 不改变 Spec 0003 已确认的一级页面集合与职责；仅收敛用户可见导航命名：`Governance & Security / Hooks & Events / Access & Audit` -> `Control / Hooks / Access`，`Project / Project Settings` -> `System / Settings`；
- 不新增独立顶层 Data 页面；
- 顶层 `API` 仅作为 Application Plane workspace，不引入独立 Control Plane API Catalog；
- 不新增 V0.1.x 才支持的产品能力；
- 不以“重建前端”为理由修改后端业务语义；
- 不为旧 React Component API、CSS class、DOM 结构或截图保留兼容；
- 不复制旧组件后逐步修样式；
- 不把 shadcn 默认视觉直接当成 Modelry 产品视觉；
- 不引入 Redux / Zustand 作为默认全局状态方案；
- 不引入 Next.js；
- 不在本 Spec 内完成正式 Playwright 全量验收，Spec 0007 在 V2 核心页面稳定后恢复。

# 4. Admin 的核心用户任务模型

Modelry Admin 不是传统“系统配置后台”，而是开发者管理 Backend 的 Control Plane。

用户进入 Admin 后，核心问题按优先级分为：

```text
1. 我的 Backend 当前是否可用？
2. 我有哪些 Collection？
3. 当前 Collection 的数据是什么？
4. 当前 Collection 的模型是什么？
5. 我要如何修改模型？
6. 这个修改会造成什么影响？
7. 修改是否已经真正生效？
8. 谁可以管理 Backend？
9. 系统最近发生了什么？
10. 出错后我应该去哪里处理？
```

页面结构必须围绕上述问题建立。

# 5. 固定信息架构

除本 Spec 明确覆盖的导航命名、Relations/Indexes 合并与 Global API 新增外，其余继续遵守 Spec 0003。

## 5.1 一级导航

```text
Core
  Overview
  Collections
  API

Control
  Changes
  Hooks
  Access

System
  Settings
  Activity
```

### Control naming

V2 将 Spec 0003 的用户可见导航名称进一步收敛：

```text
Governance & Security  -> Control
Hooks & Events         -> Hooks
Access & Audit         -> Access
```

这只是导航命名与页面标题优化，不改变页面职责：

- `Changes` -> Backend Change governance；
- `Hooks` -> V0.1 Lifecycle Hook registry / health；
- `Access` -> Control Plane access management；页面内部仍保留 `Access | Audit` 两个 local view。

采用 `Control` 的原因是这组三个页面共同回答：

> Backend 如何变化、哪些扩展在运行、谁可以管理它？

V0.1 不把尚未支持的 Event/Cron/Webhook/Delivery 暗示在导航名称中，因此使用 `Hooks` 而不是 `Hooks & Events`。

### System naming

V0.1 不提供多 Project 管理、Project Switcher 或 Projects 列表。

因此用户可见 IA 使用：

- Sidebar group：`System`；
- Sidebar item：`Settings`；
- Page title：`System Settings`。

这条规则明确覆盖 Spec 0003 中 `Project / Project Settings` 的旧命名，但不改变 Runtime 内部的 Project Root / Project Source / config truth 技术语义。

禁止恢复独立顶层：

- Data
- Schema
- Secrets
- Auth

其中 `API` 是明确的例外：V2 新增一个 Backend-wide **Application API Workspace**，但 Control Plane API 仍不作为产品级 API Catalog 展示。

Global API 与 Collection API 的关系由 Spec 0009 定义；二者必须共享 Endpoint model / Detail / Runner，而不是形成两套实现。

## 5.2 Collection Workspace

进入某个 Collection 后，二级导航收敛为：

```text
Records       <- default
Schema
Policy
Auth          <- Auth Collection only
API
```

其中 `Schema` 是统一的 Collection Model Workspace，内部包含：

```text
Schema
  Fields      <- default
  Relations
  Indexes
```

这条规则明确覆盖 Spec 0003 §3 与 Acceptance Override #5 中把 `Relations` / `Indexes` 作为独立 Collection 二级入口的旧定义；Spec 0003 的一级 IA、Collection context、API 归属和 Access/Audit 职责继续有效。

Collection 二级能力的业务含义固定为：

- `Records` -> 真实数据；
- `Schema` -> Collection 结构（Fields / Relations / Indexes）；
- `Policy` -> Application Record Authorization；
- `Auth` -> Application Authentication（仅 Auth Collection）；
- `API` -> 当前 Collection 的 Application API 使用与验证。

Collection 仍是：

- Data Usage；
- Backend Modeling；
- API Usage；

的共同工作入口。

# 6. 全局应用框架

## 6.1 App Shell 的业务职责

App Shell 只承载全局上下文，不承载具体业务功能。

必须包含：

- 当前 Instance identity；
- 一级导航；
- 当前 Runtime 状态入口；
- 当前登录 Admin Principal；
- Current Session / Logout 入口；
- 全局命令入口；
- Theme / Language；
- 全局 Toast / Notification Surface。

不得把大量 Dashboard 指标、Collection 操作或 ChangeSet 操作塞进 Sidebar。

### Admin Session client boundary

必须遵守 Frozen Control Plane Auth：

- access credential 只保存在前端 memory，不写入 localStorage / sessionStorage；
- refresh material 只由 HttpOnly Cookie 承载，Frontend JavaScript 不读取；
- access credential 到期后通过 refresh transport 轮换；
- refresh 失败/Session revoked 后返回 Login，并尽可能保留原 deep link；
- Logout 调用真实 Control Plane logout，撤销当前 server-side session 并清理本地 access credential。

## 6.2 Runtime 状态

用户在任何页面都必须能够辨认 Runtime 是否处于：

- Ready；
- Pending Migration；
- Drift；
- Recovery Required；
- 部分数据不可读取。

状态异常时必须提供明确跳转目标，例如：

```text
Pending Migration    -> Changes
Unexported Artifacts  -> Changes
Drift                 -> Changes
Config Recovery       -> System Settings
Operational Error     -> Activity
```

不得只用红点而不告诉用户下一步。

## 6.3 全局操作反馈

持久化操作必须区分：

- started；
- succeeded；
- partially succeeded；
- failed；
- requires confirmation；
- requires follow-up。

Toast 只用于瞬时反馈，不作为最终结果唯一载体。

## 6.4 页面操作统一规则

所有核心工作面必须遵守以下交互约束：

1. **一个工作面只有一个明显主操作。** Secondary / overflow / row action 不得与主操作抢视觉层级。
2. **列表负责选择对象，Sheet/Drawer 负责查看或编辑一个对象，Dialog 负责高风险/不可逆确认。**
3. **持久化成功后，真实 durable result 必须留在当前上下文可见。** 不能只 Toast 后关闭界面，让用户重新寻找结果。
4. **Backend Model Draft 统一通过 Review Changes。** POST 前可展示 Frontend Preview；POST 后 Review 必须切换为 Runtime-canonical Structured Diff、Risk、Impact Flags、Preconditions 与受影响数据。
5. **Risk / Impact / expandsAccess 不是用户输入。** Frontend 可以基于 Draft 计算即时 Preview，但 POST ChangeSet 后由 Runtime 重新计算；**Runtime 返回的 ChangeSet Risk / impactFlags / Preconditions 才是 Apply 的权威值**。若 Runtime 提升风险，UI 必须按返回结果重新进入确认流程。
6. **Capability 决定可操作性，不由 Principal type 推断。** inspect / propose / apply / mutate / audit 等动作必须按 Frozen Capability 单独 gate；没有 Apply 权限时可以保留 Propose/Save ChangeSet，但不能显示可执行 Apply。
7. **复合页面按子能力独立失败。** 一个子视图无权限不能让整个页面失效，例如 Access 与 Audit、Auth Configuration 与 Sessions、Settings Runtime 与 Secrets 必须各自按 capability 呈现。
8. **Metric Card 不是默认页面结构。** 只有指标会改变用户下一步决策时才使用。
9. **二级工具不得挤占主任务。** Simulation、OpenAPI Export、Graph 等必须作为 secondary action；未被 Runtime 支持的 Import/Export 等动作不得展示占位 UI。
10. **同一个可变业务对象只有一个 Canonical Editor / Draft / submit path。**

推荐页面骨架：

```text
Context / Title
-> conditional Attention / Impact
-> Primary Work Surface
-> one Primary Action
-> contextual Secondary Actions
-> Durable Result visible in-place
```

## 7.1 Bootstrap

### 页面目的

回答：

> 这是一个全新的 Modelry Instance，我如何建立第一个 Admin 身份？

### 核心内容

必须展示：

- 当前 Instance 基本身份；
- Bootstrap 状态；
- Setup Token 输入；
- Admin Email；
- Password；
- Bootstrap 的安全说明。

### 主操作

`Create Admin / Complete Bootstrap`

### 业务结果

成功后：

```text
Bootstrap
-> Admin Principal created
-> Admin credential/session established
-> Bootstrap endpoint no longer acts as normal login path
-> redirect Overview
```

### 状态

必须覆盖：

- invalid setup token；
- already bootstrapped；
- expired/invalid request；
- network/runtime unavailable；
- submit in progress。

## 7.2 Login

### 页面目的

回答：

> 我如何进入这个 Modelry Instance 的 Control Plane？

### 核心内容

- Admin Email；
- Password；
- Instance identity；
- 登录错误。

### 主操作

`Sign in`

### 业务结果

```text
Credential accepted
-> Control Plane Session created
-> current Principal resolved
-> return original deep link if available
```

### 禁止

- 不展示业务 Auth Collection 用户登录；
- 不把 Admin Login 与 Application Auth 混为一体。

## 7.3 Overview

### 页面目的

Overview 不是“统计 Dashboard”，而是回答：

> 我的 Backend 现在是否健康？我现在最需要处理什么？

Overview 是 **Action Center + Backend Health**，不是 Collections、Changes、Activity 的缩略复制。

### 信息优先级

#### 第一层：Needs Attention

只有存在需要处理的事项时显示，例如：

- Drift；
- Pending Migration；
- Unexported Migration Artifact；
- Recovery Required；
- Pending / high-risk ChangeSet；
- failed Lifecycle Hook；
- Database / Storage 异常；
- Project Source 不可写；
- 部分核心数据读取失败。

每一项必须明确：

- 问题是什么；
- 当前影响是什么；
- 建议下一步；
- 去哪里处理。

异常项按影响优先于正常状态展示。

#### 第二层：Backend Health

只展示会影响当前工作判断的项目级健康事实：

- Runtime；
- Database；
- Storage；
- Migration / Drift / Unexported Artifacts；
- Project Source。

正常状态保持紧凑；异常状态提供解释和入口。

读取失败时状态必须显示 Unknown / Unavailable，不能伪装为 Ready 或 0。

#### 第三层：Continue Recent Work

只展示 1～3 个真正可以继续处理的最近工作，例如：

- 最近编辑的 Collection；
- 尚未处理的 ChangeSet；
- 最近失败后可 Retry 的操作。

其作用是继续任务，不是重新列出 Collection inventory。

#### 第四层：导航入口

提供进入：

- Collections；
- Changes；
- Activity；

的清晰入口，但不复制这些页面的列表或完整时间线。

### 主操作

没有固定 “Create Anything” 主按钮。

Overview 的主行为是：

`Resolve Next Action / Continue Work`

### 禁止

- 不堆叠没有决策价值的 KPI；
- 不复制 Collection inventory；
- 不复制完整 Recent Activity timeline；
- 不用绿色 Ready 掩盖 Database / Storage / partial read failure；
- 不复制完整 ChangeSet 信息。

## 7.4 Collections

### 页面目的

回答：

> 我的 Backend 有哪些数据模型？我要进入或创建哪个 Collection？

Collections 是 **Collection 选择与创建入口**，不承担 Schema/Relation/Index 详情浏览。

### 展示方式

Collections 必须同时提供两种展示模式：

```text
[Card] [List]
```

规则：

- **默认使用 Card View**；
- List View 作为高密度浏览方式；
- 两种视图使用同一份 Collection query / filter / sort state；
- 切换视图不得改变当前 Search / Filter / Sort；
- 点击 Card 或 List row 都进入同一个 Collection Workspace；
- View mode 只是展示偏好，不产生业务状态，也不影响 URL 中的 Collection identity；
- 可以将用户最后一次选择作为本地 UI preference 保存；首次进入或没有偏好时必须回到 Card View。

这里的 Card 是 **Collection selection card**，不是 Dashboard Metric Card。它用于帮助用户识别和进入一个业务对象，因此不违反“Metric Card 不是默认页面结构”的全局规则。

### Card View（默认）

Card 必须保持克制，不做大型 Dashboard 卡片。

每张 Collection Card 默认展示：

```text
Collection Name                         Normal / Auth

Description（存在时，最多 2 行）

Records       <count>
Fields        <count>

Pending Change / Drift / Risk（仅存在时）

Last updated / concise metadata（有真实来源时）
```

卡片要求：

- Collection Name 是最主要识别信息；
- Normal / Auth 使用轻量 Badge；
- Record Count / Field Count 只作为 concise metadata，不做大号 KPI；
- Pending Change / Drift / Risk 只有存在时才突出；
- Relation / Index / Policy 详情不进入 Card；
- 整张 Card 可点击进入 Collection；
- secondary overflow 可提供已经 operable 的 Collection contextual action，但不得让多个按钮抢占 Card 主视觉；
- Description 不存在时不保留空白占位。

推荐布局：

- 1440px：3～4 columns；
- 1920px：4～5 columns；
- 1280px：至少保持 3 columns 或根据可用宽度自适应；
- Card 使用统一最小宽度，禁止因单个长 Name / ID 破坏整个 grid。

### List View

List View 面向 Collection 数量较多、需要快速扫描和比较的场景。

默认列：

```text
Name
Type
Records
Fields
Status
Updated
```

其中：

- Status 只显示 Pending Change / Drift / Risk 等需要用户关注的状态；正常状态保持简洁；
- 不常驻展示 Relation / Index / Policy 详情；
- 行点击进入 Collection；
- 支持与 Card View 完全相同的 Search / Filter / Sort。

### 核心内容

无论 Card / List，每个 Collection 只展示帮助用户选择对象的信息：

- Name；
- Collection Type：Normal / Auth；
- Record Count；
- concise model size，例如 Field Count；
- Pending Change / Drift / Risk 等异常或待处理状态；
- Description / Updated 等信息仅在有真实数据来源且有助于识别对象时展示。

Relation / Index 等模型详情只在异常、冲突或需要处理时显示摘要，不作为常驻 inventory 信息。

### 默认操作

点击 Collection：

```text
Collections
-> Collection Workspace
-> Records
```

### 主操作

`Create Collection`

创建时必须明确选择：

- Normal Collection；
- Auth Collection。

Create Collection 本身是 Model Change，最短路径为：

```text
Create Collection
-> enter required collection definition
-> Review Change
-> POST ChangeSet
-> use Runtime-returned canonical Risk / Preconditions
-> Apply / Confirm & Apply when authorized
-> durable Collection appears
```

用户只有 `changeset:propose` 而没有 `changeset:apply` 时，允许 `Save as ChangeSet`，不显示可执行 Apply。

Apply success 后直接进入新 Collection 的 Workspace，并让 durable Collection identity 可见；空 Collection 优先引导去 Schema 添加第一个 Field。

不得在 Apply 成功前把 Proposal 伪装成已创建 Collection。

### 辅助操作

- Card / List view switch；
- Search；
- Filter by type；
- Sort；
- direct deep link。

### 禁止

- 不把 Relation / Index / Policy 详情堆在 Collection List；
- 不提供没有真实 Runtime 支撑的 placeholder action；
- 不把 Import Schema 作为按钮占位但点击只弹 alert。

## 7.5 Global API

### 页面目的

回答：

> 整个 Backend 暴露了哪些 Application API？最近这些 API 真实发生了什么？

Global API 是 Backend-wide **Application API Workspace**，固定 local view：

```text
Endpoints      <- default
Requests
```

### Endpoints

Endpoints 聚合整个 Backend 的 Application Plane API：

- Collection Data API；
- Auth Collection 对应 Auth API；
- 后续已正式支持的 Application capability。

Endpoint inventory 使用现有 public Application OpenAPI projection：

```text
GET /api/v1/openapi.json
```

明确排除：

```text
/_modelry/api/v1/*
```

页面支持：

- Search；
- Collection filter；
- Data/Auth kind filter；
- Method/Auth filter；
- Endpoint Detail；
- shared real Application Runner；
- `Open in Collection`；
- `View Requests for this Endpoint`；
- OpenAPI secondary action。

Global API Runner 与 Collection API Runner 必须是同一个 canonical implementation。

### Requests

Requests 是 API Request Logs / operational telemetry，不是 Audit，也不是 Activity。

它的 Runtime/storage/Control Plane API、安全脱敏、Retention 与 capability 由 **Spec 0009** 定义。

在 Spec 0009 Runtime 未实现前：

- 不展示 fake Request rows；
- 不使用 mock/console log 冒充真实 request telemetry；
- 可以暂时隐藏 Requests local view，而不是展示不可用 placeholder。

实现后支持：

- Collection / Endpoint / Method / Status / Error / Time filter；
- cursor pagination；
- Request Detail Sheet；
- requestId deep link；
- Open Endpoint / Open Collection；
- API Runner -> Request Log 闭环。

推荐 URL：

```text
/admin/api/endpoints
/admin/api/requests
```

Global API 不改变 Collection Workspace 内 `API` 的存在；前者提供 Backend-wide 聚合与请求观测，后者保持当前 Collection 上下文。

# 8. Collection Workspace


## 8.1 Workspace Header

必须保持 Collection Context。

持续显示：

- Breadcrumb；
- Collection switcher；
- Collection name；
- Normal/Auth type；
- Pending Change / Drift / Risk 等当前需要处理的状态。

不持续显示与当前 Tab 强相关的统计：

- Record Count 由 Records 工作面展示；
- Field Count 由 Schema 工作面展示。

用户切换 Tab 时 Collection context 不丢失。

### Collection contextual actions

Workspace Header 的 secondary overflow 提供已经 operable 的 Collection-level 管理动作：

- `Collection Settings`；
- `Delete Collection`。

`Collection Settings` 使用一个 Sheet 编辑：

- name / label；
- description；
- softDelete；
- optimisticLock。

提交时按真实 operation 拆分为 `collection.rename` / `collection.update`，进入同一个 Collection Modeling Draft + Review Changes；不得用 drop + create 模拟 rename，stable Collection ID 必须保持。

`Delete Collection` 生成 `collection.drop`，必须经过 Review Changes，并以 Runtime-canonical destructive risk / checkpoint / Human Confirmation 为准。

这些都是 secondary contextual action，不与当前 Tab 的 primary action 抢层级。

当存在 pending model changes 时，Header 只显示简洁状态和：

`View Changes`

具体影响必须由相关业务页面在上下文中说明，而不是把 ChangeSet Detail 复制到 Header。

```text
Records · <record count>                         + Create Record
[Model Change Impact — only when relevant]
Search…   Filter   Sort   Columns                More
────────────────────────────────────────────────────
DataTable
```

不使用统计卡片行。

### Model Change Impact

- change summary；
- Runtime-canonical Risk；
- existing Record impact；

- field-driven stable columns；
- sort；
- filter；
- pagination；
- column visibility；
- row selection；

```text
select file
-> request Upload Session
-> upload bytes
-> show uploaded/pending state
-> Record mutation submits uploadSessionId reference
-> successful Record transaction commits the file binding
```

上传成功不等于 Record 已保存；Record mutation 失败时不得把 Upload Session 伪装为 committed。

## 8.3 Schema

### 页面目的

回答：

> 这个 Collection 的结构是什么？我要如何安全地修改 Fields、Relations 与 Indexes？

Schema 是 **Collection Model Workspace**，并且是 Fields / Relations / Indexes 的唯一 Collection 二级入口。

内部固定 local view：

```text
Fields      <- default
Relations
Indexes
```

三个 local view 共享：

- 同一个 Collection Modeling Draft；
- 同一个 Review Changes；
- 同一个 ChangeSet lifecycle；
- 同一个 Runtime-canonical Risk / Impact / Preconditions；
- 同一个 Apply / Confirm & Apply 结果闭环。

切换 local view 不丢失 Draft。

为刷新、浏览器返回、Agent deep link 与 Playwright 稳定性，三个 local view 必须可独立 deep link；推荐：

```text
/collections/:collectionId/schema/fields
/collections/:collectionId/schema/relations
/collections/:collectionId/schema/indexes
```

UI 中仍只显示一个 Collection 二级入口 `Schema`。

### 8.3.1 Fields

Fields 是默认 local view，也是 **Field Model Canonical Editor**。

首屏：

```text
Schema · <field count>
[Fields] [Relations] [Indexes]                    + Add Field
[Pending / Drift impact — only when relevant]
────────────────────────────────────────────────────────
Field        Type        Required        Features        …
title        text        Yes             searchable
author       relation    Yes             relation -> users
...
```

不展示 Total / Required / Searchable / Sortable metric-card row。

Field List 默认以 inspect 为主，不把每一行永久渲染成大量 Input / Select / Checkbox。

主操作：`Add Field`。

Add 或 Edit row -> `Field Editor Sheet`。

Field Editor 统一承载：

- Name / Label；
- Type；
- Required / Default；
- Validation；
- Searchable / Sortable；
- type-specific options；
- Relation configuration；
- File configuration。

Relation / File 都是 Field Type。

### 8.3.2 Relations

Relations 是 **Relation-oriented projection**，不是第二套 Model Editor。

首屏：

```text
Schema
[Fields] [Relations] [Indexes]                 + Add Relation
──────────────────────────────────────────────────────
Field       Target       Cardinality       Delete behavior
author      users        many-to-one       restrict
...
```

主操作：`Add Relation`。

Add / Edit Relation 使用 Fields 中完全相同的 Relation Field Editor：

```text
Relations view
-> shared RelationEditor
-> shared Collection Modeling Draft
-> Review Changes
-> ChangeSet
-> Apply
```

Schema Fields 与 Relations local view 对同一 Relation 必须产生完全相同的 Validation、Diff、Risk 与 Change Operation。

Relation graph 仅作为 collapsible secondary view，不作为主编辑器。

禁止：

- 第二套 Relation Draft；
- 第二套 Relation submit path；
- 与 Field Editor 不一致的 Relation validation。

### 8.3.3 Indexes

Indexes 是 Collection 结构中的查询与唯一性约束视图。

首屏：

```text
Schema
[Fields] [Relations] [Indexes]                    + Add Index
─────────────────────────────────────────────────────────
Name                 Type       Fields       Runtime Status
idx_posts_slug       Unique     slug         Applied
...
```

主操作：`Add Index`。

Add / Edit -> `Index Editor Sheet` -> 保存到共享 Collection Modeling Draft。

每个 Index row 的 secondary menu：

- Edit；
- Remove。

Remove 使用真实 `index.drop` operation，不直接修改 Runtime。

Index Review 除通用 Diff / Risk 外必须突出：

- referenced fields validity；
- uniqueness precondition；
- duplicate/conflict result；
- affected data；
- preview Risk（POST 后以 Runtime canonical Risk 为准）。

`Declared` 与 Runtime `Applied` 必须是不同状态。

### Shared Draft

Fields / Relations / Indexes 任一 local view 保存编辑后，都进入同一个 **Collection Modeling Draft**。

存在 Draft 时，在整个 Schema Workspace 显示统一 sticky action bar：

```text
<change count> unsaved model changes     Discard     Review Changes
```

`Review Changes` 是 Draft 状态下唯一主操作。

Draft 可以同时包含：

```text
field.add
relation.update
index.create
```

用户不需要为了完成一次 Collection Model 调整在三个 Collection 页面之间跳转。

### Review Changes

Review surface 在 POST 前可以展示 Frontend-derived Preview：

- Structured before/after Diff；
- preview Risk / impact；
- Preconditions preview；
- affected Records / conflict result（Runtime 有真实结果时）。

用户不得选择 SAFE / DATA_REWRITE / DESTRUCTIVE / IRREVERSIBLE，也不得手工勾选 expandsAccess。

点击 Apply 或 Save as ChangeSet 时，Frontend 先创建 ChangeSet；之后必须以 Runtime 返回的 canonical Risk / impactFlags / Preconditions 为准重新渲染 Review：

- canonical SAFE + expandsAccess=false + 当前 Admin 具备 `changeset:apply` -> `Apply`；
- canonical DATA_REWRITE / DESTRUCTIVE / IRREVERSIBLE / expandsAccess=true -> 受控 Human Admin `Confirm & Apply`；
- 无 `changeset:apply` -> 只能保存并 `Open in Changes`；
- secondary -> `Save as ChangeSet`。

Agent / Service 不能通过 UI 或请求字段自我充当高风险 Human Confirmation。

### 下一状态

Apply success：

```text
Review
-> Apply Attempt succeeds
-> Review closes
-> active Schema local view refetches
-> Draft clears
-> applied model remains visible
```

Save as ChangeSet：

```text
Review
-> Save as ChangeSet
-> Draft clears
-> inline success notice
-> Open in Changes
```

领域上仍严格保持：

`Propose -> ChangeSet -> Apply Attempt -> Migration -> Audit`

但不要求 Human 每次都跳转 Changes 页面。

### 离开保护

存在 Draft 时离开 Schema / Collection 不得静默丢失；必须明确继续编辑或 Discard。

## 8.4 Policy

### 页面目的

回答：

> 对当前 Collection，Application Principal 在 list/view/create/update/delete 下能访问什么？

### 首屏结构

固定使用 operation context：

```text
Policy                                          Simulate
[List] [View] [Create] [Update] [Delete]
──────────────────────────────────────────────────────
Current rule for <operation>
Expression / Rule
Runtime semantics / rule status

                                             Edit Rule
```

五个 operation 已固定，不再同时展示一个独立 Rules List + 大型 Editor。

Rule Editor 只编辑 Frozen Policy 语义：

- Mode：Allow / Deny；
- Expression。

“当前没有 Rule”必须与“存在一个明确的 Deny Rule 或表达式为 false 的 Rule”区分；不存在 Rule 时使用 `Define Rule` 创建真实 `policy.update` proposal，不能把 absence 伪装成已有拒绝规则。

### 主操作

当前 operation 已存在 Rule -> `Edit Rule`。

不存在 Rule -> `Define Rule`。

Edit 后形成 local Draft，并出现：

```text
Discard                                  Review Changes
```

页面 Header 不使用 `Propose Change` 作为长期主按钮。

### Review Changes

展示 policy Diff、Frontend preview Risk 与 access impact；创建 ChangeSet 后必须切换为 Runtime canonical Risk / impact。

`expandsAccess` 不得由用户填写。Frontend 可以预览 Policy Diff 的 access impact，但 Runtime 创建 ChangeSet 后返回的 canonical impactFlags 才是权威值。

canonical `expandsAccess=true` 必须由受控 Human Admin `Confirm & Apply`。

### Simulation

`Simulate` 为 secondary diagnostic action，打开 Sheet。

默认带入：

- current operation；
- current / draft expression。

用户补充：

- Application Principal；
- operation-specific Record / Before / After context。

`operation=list` 时必须提供 `context.record`；Simulation 语义同时受当前已发布的 view Policy 约束，不能把 draft list expression 当成唯一授权判断。

`Run Simulation` 后结果留在 Sheet。

Simulation 不修改 Draft、不产生 ChangeSet。

Policy Apply success 后停留在当前 operation，展示新 Applied Rule，并使旧 simulation result 失效。


## 8.5 Auth

仅 Auth Collection 显示。

### 页面目的

回答：

> 这个 Auth Collection 如何认证业务用户？当前 Application Auth Sessions 是什么状态？

使用两个 local view：

`Configuration | Sessions`

### Configuration

首屏只展示 Frozen AuthConfiguration：

- registrationEnabled；
- loginMethods：email_password / username_password；
- primaryIdentifier；
- sessionTtl；
- passwordPolicy。

主操作：`Edit Configuration`。

Edit -> local Draft -> Review Changes -> ChangeSet -> Apply / Confirm & Apply。

- principalId；

```text
Auth Configuration
!= Auth User Records
!= Application Auth Sessions

```

业务用户仍通过 `Records` 管理。


## 8.6 API

### 页面目的

回答：

> 当前 Collection 暴露哪些真实 API？我如何理解并立即验证它？

### 首屏结构

采用 two-pane API Explorer：

```text
Endpoints                     Endpoint Detail / Runner
GET /posts                    Contract
POST /posts                   Params / Headers / Body
GET /posts/:id                Auth requirement
                              Run Request
                              Response
```

Endpoint list 必须保持当前 Collection context：

- Normal Collection：当前 Collection Data API；
- Auth Collection：Data API + 当前 Auth Collection 对应的 Auth API；

### Authentication boundary

API Runner 走 Application Data Plane，不得自动转发 Admin Control Plane Session/API Key。

Runner 必须显式使用：

- Anonymous；或
- 对应 Application Auth 的 credential/context。

Runner 使用的 Application credential 仅作为当前调试会话输入，不自动写入 Project Secret、localStorage 或 Control Plane Credential。

- Open Global API；
- View Request Logs（Spec 0009 Runtime 已实现时）；
- Copy curl；
- Copy path；
- Export OpenAPI；
- Realtime connect/test（Runtime 已真实支持时）。

Spec 0009 Runtime 已实现后，Runner 必须展示 canonical requestId，并提供 `View Request Log`，跳转 Global API / Requests，而不是在 Collection 下再建立 Logs Tab。

Runner 必须明确标记“发送的是真实 Application Request”。对于 DELETE 等明显 destructive request，发送前使用确认 Dialog；不得因为它位于 API Explorer 就弱化真实副作用。

禁止静态 demo response 伪装真实执行。


# 9. Changes

## 页面目的

回答：

> 哪些 Proposal 需要治理？它们属于哪个 Collection 或 System？它们会改变什么？风险是什么？每次 Apply 实际发生了什么？

Changes 是 **全局 Canonical Governance + Execution History Workspace**。

它不拆成每个 Collection 一套 Changes 页面；所有 ChangeSet 使用同一个治理入口，但必须有明确 Scope。

## Scope model

V0.1 Changes 固定支持：

```text
All
System
Collection
  └─ <collectionId>
```

每个 ChangeSet 在 UI 中必须投影成：

- `Collection · <name>`；或
- `System`。

Scope 是展示 / 筛选 / 分组语义，不创造第二套 ChangeSet domain model。

对于能够从 operation target / stable collection identity 确定 Collection 的 ChangeSet，归入对应 Collection Scope。

Runtime Config 等非 Collection ChangeSet 归入 `System`。

如果一个未来 ChangeSet 真的跨多个 Collection，本 Spec 不把它伪装成单 Collection；显示 `Multiple Collections` 并在 detail 中列明真实 targets。

## Collection deep link

Collection Workspace 不增加 `Changes` 二级 Tab。

Records / Schema / Policy / Auth 等上下文中的：

`View Changes`

必须进入同一个全局 Changes 页面，并自动带入当前 Collection Scope，例如：

```text
/admin/changes?scope=collection&collectionId=<id>
```

System Settings 的 ChangeSet 可以 deep link：

```text
/admin/changes?scope=system
```

因此：

> **Changes 是一个页面，Collection 是最重要的上下文过滤维度之一。**

## 禁止 Generic New ChangeSet

Changes 页面不提供通用 `New ChangeSet` 作为主操作。

Proposal 应来自真实业务上下文：

- Collection / Schema（Fields / Relations / Indexes）；
- Policy；
- Auth Config；
- System Settings；
- MCP / CLI / Agent。

Changes 不重新复制这些编辑器。

## 首屏结构

默认进入 `Needs Review`：

```text
Changes
[Needs Review <n>] [Applying] [History]

Scope: [All] [System] [Collection ▼]      Search / Risk Filter
────────────────────────────────────────────────────────────
ChangeSet List / Groups       Selected ChangeSet
                              Scope
                              Source / Proposer / Intent
                              Risk + Impact
                              Structured Diff
                              Preconditions
                              ----------------
                              Apply / Review & Confirm
```

### List / grouping

默认 `All` 时，可以按 Scope 分组：

```text
posts
  Add field slug
  Add unique index

users
  Update view policy

System
  Change publicUrl
```

但 grouping 不得把真正的 ChangeSet 状态隐藏掉。

Ready / High Risk / Failed Attempts / Applied 数量使用 Tabs / Filters / Counts，不把 Failed 伪装成 ChangeSet status，也不使用 dashboard metric-card row。

## ChangeSet Detail

必须展示：

- Scope；
- intent；
- source / proposer；
- base model/config hash；
- Structured Diff；
- **Runtime-canonical Risk**；
- impact flags；
- Preconditions；
- confirmation requirement；
- source-context deep link（仅来源上下文可解析时）。

Collection Scope 的 detail 提供：

`Open Collection`

System Scope 的 detail 提供：

`Open System Settings`

但 Changes 自身仍保留治理和执行历史的唯一事实视图。

## Action hierarchy

Ready + SAFE：

- primary `Apply`；
- secondary `Open source context`；
- Cancel 在 secondary/destructive action。

High-risk / expandsAccess：

- primary `Review & Confirm`；
- confirmation 展示具体 impact；
- Confirmation 只能来自受控交互式 Admin；
- Agent / Service 不能自我确认；
- Confirm 后执行 Apply。

Applying：

- 禁止重复 submit；
- 展示 current execution state。

Applied：

- detail 保持可见；
- ChangeSet 状态展示 `Applied`；
- 对应 ApplyAttempt 展示 `Succeeded`；
- resulting Migration / durable model result；
- 返回对应 Collection 或 System Settings 的入口。

Failed Apply Attempt：

- failure inline 展示在 action area；
- ChangeSet 回到 `Ready`；
- `Retry` 成为主操作；
- previous failed attempt 保留；
- Retry 必须重新校验当前 Risk / Preconditions / Confirmation，不能复用已经失效的安全判断。

若返回 `CHANGESET_STALE`，不得继续盲目 Retry；必须说明 baseModelHash/baseConfigHash 已变化，并引导回 source context 重新生成 Proposal。

## History

Apply Attempts 与 resulting Migration 归属于 selected ChangeSet 的 detail/history。

不得在页面下方再维护一个与 ChangeSet 脱节的第二套 Migration History 面板。

Changes 是所有 ChangeSet 的统一事实入口，但不是 Human 建模动作的机械中转页。

# 10. Hooks

## 页面目的

回答：

> 当前 Instance 已注册哪些 V0.1 Lifecycle Hook？它们当前是否健康？

### V0.1 能力边界

一级 IA 名称继续保持 `Hooks`，但 V0.1 页面只展示真实 Lifecycle Hook Runtime。

V0.1 Lifecycle Hook 是 **Trusted Project Code**。Admin V2 不提供 Hook Code Authoring、Register Hook、Event Hook、Cron、Webhook 或 Delivery 管理 UI。

当前 Change Engine 明确把 `hook.*` operation 视为 deferred；因此 Admin 不得通过 Generic ChangeSet 伪造 Hook Definition mutation。

### 首屏

```text
Hooks
Lifecycle Hooks
────────────────────────────────────────────────
Name        Trigger              Status    Runtime
validate    record.beforeCreate  Enabled   TypeScript
...
```

页面没有 V0.1 全局 Create/Register 主按钮。

### 核心内容

每个 Hook 核心展示 Frozen LifecycleHook 可以真实提供的事实：

- Hook Name；
- Kind = Lifecycle；
- Trigger；
- Enabled / Disabled / Faulted；
- runtime；
- description（存在时）；
- generationId / reloadStatus / timeoutMs（存在时）。

`GET /hooks` 不保证 lastRun / lastResult / failure history，因此不得在 Registry 卡片中伪造这些字段。

若用户具备 `audit:read` 且 Activity 有真实 Hook Event，可以提供 `View recent activity` deep link；该信息属于 derived operational projection，不改变 Hook Registry DTO。

Hook Code / Definition 的编辑发生在 Project Source / coding workflow，不在 Admin 中复制第二套编辑器。

若未来某个 Hook status/config mutation 被正式加入 Frozen operable operation，再通过新的 Spec 明确其 Admin 写路径；V0.1 不提前假设。

### Runtime execution

Hook failure 不改变 Project Hook Definition。

完整跨时间 execution timeline 归 Activity；Hooks 页面只保留 current registry / health。

可 deep link：

- Activity：运行事件与错误；
- Audit：已有可追溯 Control Plane 管理事实（适用时）。

### 禁止

- 不提供 `Register Hook` 占位按钮；
- 不通过 ChangeSet 提交当前 Runtime 明确拒绝的 `hook.*` operation；
- 不展示 V0.1.x Event/Cron/Webhook/Delivery placeholder；
- 不复制 Activity timeline。

# 11. Access

## 页面目的

回答：

> 谁能够管理 Backend？这个 Principal 现在能做什么？关键管理行为是否可追溯？

页面标题固定为 `Access`。

页面内部 local view 只保留：

`Access | Audit`

不再使用 Principals / Credentials / Sessions / Capabilities 四个平级资源 Tab。

Capability 独立 gate：

- Access -> `access:manage`；
- Audit -> `audit:read`。

缺少其中一个 capability 时，只让对应 local view进入 Permission State，另一个有权限的 view 仍可正常使用。

## 11.1 Access

### 首屏结构

采用 Principal-centric master/detail：

```text
Access                                      + Create Principal
Search / Type
─────────────────────────────────────────────────────────
Principals                 Principal Detail
Admin Jane                 Jane
Agent Codex                Agent · Active
Service CI                 Capabilities
                           Credentials
                           Sessions
```

不展示 Principal / Credential / Capability / Audit metric-card row。

### 主操作

`Create Principal`

Create form 必须按 Frozen PrincipalCreateRequest 分支：

- Admin：Name + Email + Password + Description + **explicit Capability set**；
- Agent / Service：Name + Type + Description；创建后再在 Principal Detail 分配 Capability。

不得因为 Principal type 自动授予 scope；Bootstrap 首个 Admin 是唯一初始全 scope 例外。

Create success：

```text
Create Principal
-> durable Principal created
-> auto-select new Principal
-> Principal Detail opens
```

Agent / Service 创建后，在 Detail 中明确推荐下一步 `Create API Key`，但不自动创建 Credential。

### Principal Detail

顶部展示 Identity / Type / Status。

按顺序展示：

1. Capabilities；
2. Credentials；
3. Sessions（适用时）。

#### Capabilities

主操作：`Edit Access`。

新增会扩大 Control Plane authority 的 Capability 必须显式确认。

#### Principal status

Principal Detail 提供 `Suspend / Reactivate` secondary action，对应真实 Principal status mutation。

Suspend 必须明确影响并确认；成功后留在当前 Principal Detail 展示 durable status。

#### Credentials

Agent / Service 可：

- Create API Key；
- Rotate；
- Revoke。

Rotate / Revoke 都会影响机器访问，执行前必须使用明确确认；Rotate 成功后旧 key 不再作为可继续使用的 credential。

Credential metadata 常驻可见，plaintext 不可 read-back。

Create / Rotate 后进入 blocking one-time reveal Dialog：

```text
API key created
This value cannot be retrieved again.

<secret>                               Copy

                                         Done
```

`Copy` 是 reveal state 的主要操作；Done 后 plaintext 从普通 UI 永久消失。

#### Sessions

仅对适用 Principal 展示 Control Plane Session：

- Active / Revoked / Expired；
- created / lastUsed / expiry；
- Revoke。

Revoke 前确认，成功后保持当前 Principal Detail 并显示 durable Revoked 状态。

如果撤销的是当前登录 Admin 自己的 Control Plane Session，则完成撤销后立即清理 memory access credential 并返回 Login，而不是继续显示已失效的已登录 UI。

不得与 Application Auth Session 混用。

## 11.2 Audit

Audit 独立拥有：

- filters；
- durable Audit Facts table；
- selected Fact detail。

Deep link 到 Audit Fact 时必须直接选中 / 高亮，不要求用户重新搜索。

Principal deep link 返回对应 Principal Detail。

Audit 是 durable Control Plane trace，不复制 Activity timeline。


# 12. System Settings

## 页面目的

回答：

> 当前 Modelry Instance / Runtime 的真实受管配置是什么？敏感配置在哪里管理？

Sidebar 使用简短名称 `Settings`，页面标题固定为 `System Settings`。

固定：

`Runtime | Secrets | Storage`

## 12.1 Runtime

默认 read view，需要 `runtime:read`。

V0.1 Admin 可编辑的 Config ChangeSet 只包含当前真实 operable 字段：

- instanceName；
- environment；
- publicUrl。

`storagePath` 与 `storageDriver` 不属于 V0.1 online-editable Runtime Config；Local File Runtime 不支持在线移动 storage root。

具备 `config:write` + `changeset:propose` 时显示主操作：`Edit Configuration`；Apply 仍独立要求 `changeset:apply`。

Edit -> local Draft -> Review Changes。

Review 在 POST 前展示 Config Preview；创建 ChangeSet 后必须以 Runtime canonical Risk / impact / Preconditions 重新渲染。

根据规则：

- SAFE + authorized -> Apply；
- requires confirmation -> Confirm & Apply；
- secondary -> Save as ChangeSet / Open in Changes。

Apply success 后保持 Settings context，显示 durable new config。

## 12.2 Secrets

首屏使用 Secret metadata list/table。

主操作：`Add Secret`。

允许：

- create / replace；
- delete。

Delete 是直接 Secret Runtime mutation，执行前必须确认；成功后 metadata list 立即反映 Secret 不再存在。

这些是 Secret Runtime operation，不包装成 Config ChangeSet。

禁止：

- plaintext read-back；
- 在普通 detail/table 中显示现存 secret value。

Add/Replace 提交成功后必须清空本次 plaintext input；后续页面只重新读取 Secret metadata。

## 12.3 Storage

该子视图是 Runtime projection，只读展示当前 V0.1 真实 Local Storage 配置 / status。

`storageDriver=Local` 与 `storagePath` 不提供 Edit/Save；需要 `runtime:read`。

未实现的 S3 等 V0.1.x provider 不展示 future-provider card、disabled tab 或 fake setting。


# 13. Activity

## 页面目的

回答：

> 现在有什么运行问题需要处理？最近发生了什么？

Activity 是 **Operational Inbox + Cross-module Timeline**，读取需要 `audit:read`。

### 首屏

固定：

`Needs Attention | All Activity`

默认进入 `Needs Attention`。

Needs Attention 优先展示：

- Failed；
- Warning；
- Drift；
- Recovery Required；
- retryable operational failure。

成功事件不淹没异常。

### Event interaction

选择 Event 可以显示 compact explanation，但不创建重复的 Domain Detail。

每条事件必须提供 `Investigate` / deep link 到真实 Owner：

- Migration / Apply -> Changes；
- Hook -> Hooks；
- Record -> Records；
- Credential / Principal / Access -> Audit；
- Config -> System Settings。

All Activity 只负责跨模块近期 timeline。

### 禁止

- 不把 Activity 当永久 Domain Event Store；
- 不复制完整 ChangeSet、Hook、Record、Audit detail；
- 不提前展示未实现的 V0.1.x Delivery / Webhook 类型。

# 14. 页面状态规范

所有主要页面必须原生设计以下状态，而不是最后补：

- Loading；
- Empty；
- Partial Data；
- Permission Denied；
- Not Found；
- Validation Error；
- Action Failed；
- Runtime Unavailable；
- Recovery Required。

## 14.1 Partial Data

部分 API 失败时：

- 不把未知数据展示为 0；
- 正常可用区域继续可用；
- 明确指出哪些信息不可用；
- 提供 retry。

## 14.2 Permission

Capability Denied 时必须：

- 说明缺少何种能力；
- 不显示用户根本无法完成的危险操作；
- 不通过前端隐藏代替后端授权；
- 复合页面只降级无权限子视图，不因一个 API 403 让整页不可用；
- 不从 `Admin / Agent / Service` 类型推断权限，所有 Control Plane 操作以 capability 为准。

Model Change 的典型 UI gate：

- inspect -> `model:read`；
- edit/propose -> 对应 write capability + `changeset:propose`；
- apply/retry -> `changeset:apply`；
- high-risk confirmation -> 受控交互式 Admin + required capability。

## 14.3 UI Capability Matrix

Frontend 不得发明角色权限，至少按以下 Frozen capability gate：

| Surface / Action | Capability |
| --- | --- |
| Collections / Schema (Fields / Relations / Indexes) / Auth Config inspect | `model:read` |
| Collection / Schema model operations (Field / Relation / Index) / Auth Config propose | corresponding `model:write` + `changeset:propose` |
| Policy inspect / Simulation | `model:read` |
| Policy change propose | `policy:write` + `changeset:propose` |
| ChangeSet inspect / attempts / migration inspect | `model:read` |
| Apply / Retry ChangeSet | `changeset:apply` |
| Record inspect | `data:inspect` |
| Record create / update / delete | `data:mutate` |
| Bulk Preview / Execute（仅 operable 时） | `data:inspect` / `data:mutate` |
| Lifecycle Hook registry | `runtime:read` |
| Access / Principal / Credential / Control Plane Session | `access:manage` |
| Audit / Activity | `audit:read` |
| Runtime Settings read | `runtime:read` |
| Runtime Config propose | `config:write` + `changeset:propose` |
| Secrets | `secrets:manage` |

有效 Admin Session / API Key 只证明身份，不隐式授予上述 capability。

# 15. 统一操作语义

## 15.1 Model Change

以下属于当前 V0.1 Backend Model / Managed Config Change：

- Collection；
- Schema / Field；
- Relation；
- Index；
- Policy；
- Auth Configuration；
- operable Managed Runtime Config。

Lifecycle Hook Code / Definition 是 Trusted Project Code；当前 `hook.*` Change Operation deferred，不属于 V0.1 Admin 可写 ChangeSet。

领域语义统一：

```text
Inspect
-> Edit Draft
-> Validate
-> Diff
-> Risk
-> Propose ChangeSet
-> Review
-> Apply Attempt
-> Durable Change / Migration
-> Audit
```

但 **领域生命周期不要求一一映射为页面跳转**。

Human 在当前业务上下文中可以完成：

```text
Edit Draft
-> Frontend Preview
-> create ChangeSet
-> receive Runtime-canonical Diff/Risk/Impact/Preconditions
-> Apply / Confirm & Apply when authorized
-> see durable result
```

Frontend Preview 只用于即时反馈，不能成为 Risk authority。

同时提供 `Save as ChangeSet` / `Open in Changes`。

Changes 页面负责集中治理、跨来源 Proposal、历史、失败重试和高风险审查，而不是所有 Model Change 的机械中转页。

## 15.2 Runtime/Data Operation

以下不自动进入 ChangeSet：

- Record CRUD；
- Session revoke；
- Credential create/rotate/revoke；
- Secret replace/delete；
- API Runner；
- Policy Simulation。

这些操作仍必须产生正确 Durable State 与 Audit（适用时）。

## 16.1 角色

负责复杂交互 primitive：

- overlay；

- menu/dialog/popover/select behavior。

决定最终：

- color；
- typography；
- radius；

- shadow；

### Tailwind

允许：

- component 内部 styling；
- business page layout；
- responsive layout。

禁止业务页面自行发明新的视觉组件。

## 16.2 Visual Language — Neutral Developer Console

Admin V2 的正式视觉方向固定为：

> **Neutral Developer Console**

整体采用接近 shadcn black / white / zinc 的黑白灰视觉语言。

原则：

- 大面积 background / surface / border / text 使用 neutral / zinc；
- Primary Action 默认使用黑 / 白高对比，而不是品牌色铺满页面；
- 页面层级主要依靠 typography、spacing、border、density 建立；
- Card 只用于真正独立的信息单元，不把每个 section 都包成 Card；
- Table / Form / Diff / Code / Metadata 保持 developer-tool 的紧凑信息密度；
- Hash、ID、API route、field name、migration id 等 technical identifier 优先使用 monospace；
- Light / Dark 共享同一语义 Token，不建立两套视觉语言。

### Color semantics

颜色主要用于表达业务语义，而不是装饰：

- Success / Applied / SAFE -> success；
- Warning / Pending / DATA_REWRITE -> warning；
- Destructive / Failed / Drift / Recovery Required -> destructive；
- Info -> info；
- Agent / AI identity 如确有必要可使用少量 violet，但不得作为全局品牌背景色。

普通主按钮、Tab、标题、Sidebar、Card 不因为品牌识别而默认使用 Indigo / Violet。

### Shape / elevation

默认保持克制：

- Button / Input radius：约 6px；
- Table / Card radius：约 8px；
- Dialog / Sheet radius：约 10px；
- Badge / segmented / toggle 可使用 pill；
- 优先 border / whitespace，减少大面积 shadow；
- 禁止页面自行使用超大圆角、glassmorphism、gradient 或装饰性彩色 surface。

### Typography

Typography 是主要层级工具：

- Page Title：20–24px；
- Section Title：14–16px；
- Body：13–14px；
- Table：12–13px；
- Metadata：11–12px；
- technical identifier / code：monospace。

实际 token 可以在实现阶段微调，但层级关系必须保持。

## 16.3 V4 Visual Reference Override

Spec 0003 中 V4 Prototype 继续作为：

- 一级页面集合与职责（用户可见导航命名由本 Spec 收敛为 `Control / Hooks / Access / System / Settings`）；
- Collection context（但 Collection 二级 IA 中独立 Relations / Indexes 由本 Spec 覆盖）；
- 页面分组；
- 核心 interaction ownership；

的参考。

但其 Indigo/Violet 主视觉、旧 Card 密度、旧组件外观不再是 Admin V2 的视觉验收基线。

视觉冲突时：

`Spec 0008 Neutral Developer Console > Spec 0003 V4 visual reference`

因此实现 Agent 不得混用两套视觉体系。

# 25. User Stories

1. As an Admin, I want to see whether my Backend is healthy, so that I know whether I can safely continue work.
2. As an Admin, I want clear next actions when Runtime state is abnormal, so that I know where to resolve problems.
3. As a Developer, I want to browse all Collections, so that I can choose the data model I need to work on.
4. As a Developer, I want to create Normal or Auth Collections, so that I can model application data and identity domains.
5. As a Developer, I want Collection context to remain stable across Records, Schema and API, so that I do not lose orientation.
6. As a Developer, I want to browse and manage Records, so that I can inspect real application data.
7. As a Developer, I want to edit Schema as a draft before applying it, so that model changes are reviewable.
8. As a Developer, I want to understand structured Diff and Risk before applying a model change, so that I can avoid unintended data impact.
9. As a Developer, I want to define Relations with clear target and cardinality, so that references between Collections are explicit.
10. As a Developer, I want to create Indexes with precondition feedback, so that invalid unique constraints do not silently fail.
11. As a Developer, I want Policy rules separated by operation, so that authorization behavior is understandable.
12. As a Developer, I want to simulate Policy without changing it, so that I can verify access behavior safely.
13. As a Developer, I want Auth Collection configuration separated from users and sessions, so that authentication concepts are not conflated.
14. As a Developer, I want Collection API documentation and a real request runner together, so that I can understand and verify the API quickly.
15. As a Developer, I want a Global API workspace across all Collections, so that I can inspect the complete Application API surface without opening Collections one by one.
16. As a Developer, I want API request logs linked to endpoints and runner requests, so that I can diagnose authentication, policy and runtime failures.
17. As an Admin, I want all proposed Backend changes in one Changes workspace and filter/group them by Collection or System scope, so that governance is centralized without losing context.
18. As an Admin, I want failed Apply Attempts to retain the original ChangeSet, so that I can fix the problem and retry.
19. As an Admin, I want to understand high-risk change impact before confirmation, so that dangerous changes are deliberate.
20. As an Admin, I want to inspect Lifecycle Hook registry and health, so that hook problems are diagnosable.
21. As an Admin, I want to manage each Principal together with its Capabilities, Credentials and Sessions, so that I can understand who can do what without reconstructing access across multiple resource pages.
22. As an Admin, I want API key plaintext shown only once, so that credentials cannot be casually re-read.
23. As an Admin, I want an Audit trail of critical operations, so that I can trace who changed what.
24. As an Admin, I want System Settings Runtime Config edits to become System-scoped ChangeSets, so that operational configuration changes are governed.
25. As an Admin, I want Secret metadata without secret read-back, so that sensitive values stay protected.
26. As an Operator, I want Activity to prioritize failures and warnings before the full timeline, so that I can act on operational problems quickly.
27. As a User with partial permissions, I want unavailable actions clearly disabled or absent with meaningful explanation, so that I understand my actual capabilities.
28. As a Developer using deep links, I want tabs, filters and selected objects to survive refresh where appropriate, so that URLs remain useful.
29. As a Keyboard user, I want consistent focus and dialog behavior, so that Admin is fully operable without a mouse.
30. As a maintainer or coding agent, I want business pages composed from a constrained Design System, so that new work does not create a new visual language.
31. As a Developer viewing Records, I want to see when a pending model change may affect current data, so that I can understand risk before continuing data work.
32. As a Developer editing a safe model change, I want to review and apply it in context when authorized, so that governance does not require unnecessary navigation.
33. As an Admin reviewing access, I want one Principal detail to show its capabilities, credentials and sessions, so that access questions are answered in one place.

# 29. 最终架构结论

Modelry Admin V2 的最终原则：

```text
Business Task
    ↓
Page / Feature
    ↓
Modelry Domain Components
    ↓
Modelry Common Components
    ↓
Modelry UI Components
    ↓
shadcn / Base UI
    ↓
Tailwind + Design Tokens
```

同时：

```text
Server State -> TanStack Query
Table State  -> TanStack Table
Form State   -> React Hook Form + Zod
URL State    -> React Router
Local State  -> React
```

**业务页面决定“用户要完成什么”，Design System 决定“它应该长什么样和如何交互”。**

这是 Admin V2 重建的核心边界。
