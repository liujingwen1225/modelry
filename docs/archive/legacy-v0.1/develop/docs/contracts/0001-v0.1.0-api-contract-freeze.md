## 1. Purpose

Modelry 的 Admin 前端已经通过 Repository、Service、Domain Type、Mock Closure 和页面 Journey 固定了 V0.1.0 的机器语义。本 Contract 将这些语义与 Accepted Scope、Business Baseline、Technical Spec、ADR 和 Amendment 汇合成 Backend 可以直接实现和验证的公共边界。

冻结完成后，Backend 实现不得根据页面临时形状重新猜测：

- 哪些操作属于 Data Plane，哪些属于 Control Plane；
- Record Policy 与 Capability Scope 如何分离；
- File Upload Session 如何绑定 Record；
- ChangeSet 与 ApplyAttempt 如何分离；
- 失败、冲突、漂移和未就绪如何编码；
- 哪些 Frontend Repository 方法是后端资源，哪些只是派生读取或 presentation helper。

## 3. API Namespace and Authentication

### 3.1 Namespace

| 面 | Base path | 服务对象 | 授权原语 |
| --- | --- | --- | --- |
| Data Plane | `/api/v1` | Application、SDK、业务 Auth Principal | Record Policy |
| Control Plane | `/_modelry/api/v1` | Admin、Agent、CLI、MCP、Admin Repository | Capability Scope；V0.1.0 operable credential 为 Admin Session 或 Agent/Service API Key |
| Embedded Admin UI | `/admin` | 人类 Admin 操作界面 | Admin Control Plane Session；access credential 在 memory，refresh material 为 HttpOnly Cookie |

Data Plane 与 Control Plane 不共用默认权限含义。Control Plane 对业务 Record 的访问是 `Administrative Data Access`，不把 Admin/Agent 映射为 `auth.id`，默认不运行业务 Record Policy，但每次访问必须使用 `data:inspect` 或 `data:mutate` 并形成 Audit Fact。

Admin 是 Control Plane Principal vocabulary 的一部分。Admin bootstrap/login/session transport 属于 V0.1.0 Control Plane contract；它与 Application Auth Collection transport 使用不同 namespace、DTO、security scheme 和 session metadata。

### 3.2 Credential boundary

- `Principal` 表示谁在操作；`Credential` 表示如何证明身份；两者永远不是同一对象。
- Application Data Plane 使用 `Authorization: Bearer <opaque-access-token>`。
- Agent / Service 使用 Control Plane API Key；API Key 明文只在创建/rotate 响应显示一次。
- V0.1.0 Control Plane operable credentials 同时包括 Admin Session 与 Agent / Service API Key。
- Admin access credential 是短生命周期 opaque bearer；Admin refresh material 通过 `HttpOnly; SameSite=Lax; Path=/_modelry/api/v1/auth` cookie 传输，HTTPS 时设置 `Secure`，不进入 JSON response。
- Bootstrap Setup Token 只用于创建首个 Admin，成功后立即失效；它不是普通长期 Credential。
- `ControlApiSession` 只表示 Admin Control Plane access credential；`ControlPlaneSession` 表示其 server-side refresh session metadata。
- Application `AuthSession`、Admin `ControlPlaneSession`、Agent/Service `Credential` metadata 是三种不同 backend 语义，不能互相替代。
- Admin session 遵循 §15.5 的默认生命周期：access credential 15 分钟、refresh session 30 天；服务端持久化 token hash，不持久化 token plaintext。
- API Key、Session、Password、Secret plaintext 不从 Inspect/read response 返回；Credential resource 仍只返回 API Key metadata，Admin Session 通过 Admin Auth response/session routes 表达。
- `changeset:propose` 不等于 `changeset:apply`；`data:inspect` 不等于 `data:mutate`。

## 4. DTO Rules

### 4.1 Common rules

- 所有 stable identity 使用 `string` opaque ID；Backend 不要求客户端解释 ID 结构。
- 所有时间使用 RFC3339 `date-time`；持久化前统一为 UTC。
- JSON object key 的 canonicalization、model/config hash 和 Snapshot 使用同一规范化实现。
- 业务逻辑只依赖 `error.code`、`error.details` 和结构化 metadata，不解析 `message`。
- `message` 面向人类；`hint` 是可选操作提示；`requestId` 必须可追踪；`correlationId` 用于跨 Apply/Audit/Work 关联。
- Response 的 system-owned metadata（`id`、`createdAt`、`updatedAt`、`version`、`deletedAt`）不能通过普通 Record mutation payload 覆盖。

### 4.2 Frontend adapter boundary

Frontend Domain Type 是页面和 Service 的模型，不等同于 HTTP JSON 的逐字段复制。Backend implementation 必须使用 OpenAPI/contract DTO，再由真实 Repository adapter 做转换。

已冻结的适配规则：

- Backend list envelope 使用 `totalItems`；Frontend `RecordListResult.total` 是 adapter projection。
- Backend Auth login method 使用 `email_password` / `username_password`；Frontend 的 `Email + Password` / `Username + Password` 是显示/Domain label。
- Backend 使用 `If-Match: "<version>"`；Frontend `expectedVersion` 只是 **optional** adapter 输入，仅在 Collection `optimisticLock=true` 时由调用方提供，绝不作为第二个 request body 字段。
- Backend File Field 新绑定只接受 `{ "uploadSessionId": "..." }`（或数组）；`FileValue` 是响应表示，不是上传入口。
- `BulkMutationExecuteRequest` 必须携带服务端可验证的 `previewId` 和 confirmation context；Frontend 当前 Repository selection input 不代表服务端已经确认。
- `ApiRepository.runEndpoint` 的 method/path/status 来自当前生成的 OpenAPI，不产生第二套 API registry。

## 5. Data Plane Contract

### 5.1 Records

Canonical Application routes：

```text
GET    /api/v1/collections/{collection}/records
POST   /api/v1/collections/{collection}/records
GET    /api/v1/collections/{collection}/records/{recordId}
PATCH  /api/v1/collections/{collection}/records/{recordId}
DELETE /api/v1/collections/{collection}/records/{recordId}
```

规则：

- `{collection}` 是 lowercase API name；Control Plane `{collectionId}` 使用 stable opaque ID。
- 只支持 `PATCH`，不提供 `PUT` replacement semantics。
- List query 使用 `filter`、`sort`、`page`、`perPage`、`expand`；`page` 默认 `1`，`perPage` 默认 `30`、最大 `100`。
- `sort` 是逗号分隔字段名，`-field` 表示降序；`filter` 使用统一 Expression Engine。
- `expand` 最大深度为 `2`；每个目标 Record 重新执行目标 Collection `view` Policy。
- List 结果必须同时满足 `list` 和 `view` Policy；List Policy 必须尽可能下推到查询，不能先读全量再在内存中过滤。
- Application 无权 view 的单条 Record 使用非泄漏 `404 NOT_FOUND`；Control Plane diagnostic surface 可以返回结构化 `POLICY_DENIED`。
- Record 输出至少包含 `id`、`collectionId`、`values`、`createdAt`、`updatedAt`；启用 optimistic lock 时包含从 `1` 开始的 `version`。
- `createdAt` / `updatedAt` 是 UTC `date-time`。
- Collection 启用 `softDelete` 时，Data Plane DELETE 改变 `deletedAt`，普通 list/view/expand 默认看不到；Data Plane 没有 `includeDeleted` escape hatch。
- 默认值在 create candidate 上应用；用户显式提供的值不被默认值覆盖。
- Validation failure 使用统一 Structured Error，不依赖 UI 的字段文案。

### 5.2 Record Policy

Record Policy 必须分别冻结并求值：

```text
list / view / create / update / delete
```

语义：

- `list`：对持久化 Record 求值，并和调用者 Filter 合并执行；返回集合还必须满足 `view`。
- `view`：对持久化 Record 求值；未授权单条请求不泄漏存在性。
- `create`：基础 validation -> `beforeCreate` Hook -> final validation -> 对 final `after` candidate 求值 -> transaction。
- `update`：对 `before` 求值 -> 构建 candidate -> `beforeUpdate` Hook -> final validation -> 对 final `after` 求值；before/after 都必须通过。
- `delete`：对删除前 `before` 求值，然后执行 `beforeDelete` Hook；soft delete 仍是 delete operation。
- Relation write 必须验证 target 存在且当前 Application Principal 可 view；不存在和不可 view 使用同一类非泄漏 validation failure。
- Relation Expand 不得因为父 Record 可读而绕过目标 Record Policy；single denied target 为 `null`，many denied entries 被省略。
- Realtime subscription filter 只会进一步缩小已授权事件集合，不能替代 Record Policy。

### 5.3 Realtime

`GET /api/v1/realtime` 是 best-effort SSE projection，不是可靠消息队列。

- 支持 collection、Expression Engine filter 和 `Last-Event-ID` 的同进程 bounded replay。
- create/update/delete 的可见性变化以同一个 Mutation Domain Event 的 before/after projection 判断。
- visible -> invisible 只发 Record ID 级 `record.removed`/`record.deleted`，不能泄露 Record body。
- 默认 replay ring 为 bounded；Runtime restart 后可以发 `modelry.reset`，客户端重新读取当前状态。
- 不承诺跨 Runtime restart 的持久事件重放。

### 5.4 Public OpenAPI projection

`GET /api/v1/openapi.json` 是匿名可读的 Public Data Plane projection，不是完整 Control Plane route registry：

- Runtime response 只保留 Frozen Contract 中以 `/api/v1/` 开头的 Application paths，并排除 `/_modelry/api/v1/` Control Plane paths；这是 path-prefix projection，不是按 operation `security` 临时筛选。
- `contracts/openapi/v0.1.0.json` 仍然保留完整的 Data Plane 与 Control Plane operation inventory，是唯一完整机器 Contract；公共 response 的裁剪不删除或修改其中任一 Control Plane operation。
- Application API 的 operation、DTO、错误、认证和 Policy 语义保持完整；Admin consumers 继续使用 `/_modelry/api/v1/...` 的既有 Control Plane transport，不因公共 projection 改变。
- 该可见性决策由 `dataGetOpenApiDocument` 的 `x-modelry-public-projection` metadata 表达，并由 Contract test 校验；Runtime 对齐属于独立实现 Issue。

## 6. Optimistic Lock

只保留一套传输语义：HTTP `If-Match`。

- Collection `optimisticLock=true` 时，PATCH 和 DELETE 必须携带 `If-Match: "<positive-integer>"`。
- 版本不一致统一返回 `409 OPTIMISTIC_LOCK_CONFLICT`，`details` 至少可以包含 expected/actual version。
- 成功更新只递增一次 `version`。
- `optimisticLock=false` 时不强制 If-Match；Frontend Repository 的 `expectedVersion` 不能被解释成第二个 request body 字段。
- Repository `expectedVersion` 是 optional adapter input：`optimisticLock=false` 时可以省略，adapter 不发送 `If-Match`，也不得伪造一个 version。
- PATCH conflict 和 DELETE conflict 使用同一错误码和 HTTP status。

## 7. Upload Session / Local File

V0.1.0 只冻结 Local Storage 的临时 Upload Session：

```text
pending -> uploaded -> committed
       \-> expired
```

Application routes：

```text
POST /api/v1/upload-sessions
PUT  /api/v1/upload-sessions/{sessionId}/content
GET  /api/v1/upload-sessions/{sessionId}
GET  /api/v1/files/{fileId}
```

Admin Repository 使用同一语义的 Control Plane `/.../data/upload-sessions` projection。

- Request 包含 collection、field、original filename、MIME、declared size 和可选 fileCount。
- Runtime 在创建 Session 时验证目标 File Field、大小、MIME 和绑定 owner。
- binary handoff 使用 `application/octet-stream`；V0.1.0 不冻结 multipart production runtime、presigned URL 或 S3。
- 上传完成后校验实际大小，计算 SHA-256，状态变为 `uploaded`。
- Record create/update 的 File Field 新绑定只能提交 `{ uploadSessionId }`；Record transaction 成功时才将 Session 变为 `committed`。
- Record transaction 失败时 Session 保持 `uploaded`，不能被假装已绑定。
- 默认过期时间为 `1 hour`；过期、无效、owner/collection/field 不匹配返回 `UPLOAD_SESSION_INVALID` 或明确的 `VALIDATION_ERROR`，不得泄漏其他 Session 信息。
- 未绑定临时文件不可通过正式 file download route 读取。
- File download 必须重新检查 owning Record 的 view Policy；URL 本身不是授权凭证。
- 不存在 standalone `commitUploadSession` HTTP endpoint；Frontend helper 只保留为 presentation-only seam。
- orphan file deletion 是 commit 后 durable work，不能在请求路径中假设物理文件删除与 DB mutation 同步完成。

## 8. Backend Model / Modeling Contract

Backend Model 是产品语义 Source of Truth，持久化真相层级固定为：

```text
Project Migration History -> Runtime Backend Model -> Generated Schema Snapshot
```

V0.1.0 Model contract 覆盖：

- Normal/Auth Collection；
- Field：`text`、`integer`、`number`、`decimal`、`boolean`、`date`、`datetime`、`json`、`relation`、`file`、`select`、`email`、`url`；
- Relation cardinality `one | many`；`onDelete` 为 `restrict | setNull`；
- `relation(one) + required=true` 只允许 `restrict`；`relation(many) + required=true` 删除后不得变空；
- File 单值/多值、大小和 MIME pattern；
- Declarative literal Default 与 Validation；
- Collection options：`softDelete`、`optimisticLock`；
- Policy 的五种 operation；
- Auth Collection configuration；
- Index 与 Unique；多字段通过 `fields[]` 表达，不存在独立 Composite index type。

Collection、Field、Relation、Index、Policy 等定义都保留 stable opaque ID。Rename 必须保持 ID，不能以 drop + add 伪装。

`modelHash` 只对 canonical semantic model payload 计算，排除自身、modelRevision、generated timestamp、Runtime status 和 Migration Ledger 执行时间。Snapshot、stale detection、Migration before/after hash 必须复用同一实现。

## 9. ChangeSet / Diff / Risk / ApplyAttempt

### 9.1 ChangeSet

ChangeSet 是提案，不是一次执行。状态冻结为：

```text
Draft -> Ready -> Applying -> Applied
Draft / Ready -> Cancelled
```

V0.1.0 可以在 Propose 后直接返回 `Ready`，但不得改变领域含义。ApplyAttempt 失败后 ChangeSet 回到 `Ready`；ChangeSet 不存在 terminal `Failed`。

ChangeSet 至少包含：stable ID、kind、source Principal、reason/intent、baseModelHash 或 baseConfigHash、typed operations、structured before/after Diff、单一 Risk、ImpactFlags、Preconditions、timestamps 和 attempt references。

### 9.2 ApplyAttempt

每次 Apply 都创建独立事实：

```text
Pending -> Running -> Succeeded
                   -> Failed
```

ApplyAttempt 至少记录 Attempt ID、ChangeSet ID、发起 Principal、Risk/impact snapshot、confirmation context、Preconditions summary、时间、Migration/ApplyPlan 关联、result 和 structured error。

Retry 创建新的 ApplyAttempt；同一 ChangeSet 已形成 reserved ApplyPlan 后必须复用相同 Migration ID、文件名和 exact Artifact bytes，不得因为重试产生第二份等价 Migration。

### 9.3 Risk / confirmation

Risk 只有一个可排序主级别：

```text
SAFE < DATA_REWRITE < DESTRUCTIVE < IRREVERSIBLE
```

一个 ChangeSet/Migration 取所有 operations 的最高风险，并附带：

- `requiresBackfill`
- `dropsData`
- `changesCardinality`
- `expandsAccess`
- `requiresCheckpoint`

规则：

- SAFE 且 `expandsAccess=false`：具备所需 capability 的 Agent 可以自动 Apply。
- DATA_REWRITE、DESTRUCTIVE、IRREVERSIBLE：必须 Human Confirmation。
- `expandsAccess=true`：即使数据 Risk 为 SAFE 也必须 Human Confirmation。
- Human Confirmation 必须来自受控交互式 Admin，Apply Agent 不能自我充当确认人。
- DESTRUCTIVE/IRREVERSIBLE 在 DB mutation 前必须成功创建 checkpoint。
- caller 提交的 Risk 不是权威值；Runtime 必须重算 Risk 和 Preconditions，并取 `max(artifactDeclaredRisk, recomputedRisk)`。
- `CHANGESET_STALE` 统一表示 baseModelHash/baseConfigHash 不匹配。

## 10. Bulk Administrative Mutation

Bulk Record mutation 不进入 ChangeSet，固定为：

```text
Target Selection -> Impact Preview -> Human Confirmation -> Execute -> Result Summary -> Audit
```

- Preview 使用 `data:inspect`，生成 opaque `previewId`、目标快照、requested/affected/blocked counts、warnings 和 impact level。
- Execute 使用 `data:mutate`，必须关联 previewId 和服务端可验证的 confirmation context。
- Partial failure 是合法结果；返回 succeeded/skipped/failed counts、per-record failures 和 `auditFactId`。
- Bulk update/delete 的数据路径仍是 Administrative Data Access，不伪装成 Application Auth Principal，不创建伪 ChangeSet。

## 11. Control Plane Access

### 11.1 Principal / Credential

V0.1.0 Control Plane Principal：`Admin`、`Agent`、`Service`。业务 Auth Principal 只服务 Application Data Access。

V0.1.0 operable Control Plane Credential 同时包括：

- `Admin Session` —— Admin 的短生命周期 opaque access credential + server-side refresh session；
- `API Key` —— Agent / Service 的机器 Credential，明文只在创建/rotate 响应显示一次。

`Principal != Credential` 仍然成立：Admin、Agent、Service 是 Principal；Admin Session 与 API Key 是 Credential。API Key 不携带隐式超级管理员语义，实际权限始终来自 Capability Scope。

### 11.2 Admin Control Plane Auth

以下 transport 是 V0.1.0 operable contract，并与 `/api/v1/auth/...` 的 Application Auth Collection routes 完全分离：

| Method | Path | Request / Response | Authentication | Capability |
| --- | --- | --- | --- | --- |
| `POST` | `/_modelry/api/v1/bootstrap/admin` | `BootstrapAdminRequest` -> `BootstrapAdminResponse` | one-time Bootstrap Setup Token | bootstrap exception；成功创建的首个 Admin 获得全部 V0.1.0 scopes |
| `POST` | `/_modelry/api/v1/auth/login` | `AdminLoginRequest` -> `AdminLoginResponse` | Admin email + password | authentication transport；不授予额外 scope |
| `POST` | `/_modelry/api/v1/auth/refresh` | no body -> `AdminRefreshResponse` | `AdminRefreshCookie` | authentication transport；refresh rotates server-side session |
| `POST` | `/_modelry/api/v1/auth/logout` | no body -> `204 No Content` | `ControlApiSession` | 当前 session self-revocation；不改变 scope |
| `GET` | `/_modelry/api/v1/auth/current` | no body -> `AdminCurrentResponse` | `ControlApiSession` | 当前身份/session self-inspection；不改变 scope |
| `GET` | `/_modelry/api/v1/auth/sessions` | no body -> `ControlPlaneSession[]` | `ControlApiSession` | `access:manage` |
| `DELETE` | `/_modelry/api/v1/auth/sessions/{sessionId}` | `SessionIdPath` -> `ControlPlaneSession` | `ControlApiSession` | `access:manage` |

OpenAPI operation 的 `x-error-codes` 对每个 Admin Auth route 的 HTTP status 与稳定 `error.code` 做机器可读绑定；通用 response envelope 仍遵循第 17 节。

Bootstrap transport 语义：

- Runtime 在不存在 Admin 时生成并打印当前 one-time Setup Token；请求必须携带 `bootstrapToken`、`email`、`password`；
- token 只允许创建第一个 Admin，成功后立即失效；在 bootstrap 未完成时进程重启，旧 token 不再有效，Runtime 可以生成新的 token；
- 缺失/格式非法 JSON 字段返回 `VALIDATION_ERROR`（422）；格式合法但值错误的 token 返回 `BOOTSTRAP_TOKEN_INVALID`（401）；已过 Runtime 有效期或已被重启替换的 token 返回 `BOOTSTRAP_TOKEN_EXPIRED`（401）；已有 Admin 时返回 `ADMIN_ALREADY_BOOTSTRAPPED`（409）；这些失败都不得创建 Admin；
- Bootstrap token 不进入 Credential list、不能用于普通 Control Plane operation，也不能成为长期 API Key 或 Session。

Admin login/session 语义：

- login 使用 Control Plane Admin email + password；invalid credential 返回 `ADMIN_CREDENTIAL_INVALID`（401），Suspended Admin 返回 `ADMIN_SUSPENDED`（403）；Admin 不属于业务 Auth Collection；
- 成功响应只返回短生命周期 opaque access credential、`accessTokenExpiresAt`、Admin Principal 和 Session metadata；refresh material 只通过 `Set-Cookie` 返回；
- `ControlApiSession` 是 Authorization bearer access credential。它只回答“Who are you?”；普通 Control Plane operation 仍必须继续通过 Capability Scope；
- `AdminRefreshCookie` 是 HttpOnly `modelry_admin_refresh` cookie，必须使用 `SameSite=Lax` 与 `Path=/_modelry/api/v1/auth`，HTTPS 时设置 `Secure`，不得暴露给 JavaScript。Refresh 轮换 cookie 和 access credential；refresh 缺失、过期、已撤销或无效返回 `ADMIN_SESSION_INVALID`（401）；
- logout 撤销当前 server-side session 并清除 refresh cookie；清除响应必须使用与创建/轮换相同的 `Path=/_modelry/api/v1/auth` scope，并发送空值与 `Max-Age=0`（或合法的过去 `Expires`）；revoke 对指定 session 的服务端撤销立即生效；Session list/revoke 需要 `access:manage`；
- Session metadata 只能包含 opaque `sessionId`、`principalId`、时间、状态和受限 device metadata，不包含 access/refresh token plaintext。

Capability layering：

Bootstrap、login、refresh、logout、current 是建立、轮换、撤销或检查认证 transport 的生命周期操作，因此不要求一个已有的业务 capability；它们不授予对 Control Plane resource operation 的权限。普通 Control Plane resource operation 以及跨 Session 的 list/revoke 仍必须先通过 capability evaluation；有效 Admin Session 本身不能绕过 scope。

```text
Admin Session / API Key
        ↓
Principal
        ↓
Capability Scope
        ↓
Control Plane Operation
        ↓
Audit Fact
```

Bootstrap 创建的首个 Admin 是唯一的初始授权例外：按 Accepted Spec 获得全部 V0.1.0 Capability Scopes；后续 Admin 通过 `POST /_modelry/api/v1/principals` 的 `AdminPrincipalCreateRequest` branch 创建，要求 `access:manage` 与显式 scope set；后续 Admin、Agent、Service 仍不能因为 Principal type 而隐式获得全部 scope。

### 11.3 Capability vocabulary

冻结且机器可读的 Capability：

```text
model:read
model:write
config:write
data:inspect
data:mutate
changeset:propose
changeset:apply
policy:write
secrets:manage
access:manage
audit:read
runtime:read
```

任何 scope 都不隐式授予其他 scope。Policy Simulation 是独立诊断能力，不等同 Administrative Data Access。

## 12. Secret Contract

Secret routes 只支持 metadata list、set/replace、delete：

- Response 只包含 `name`、`present`、`updatedAt`；
- set/replace 请求可以包含 plaintext，但响应绝不回显已保存值；
- Secret plaintext 不进入 Project Source、Audit、Activity、普通 Record 或 Hook Inspect；
- Secret API 要求 `secrets:manage`，写入/替换/删除形成 durable Audit Fact；
- V0.1.0 不提供 plaintext retrieval endpoint。

## 13. Audit Contract

Audit Fact 与 Activity 严格分开。

Audit Fact 的字段集合包括：

- `id`
- Principal actor 的 `principalId`、`principalType`、可选 `capability`，或 non-principal source actor 的 `source`
- `objectType`
- `objectId`
- `action`
- `result`
- `occurredAt`
- request-driven event 的 `requestId`
- 需要跨操作关联时的 `correlationId`
- 适用时的 `relatedRefs`

其中 actor 必须且只能是以下两种形状之一：

1. **Principal actor**：`principalId` 与 `principalType` 必须成对存在；`principalType` 只能是 `Admin`、`Agent` 或 `Service`。`capability` 只在 Capability-gated Control Plane operation 中出现并使用冻结的 Capability vocabulary；非 Capability authentication transition 不要求该字段。
2. **Non-principal source actor**：`source` 必须来自 `Bootstrap`、`Unauthenticated`、`Runtime` 或 `Filesystem`；该形状不能同时包含 `principalId`、`principalType` 或 `capability`。

OpenAPI 以 `oneOf` 表达上述互斥关系，因此只存在一个 Principal 字段、只存在 `principalType`、同时存在两类 actor 或完全没有 actor 都是非法 AuditFact。`source` 不承载 Application Auth Principal，也不得通过 `unknown`、email、request ID 或 fake Principal 补齐身份。

认证安全事件使用以下语义：

- Bootstrap Token failure：`source=Bootstrap`、`action=control.bootstrap.failed`、`result=Failed`；不伪造 Principal 或 Capability。
- Bootstrap success：`source=Bootstrap`、`action=control.bootstrap.succeeded`、`result=Succeeded`；不包含 Principal 或 Capability；新 Admin 仅作为 `objectType=Principal`、`objectId=<new-admin-id>` 的 target。
- Login failure（invalid 或 unknown Admin）：`source=Unauthenticated`、`action=control.login.failed`、`result=Failed`；即使查到匹配 Admin，也不能把未证明身份的 Admin 作为 actor。
- Login success：使用真实 `principalId`、`principalType=Admin`、`action=control.login.succeeded`、`result=Succeeded`；不要求伪造 Capability。
- Invalid/expired refresh authentication：`source=Unauthenticated`、`action=control.refresh.failed`、`result=Failed`；logout authentication failure 使用同一 source 语义。

Audit details 不得保存 password、password hash、access token、refresh token 或 API key，也不得泄漏可被外部利用的身份枚举信息。

Audit query 支持 principal、object、action、result、requestId、time range、related object 和 pagination。要求审计正确性的 mutation 必须与 Audit Fact 原子持久化，或由同一 durable fact 可恢复生成。

Activity 是 Runtime/Migration/Hook/Delivery 等跨模块 projection，可以深链 Audit Fact，但不替代 Audit storage，也不因为有 `Delivery` projection 就冻结 Delivery API。

## 15. Auth Collection V0.1.0

冻结的 Auth Collection 能力：

- Email + Password（机器值 `email_password`）；
- Username + Password（机器值 `username_password`）；
- `registrationEnabled`；
- `primaryIdentifier`；
- session TTL；
- password policy；
- revocable Access/Refresh Session。

Registration pipeline 必须执行 target Auth Collection 的 create Policy 和 Lifecycle Hook，不得成为旁路；Registration 成功不隐式创建 Session，客户端随后 Login。

V0.1.0 Application Auth route inventory 与 OpenAPI 完全一致：

| Method | Path | Request / Response | Authentication |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/{collection}/register` | `AuthRegisterRequest` -> `AuthRegistrationResponse` | anonymous |
| `POST` | `/api/v1/auth/{collection}/login` | `AuthLoginRequest` -> `AuthSessionResponse` | anonymous |
| `POST` | `/api/v1/auth/refresh` | `AuthRefreshRequest` -> `AuthSessionResponse` | refresh credential |
| `POST` | `/api/v1/auth/logout` | no body -> `204 No Content` | `BearerAuth` |
| `GET` | `/api/v1/auth/sessions` | no body -> `AuthSession[]` | `BearerAuth` |
| `DELETE` | `/api/v1/auth/sessions/{sessionId}` | `SessionIdPath` -> metadata-only `AuthSession` | `BearerAuth` |
| `POST` | `/api/v1/auth/logout-all` | no body -> `204 No Content` | `BearerAuth` |

The Application Auth login and refresh responses remain token-bearing `AuthSessionResponse`. Both Application Auth session revoke responses use `AuthSessionMetadataResponse`, whose payload is metadata-only `AuthSession`; revoke does not issue or return access/refresh token plaintext.

V0.1.0 不冻结并不实现 Email Verification、OTP、Password Reset、OAuth、SMTP provider 或 Anonymous Auth。

## 16. Lifecycle Hook Contract

V0.1.0 Backend-facing Hook contract 只包含 `Lifecycle`：

- `record.beforeCreate`
- `record.beforeUpdate`
- `record.beforeDelete`

允许读取 configuration/status/reload state/generation/timeout/lifecycle trigger metadata。Hook 是 Trusted Project Code，但必须具备 throw/rejection/timeout/runaway fault boundary。

冻结的 reload 语义：

- invocation 开始时绑定 immutable active generation；
- reload 成功只影响后续 invocation；
- 新版本加载/语法/import 失败时保留 last-known-good generation；
- reload success/failure、Faulted/Fallback、timeout 均可观察并进入必要 Audit；
- Hook timeout 默认 `2s`，可配置范围 `50ms..10s`。

Hook 失败与超时的 HTTP transport 复用 §17 的冻结映射：`HOOK_FAILED -> 422`、`HOOK_TIMEOUT -> 504`。因为 Hook 运行在唯一 Record mutation 路径上，以下 operation 都可能返回这两个 response，Frozen OpenAPI 必须声明：

| Method | Path | Hook error response |
| --- | --- | --- |
| `POST` | `/api/v1/collections/{collection}/records` | `422`、`504` |
| `PATCH` | `/api/v1/collections/{collection}/records/{recordId}` | `422`、`504` |
| `DELETE` | `/api/v1/collections/{collection}/records/{recordId}` | `422`、`504` |
| `POST` | `/api/v1/auth/{collection}/register` | `422`、`504` |
| `POST` | `/_modelry/api/v1/data/collections/{collectionId}/records` | `422`、`504` |
| `PATCH` | `/_modelry/api/v1/data/collections/{collectionId}/records/{recordId}` | `422`、`504` |
| `DELETE` | `/_modelry/api/v1/data/collections/{collectionId}/records/{recordId}` | `422`、`504` |

Application Auth register 不是 Hook 旁路：它复用同一 Application Record Service，因此必须执行 target Auth Collection 的 create Policy 与 Lifecycle Hook（与 §15 一致）。Control Plane Administrative Record mutation 复用同一 Record Service，同样适用。

Event Hook、Cron、Webhook、Delivery、Delivery Retry/History 不进入 V0.1.0 operable paths。

`frontend/admin/src/repositories/contracts.ts` 是 Frozen Repository Contract 的 source。每个 Frozen Repository method 的签名（参数名、参数类型、参数可选性、参数顺序、返回类型）同时冻结在 mapping JSON 的 `signature` 字段中。`bun run contract:check` 使用 TypeScript AST 解析该 source 并与冻结签名逐一比对，因此 required↔optional、参数增删 / 顺序 / 改名 / 类型、返回类型、method rename 以及 method / Repository 增删都会导致 gate 失败。修改任一 Repository method 签名必须先走 Contract Gap 流程。

## 19. Explicit Deferred Scope

以下能力在 V0.1.0 只允许出现在产品文档、类型边界或 read-only presentation fixture 中，不得出现在 OpenAPI operable paths、Repository backend method 或可调用 Control Plane API：

- OAuth；
- SMTP / Email Provider；
- S3 Compatible Storage / presigned upload；
- Email Verification；
- OTP；
- Password Reset；
- Event Hook；
- Cron；
- Webhook；
- Event Delivery、Delivery Retry、Delivery History API；
- 完整 Custom API runtime；
- Batch、完整 Backup/Restore UX。

`DeferredHookDelivery` 只能作为前端 read-only fixture，用来表达 V0.1.x 预览，不是 V0.1.0 Backend contract。

## 20. Backend Implementation Constraints

本 Contract 合并后，Backend implementation 必须：

1. 使用本 OpenAPI/DTO 作为 transport contract，不从页面或 Mock 猜 endpoint；
2. 保持 Data Plane / Control Plane namespace 和授权边界；
3. 保持 Backend Model -> ChangeSet -> Migration -> Snapshot 的 source-of-truth chain；
4. 不将 `failed` 添加到 ChangeSet status；失败只存在 ApplyAttempt；
5. 不把 bulk mutation 重新放入 ChangeSet；
6. 不把 Admin/Agent principal 注入 `auth.id`；
7. 不把 final FileValue 当作上传绑定入口；
8. 不返回 Secret、Password、API Key、Session plaintext；
9. 不将 Lifecycle Hook 以外的 Event/Cron/Webhook/Delivery 实现偷偷纳入 V0.1.0；
10. 不为 V0.1.0 引入仅为假设 PostgreSQL 准备的通用 DatabaseAdapter。

发现 Contract Gap 时必须停止局部顺手修改：

```text
发现 Gap -> 创建独立 Contract Issue -> 更新 Contract -> Contract Review -> 合并 develop -> Backend 继续
```

## 21. Freeze Change Policy

一旦 Issue #39 通过 PR `feature/39-api-contract-freeze -> develop` 合并：

- Backend implementation 不得自行修改本 Contract、OpenAPI、DTO、错误码、路径、状态或授权边界；
- 任何必要变更必须创建独立 Contract Issue，说明兼容影响和迁移策略；
- 更新后必须重新运行 contract check、Frontend Closure 和相关 CI；
- 未经 Contract Review 的 Backend workaround 不构成新契约；
- 机器契约的破坏性变化不能以“后端内部实现”名义绕过评审。
