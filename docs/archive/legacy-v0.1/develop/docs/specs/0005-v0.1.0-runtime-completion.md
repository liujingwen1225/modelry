## 3. 用户故事

1. As an application developer, I want an Auth Collection to provide registration and password login, so that an application can authenticate real users without inventing a separate user service.
2. As an authenticated application user, I want sessions to expire, rotate and be revoked, so that a leaked or obsolete credential does not remain valid indefinitely.
3. As an authenticated application user, I want to inspect and revoke my own sessions or sign out everywhere, so that I can control active access to my account.
4. As a project administrator, I want to inspect and revoke Application Auth sessions through the Control Plane, so that compromised application sessions can be invalidated without impersonating the application user.
5. As an application developer, I want invalid, expired and revoked credentials to fail closed without leaking whether an identity exists, so that authentication does not weaken the existing Record Policy boundary.
6. As an application developer, I want File Fields to upload and read local files through record authorization, so that file access follows the same application data rules as the owning record.
7. As a project developer, I want deterministic lifecycle hooks to validate or enrich mutations before commit, so that project rules can extend the backend without creating a second write path.
8. As an application client, I want realtime updates only for committed records I am authorized to see, so that live updates do not become an authorization side channel.
9. As a project administrator, I want to create, replace, inspect metadata for and delete Secrets without re-reading plaintext values, so that runtime credentials can be managed safely.
10. As a project developer, I want API Usage and OpenAPI to describe and exercise the real Runtime, so that documentation and interactive calls cannot drift from production behavior.
11. As a coding agent, I want a small set of intent-oriented MCP tools for inspect, propose, apply, administrative data and Secret operations, so that I can safely operate Modelry through existing domain boundaries.
12. As a CLI user, I want the V0.1.0 CLI Core commands to invoke the same real services as Admin and MCP, so that terminal workflows do not create a parallel implementation.
13. As an operator, I want `doctor` and drift diagnostics to report real project/runtime state, so that I can detect and understand configuration or schema divergence before release.
14. As a release maintainer, I want a Blog reference application to exercise Auth, File, Policy, Hook, Realtime, Secret, OpenAPI, MCP, CLI, ChangeSet, Migration, Drift and Audit, so that V0.1.0 has one reproducible end-to-end acceptance path.
15. As a maintainer, I want any mismatch between implementation needs and the Frozen Contract to be raised as an explicit Contract Gap, so that implementation convenience cannot silently change V0.1.0 machine semantics.

## 4. 范围

### 4.1 Application Auth Runtime

实现冻结合约中的 Application Auth 路由，HTTP method 以 Frozen Contract 为准：

- `/api/v1/auth/{collection}/register`
- `/api/v1/auth/{collection}/login`
- `/api/v1/auth/refresh`
- `/api/v1/auth/logout`
- `/api/v1/auth/sessions`
- `/api/v1/auth/sessions/{sessionId}`
- `/api/v1/auth/logout-all`

同时实现 Frozen Control Plane Contract 中的 Application Session 管理能力：

- `/_modelry/api/v1/auth/collections/{collectionId}/sessions`
- `/_modelry/api/v1/auth/collections/{collectionId}/sessions/{sessionId}`

要求：

- 支持 Email + Password 和 Username + Password 两种 V0.1.0 登录方式。
- 使用 Auth Collection 的真实 Record 作为业务身份边界。
- Password 是独立 Credential，不是普通 Collection Field；`password` / `passwordHash` 不得作为普通 Backend Model Field 或业务 Record value 持久化、查询或返回。
- Password Credential 必须以安全散列或等价不可逆形式保存；算法与迁移信息属于认证子系统内部状态。
- 建立短生命周期访问凭证 + 服务端可撤销 Refresh Session 的生命周期，覆盖过期、撤销、rotation 与 replay rejection。
- Application 自助 Session API 只能查看/撤销当前业务身份拥有的 Session；Control Plane 管理 Session 使用既有 Capability/Audit 边界，不伪装成业务 `auth.id`。
- 在 HTTP → Application Service 边界注入真实 `ApplicationAuthContext`，继续复用现有 Record Policy、Relation Policy、Filter、View/Create/Update/Delete authorization evaluation。
- Anonymous 请求继续以 `auth=null` 进入业务授权；invalid Authorization、过期 Session、已撤销 Session 必须 fail closed。
- 认证失败、记录不存在、错误 credential 与错误 collection 保持 non-leaking error 语义。
- 不得使用 `X-Modelry-API-Key`、测试专用 header 或 Control Plane credential 代替 Application Auth。
- 通过统一 Domain Event/Audit seam 表达当前范围可产生的认证事件，至少包括 `auth.registered`、`auth.login.succeeded`、`auth.login.failed`、`auth.session.revoked`；不得由 Realtime、Hook 或 Audit 直接监听认证内部存储表重新解释事实。
- 与认证状态变更关联的事件/审计事实必须保持事务一致性；登录失败事件不得泄漏 Identifier 是否存在。

Control Plane Auth 已经是独立能力，本规格不重新实现 Admin/Control Plane 登录。

### 4.2 Secret Runtime

实现 Frozen Control Plane Contract 中的 Secret 管理能力：

- `GET /_modelry/api/v1/secrets`
- `PUT /_modelry/api/v1/secrets/{name}`
- `DELETE /_modelry/api/v1/secrets/{name}`

要求：

- Secret 是一级 Control Plane 资源，不是 Application Record Field。
- 读取接口只返回名称、存在性及 Frozen Contract 允许的 metadata，不返回已保存 Secret 明文。
- create/replace/delete 必须经过现有 Control Plane Principal/Capability 边界，并按 Frozen Contract 使用 `secrets:manage` 等既有能力语义。
- Secret mutation 必须进入 Audit；日志、错误、inspect、MCP 返回不得泄漏 Secret value。
- Lifecycle Hook 与 MCP 使用同一 Secret Service/Repository seam，不允许各自实现第二套 Secret backend。
- V0.1.0 不引入远程 Secret Manager、Vault 集成或 Secret versioning 产品能力。

### 4.3 Local File 与 Upload Session Runtime

实现冻结合约中的 Local File 路由：

- `/api/v1/upload-sessions`
- `/api/v1/upload-sessions/{sessionId}/content`
- `/api/v1/upload-sessions/{sessionId}`
- `/api/v1/files/{fileId}`

要求：

- 支持 File Field 的单文件和多文件值。
- 上传过程具备 session、大小限制、MIME 限制和失败清理语义。
- 文件引用必须绑定到真实 Record/Field，并遵守 Application Auth 与 Record Policy。
- 下载或读取文件不得绕过记录级授权。
- V0.1.0 只实现 Local Storage；S3 放入 V0.1.x。
- 不新增 Frozen Contract 未声明的 upload/complete 路由；具体 HTTP method 以现有合约为准。

### 4.4 Lifecycle Hook Runtime

要求：

- 接入现有 Record mutation seam，不创建第二套写入路径。
- V0.1.0 只支持本地、事务内、确定性的 TypeScript Project Hook，用于验证和字段补全。
- pre-commit hook 可以拒绝不满足业务规则的 mutation。
- Hook 如需 Secret，只能通过受控 Secret Runtime seam 获取，不能直接读取内部 Secret 存储。
- 不在 V0.1.0 引入外部 side-effect executor、可靠投递或不可回滚的外部副作用。
- 任何未来的 commit 后外部副作用属于 V0.1.x Event Hook/Webhook 范围，不得由本阶段顺带实现。
- 覆盖 hook fault、超时、重复执行、恢复和运行状态记录的 V0.1.0 baseline。
- Hook 失败不能伪造 mutation 成功，也不能破坏已提交数据的一致性。

Event Hook、Webhook、Cron 和外部 delivery guarantee 不属于 V0.1.0。

### 4.5 SSE Realtime Runtime

实现 `/api/v1/realtime`：

- 只发布已经提交的统一 Domain Event。
- 对订阅者执行 Application Auth 和 Policy 过滤。
- 提供连接建立、heartbeat、断开、重连和基本 backpressure 语义。
- 不承诺 V0.1.0 具备完整 replay queue 或 event store。
- 不允许未授权订阅通过事件 payload 推断其他记录或认证身份存在性。
- Realtime 只消费统一事件事实，不通过查询内部业务表或 Auth 表自行重建事件。

### 4.6 OpenAPI 与 API Usage Runtime

实现 `/api/v1/openapi.json` 和 API Usage 的生产接线：

- Frozen OpenAPI 3.1 contract 是唯一对外 operation 语义来源。
- API Usage/API Runner 必须调用真实 HTTP Runtime，不得继续使用独立 mock 语义。
- 不复制 Record Query、Policy、Auth、Secret 或 Upload 的业务规则。
- 如果实现发现 Frozen Contract 与已确认需求不一致，必须单独创建 Contract Gap Issue，不能在本规格中静默修改合约。

Policy Simulation 的 `operation=list` 语义属于上述 Frozen Contract 的机器语义：`allowed` 表示给定 `principal` 与 `context.record` 的 Record 是否会出现在真实 Application List 结果中，因此必须同时满足有效 `list` Policy 与当前已发布 `view` Policy。`context.record` 虽因 operation-specific context 形状在 JSON Schema 中保持 optional，但 list simulation 缺少它时必须返回 `422 VALIDATION_ERROR`，并使用 `POLICY_CONTEXT_REQUIRED` 说明缺少的 `context.record`。`draftExpression` 只覆盖本次 list Policy 求值；view Policy、Relation visibility 和求值错误语义继续复用真实 Application Runtime，不得折叠为伪造的 `allowed=false`。

### 4.7 MCP Runtime

实现 V0.1.0 的受限 MCP 能力，覆盖 V0.1 Scope 已确认的意图域：

- inspect
- propose
- apply
- administrative data access
- record data access
- secret 相关受控操作

要求：

- 复用 Control Plane、ChangeSet、Risk、Apply、Migration、Audit、Administrative Data Access 和现有权限边界。
- Secret MCP tools 必须复用 4.2 的真实 Secret Runtime，不创建独立存储或明文读取路径。
- MCP 不得提供任意 SQL、shell 或任意文件系统访问。
- apply 必须继续经过现有 ChangeSet/Risk/Confirmation 语义。
- Secret 值不得在不必要的 inspect、日志或错误中泄露。
- MCP Record tools 属于 Administrative Data Access，继续使用 `data:inspect` / `data:mutate` 与 Audit，不伪装为 Application Auth Principal。

## 5. 实现决策与不可变架构约束

1. Backend Model 是 schema、Auth Collection、File Field 和 Policy 的 source of truth。
2. Application Data Plane 只有一条生产路径；Admin/Control Plane 可绕过 Application Policy，但不得复制 Record Store。
3. Control Plane Principal/Credential 与 Application Auth Record/Credential/Session 必须分离。
4. Password Credential 与 Auth Collection Record 分离；Password 不是普通 Field。
5. Application Auth Runtime 负责产生真实 auth context，Application Service 继续负责授权决策。
6. Relation Policy、Filter、View、Create、Update、Delete 必须继续在同一 authorization evaluation 语义内执行。
7. Secret 只有一套 Control Plane source/runtime seam；Hook、MCP、Admin 只能复用。
8. Domain Event 是 Auth、Record mutation、Realtime、Hook、Audit 的共享事实骨干；子系统不得分别监听内部表生成竞争事实。
9. 所有 mutation 的提交、domain event 和 required audit 语义必须保持可追踪；V0.1.0 Hook 仅允许事务内本地确定性行为。
10. CLI、Admin、HTTP、MCP 都是已有领域能力的入口，不得各自复制业务规则。
11. Frozen Contract 不因实现方便而修改；任何缺口单独进入 Contract Gap Review。
12. V0.x 继续保持 SQLite Only、One Instance One Project、Single Binary First。

## 6. 测试决策

测试优先使用能够验证真实系统行为的最高层公开 seam，避免为本规格新增只服务于测试的内部 mock seam。

- Application Auth：真实 HTTP route integration + SQLite persistence + 真实 Auth Collection Record/Policy；覆盖 register/login/refresh/logout/logout-all/session list/revoke、Control Plane revoke、expiration、rotation replay、non-leaking failures。
- Credential security：验证业务 Record、API response、日志、error、Audit/MCP inspect 中均不出现 password/passwordHash/refresh secret/session secret 明文。
- Secret：真实 Control Plane routes + capability + persistence + audit；证明 set 后只能读取 metadata，不能通过 list/get/log/error/MCP 取回明文。
- File：真实 upload session、Local Storage、record binding 与授权读取，不以直接 File Service 单测替代端到端授权验证。
- Lifecycle Hook：通过真实 Record mutation seam 验证 accept/reject/enrich、timeout/fault/recovery 与 rollback；不建立第二个测试写入入口。
- Realtime：真实 SSE connection，验证 committed-only、Auth/Policy filtering、disconnect/reconnect、unauthorized non-leak。
- API Usage/OpenAPI：Browser/API Runner 必须打真实 Runtime route；Frozen Contract/canonical tests 继续作为机器语义 gate。
- MCP：使用真实 MCP transport/tool invocation 验证 inspect/propose/apply/data/secret，并证明 ChangeSet/Capability/Audit 边界没有被绕过。
- CLI：以真实 CLI process/standalone seam 验证 Core commands；`doctor`、`mcp` 不允许 fixture-only pass。
- Blog E2E：作为最终 release acceptance，串联本规格全部能力，不允许用互不相干的局部测试代替最终闭环。
- 每个实现 Issue 完成后运行其 targeted tests 与 repository-wide backend/frontend/canonical/contract/build/smoke gates；Frozen Contract diff 必须为零，除非存在单独批准的 Contract Gap Issue。
