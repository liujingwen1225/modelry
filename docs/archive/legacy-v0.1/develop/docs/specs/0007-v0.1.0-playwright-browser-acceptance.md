# Spec 0007 — Modelry Playwright Browser Acceptance & Business Closure Test Project

- **Status**: Accepted
- **Target**: V0.1.0 Release Readiness / Hardening
- **Primary test runtime**: Real standalone Modelry Runtime
- **Primary browser**: Chromium
- **Exploratory tool**: Playwright MCP
- **Regression framework**: @playwright/test
- **Authoring baseline**: develop@d1f8296fc91fff62bd885fb077077c04f2b4393f

## 1. 背景

Modelry 当前已经具有较完整的：

- Backend Unit / Integration Test
- Frontend Vitest / Testing Library Test
- Canonical Backend Model Test
- Contract Check
- Standalone Smoke
- Dev Smoke
- 自研 Chrome CDP Admin Browser Smoke
- Blog Reference E2E

这些测试能够证明大量内部逻辑、API 和部分浏览器路径正确，但它们不能充分回答：

> 一个真实用户打开 Modelry Admin 后，是否真的能顺畅、正确、完整地完成一项工作？

第一轮通过 Playwright MCP 的真实浏览器操作已经暴露出若干现有自动化未发现的问题。

这说明当前存在明显测试缺口：

~~~text
代码正确
≠
API 正确
≠
页面能打开
≠
用户真的能顺畅完成业务
~~~

因此需要建立独立的 Playwright Browser Acceptance Test Project。

它不是简单的 UI Smoke，而是 Modelry 的：

**UI + Interaction + Functional + Workflow + Business Closure + Browser Regression Gate**

---

## 2. 目标

建立一套基于 @playwright/test 的真实浏览器测试工程，并结合已经安装的 Playwright MCP，严格验证：

1. 页面 UI 是否正确。
2. 页面状态是否正确。
3. 用户操作是否有效。
4. 操作过程是否顺畅。
5. 前后端是否真正连通。
6. 数据是否真正持久化。
7. 页面之间的状态是否一致。
8. Backend Model 变更是否形成完整 ChangeSet / Apply / Migration 闭环。
9. Record / Relation / File / Auth / Policy / Secret / Hook 等核心能力是否可由用户真正使用。
10. 错误情况下产品是否给出正确反馈并能恢复。
11. Restart 后运行状态是否保持正确。
12. 一个真实应用能否从空项目一直运行到完整业务结果。

最终目标不是：

> Playwright Tests Pass

而是：

> **Modelry V0.1.0 的核心用户旅程能够由真实浏览器完整完成，并且所有关键结果都能够从系统另一侧再次验证。**

## 3. Playwright MCP 与 Playwright Test 的职责

### 3.1 Playwright MCP

Playwright MCP 用于：

- 产品探索；
- 人工验收；
- 新问题发现；
- UI 检查；
- 操作流畅性检查；
- Accessibility Tree 检查；
- 页面状态检查；
- Console Error 检查；
- Network Failure 检查；
- Bug 精确复现；
- 测试路径设计；
- Test Case 校准。

其性质为：

~~~text
Browser Explorer / Tester
~~~

它主要回答：

> “真实用户操作时哪里不对？”

### 3.2 @playwright/test

仓库内 Playwright Test Project 用于：

- 持久自动化；
- Regression；
- PR 验证；
- Release Gate；
- Screenshot Regression；
- Browser Trace；
- 可重复业务闭环验证。

其性质为：

~~~text
Executable Product Acceptance Specification
~~~

它回答：

> “这个已经发现并确认正确的行为，以后是否一直正确？”

### 3.3 两者关系

Playwright MCP 不替代正式测试代码。

固定闭环：

~~~text
Playwright MCP 探索
        ↓
发现真实缺陷
        ↓
Bug Issue
        ↓
Fix
        ↓
@playwright/test Regression Case
        ↓
进入后续 Release Gate
~~~

任何 MCP 发现并确认的 P0/P1 产品缺陷，在修复后必须增加回归测试；不得只修代码而不固化验证路径。

## 4. 核心测试原则

### 4.1 优先测试真实系统

Mandatory Test 不得使用：

- Mock Repository；
- Mock Runtime；
- Fixture UI；
- React Component Mock；
- fake backend；
- intercepted fake API response。

核心链路必须使用：

~~~text
真实 Modelry Runtime
+
真实 SQLite
+
真实 HTTP API
+
真实 Admin UI
+
真实浏览器
~~~

允许在非 Mandatory 辅助测试中使用 deterministic fixture 构造输入，但 fixture 不能替代被验证的生产路径。

### 4.2 从最高层公共接口验证

Playwright 测试应优先：

~~~text
Browser UI
     ↓
HTTP
     ↓
Runtime
     ↓
Domain Service
     ↓
SQLite
~~~

不能直接调用 React 内部状态或 Repository implementation。

除专门的数据完整性诊断测试外，不直接修改 SQLite。

### 4.3 测试结果必须可从第二观察点确认

例如，创建 Record 不能只检查：

~~~text
Toast = Created
~~~

必须继续检查：

~~~text
列表出现 Record
→ 打开详情数据正确
→ API 查询结果正确
→ 刷新页面仍存在
~~~

Apply ChangeSet 不能只检查：

~~~text
Apply 成功
~~~

还必须验证：

~~~text
ChangeSet Applied
→ Apply Attempt Succeeded
→ Backend Model 已变化
→ Collection UI 已变化
→ Migration History 出现记录
→ Restart 后仍存在
~~~

这称为：

**Cross-Surface Verification**

### 4.4 Durable State 优先于瞬时 UI

成功 Toast、按钮文案、页面跳转只是瞬时信号。

对于影响持久状态的操作，测试必须至少验证一个 Durable Result，例如：

- Reload 后仍存在；
- 另一页面重新读取后存在；
- HTTP API 重新查询后存在；
- Runtime Restart 后仍存在；
- Migration / Audit / Activity 中存在对应事实。

### 4.5 不以实现细节作为断言主语

测试应该描述用户或领域行为，例如：

- “创建 Collection 后进入 Records”
- “Apply 后 Migration History 出现”
- “撤销 Session 后访问被拒绝”

而不是：

- “某 React state 等于 true”
- “某 Repository method 被调用一次”
- “某内部表第 3 列变为 1”

## 7. Runtime Fixture

Playwright 必须能够启动真实 standalone Runtime。

每个 Worker 使用独立：

~~~text
Temporary Project Root
Temporary SQLite
Temporary File Storage
Dynamic HTTP Port
~~~

基本过程：

~~~text
Build standalone
    ↓
Create isolated project root
    ↓
Start modelry serve --port 0
    ↓
Parse MODELRY_READY
    ↓
Browser connects
    ↓
Tests
    ↓
Terminate Runtime
    ↓
Cleanup
~~~

需要支持：

~~~text
runtime.start()
runtime.stop()
runtime.restart()
~~~

以验证真正的持久化和 Restart 行为。

Runtime Fixture 必须：

- 不依赖开发机固定目录；
- 不依赖固定端口；
- Windows / POSIX 路径安全；
- 测试完成后回收子进程；
- 失败时保留必要 Runtime Log；
- 不继承会污染 loopback 请求的代理配置；
- 支持为失败测试保留 Project Root 的可选诊断模式。

## 8. Browser Health Gate

每个测试默认监听：

- pageerror；
- browser console error；
- failed request；
- unhandled promise rejection；
- HTTP 5xx。

除测试明确预期的错误外：

~~~text
Console Error = Test Failure
Page Error = Test Failure
Unexpected HTTP 5xx = Test Failure
Unhandled Error = Test Failure
~~~

对于预期错误，必须按 URL / error code / operation 做精确白名单，不允许全局忽略 console.error 或 5xx。

这一层用于发现：

- 页面“看似正常”但后台已经异常；
- React runtime error；
- 请求失败后 UI 吞错；
- Promise rejection；
- 接口 500 被 fallback 数据掩盖。

## 10. 测试优先级

### P0 — Release Blocker

无法完成核心业务闭环。

例如：

- 无法 Bootstrap；
- 无法 Login；
- 无法创建 Collection；
- 无法 Apply ChangeSet；
- 无法创建 Record；
- 数据 Restart 后丢失。

任何 P0 失败：

~~~text
Release Gate = FAIL
~~~

### P1 — Product Blocker

核心功能明显错误或安全语义错误。

例如：

- Relation 错误；
- Policy fail-open；
- File 绑定失败；
- Secret 泄漏；
- Session revoke 无效；
- ChangeSet 状态不一致。

P1：

~~~text
Release Gate = FAIL
~~~

### P2 — UX / Regression

例如：

- 页面错位；
- Modal 不完整；
- 操作无 loading；
- 错误反馈不明确；
- tab 状态不合理。

Release Readiness 阶段应修复确认的 P2；P2 是否阻断发布由 Release Review 根据影响范围决定。

## 11. UI 验证

不能只使用 screenshot diff。

### 11.1 Layout

检查：

- 无元素遮挡；
- 无文字截断；
- 无错误换行；
- 无不可预期横向滚动；
- Dialog 不超出 viewport；
- Dropdown 不被裁剪；
- Sticky / Header / Sidebar 正常；
- 表格操作列可见；
- 长文本不会覆盖相邻控件；
- Empty / Loading / Error 状态不会破坏布局。

推荐主视口：

~~~text
1440 × 900
1920 × 1080
~~~

### 11.2 Visual Regression

稳定页面使用 screenshot assertion。

优先覆盖：

- Login；
- Bootstrap；
- Overview；
- Collections；
- Collection Records；
- Schema；
- Changes；
- Access & Audit；
- Settings。

对动态 ID、日期、运行时间：

- 固定测试数据；
- mask；
- 局部截图。

不得通过大范围提高 pixel tolerance 掩盖问题。

### 11.3 UI 语义检查

每个关键页面除截图外还必须检查：

- 主标题；
- Active navigation；
- 关键 CTA；
- 当前状态 Badge；
- Empty / Error / Loading 文案；
- 表格列或主要卡片；
- Dialog title 与 action。

### 11.4 Layout Hard Invariants

对于已经明确属于产品规则的布局约束，必须使用 DOM / CSS / bounding box 断言固化为自动化回归，不能只依赖 screenshot 或 MCP 人工观察。

至少覆盖：

- 技术型长 ID / UUID / Hash / Token ID / Execution ID 在列表中不得自动换行；
- 单个长字段不得导致整行异常增高；
- 表格 Header 与 Body 列边界保持对齐；
- 操作列在主视口下保持可见；
- 页面根容器不得产生非预期横向 overflow；
- Dialog / Popover / Dropdown / Tooltip 不得被 viewport 或父容器裁切；
- 固定 Header / Sidebar 不得遮挡页面正文；
- 关键 CTA 不得与文本、Badge 或其他按钮重叠；
- Loading / Empty / Error 状态切换不得造成结构性布局破坏。

对这类规则，优先使用可解释的断言，例如：

~~~ts
await expect(idCell).toHaveCSS("white-space", "nowrap");

const box = await idCell.boundingBox();
expect(box).not.toBeNull();

const hasHorizontalOverflow = await page.evaluate(
  () => document.documentElement.scrollWidth > document.documentElement.clientWidth,
);
expect(hasHorizontalOverflow).toBe(false);
~~~

禁止为了通过视觉测试而简单扩大 screenshot threshold，或使用固定 sleep 等待布局稳定。

### 11.5 Long Technical Identifier Rule

Modelry 中以下值统一视为技术型长标识符：

- Record ID；
- UUID；
- ChangeSet ID；
- Apply / Attempt ID；
- Session ID；
- Credential ID；
- Hook / Event ID；
- Artifact ID；
- Hash；
- 其他具有类似长度与识别用途的内部标识。

列表 / 表格视图必须满足：

~~~text
单行显示
+
紧凑截断
+
完整值可访问
~~~

默认推荐展示形式：

~~~text
前 8 位 + … + 后 4 位
~~~

完整值必须至少可通过以下一种用户可见方式获取：

- Tooltip；
- 专用 Copy 按钮；
- 详情页完整展示。

如果整行本身可点击进入详情，不应让点击 ID 文本直接触发复制，避免交互冲突；优先使用独立 Copy Action。

必须验证：

- 长 ID 不换行；
- 长 ID 不把单条记录撑成多行高度；
- 截断显示不会改变真实值；
- Copy / Tooltip 获取的是完整原始值；
- 不同 viewport 下仍满足上述规则。

### 11.6 Information Density / Duplicate Content Review

以下问题通常不会造成 DOM 错误，但属于正式 UI 验收范围：

- 同一页面重复展示语义相同的 Activity / Audit / Runtime 信息；
- 主内容区域因列宽或 Card 布局产生明显无意义空白；
- 次要 Card 占用过大空间，挤压核心业务内容；
- 重要待处理事项在视觉层级上弱于普通状态信息；
- 同级 Card 的高度、对齐、间距出现明显失衡；
- 同一信息在多个区域以近似内容重复出现但没有明确不同语义；
- 页面首屏无法快速识别运行状态、待处理事项和主要工作对象。

这类问题不得用脆弱的“固定像素美学阈值”自动判定。

固定策略：

~~~text
已明确的结构规则
→ DOM / Layout Assertion

稳定页面变化
→ Screenshot Regression

信息层级 / 重复 / 空白 / 排版合理性
→ Playwright MCP Visual Review

确认后的问题
→ Bug
→ Fix
→ 尽可能转换成结构断言或 Golden Screenshot Regression
~~~

例如，“Overview 只允许存在一个最近活动主区块”一旦成为正式设计规则，应转为可执行语义断言，而不是每次依赖人工发现。

### 11.7 Visual Regression Failure Policy

Screenshot Diff 触发后必须先判断差异性质，不允许直接更新 Snapshot。

分类：

~~~text
Intentional Design Change
→ 设计确认
→ 更新 Snapshot

Unexpected Layout Change
→ Bug
→ Fix
→ 保持旧 Snapshot

Dynamic Data Noise
→ 固定 fixture / mask / 局部截图

Rendering Noise
→ 仅在确认非产品问题后调整最小必要 tolerance
~~~

以下差异默认视为需要人工审查：

- 行高明显变化；
- Card 高度或宽度异常变化；
- 文本从单行变成多行；
- 表格列发生明显挤压；
- CTA 位移；
- 大面积空白新增；
- 重复区块出现；
- Sidebar / Header / Tab 对齐变化；
- Loading / Empty / Error 状态布局变化。

Snapshot 不得自动接受。

### 11.8 MCP Visual Review Checklist

Release Exploration 中，Playwright MCP 对每个主要页面除功能操作外还必须检查：

~~~text
Hierarchy
Density
Alignment
Wrapping
Overflow
Overlap
Duplication
Whitespace
Primary CTA prominence
Table readability
State readability
Viewport fit
~~~

MCP 发现“页面能用但明显排版不合理”的问题时，也必须记录为 UX Bug；不得因为没有 Console Error、HTTP Error 或 DOM Overflow 就判定页面通过。

## 12. 交互流畅性标准

“能点”不代表“交互正确”。

### 12.1 点击反馈

点击以下关键操作：

~~~text
Create
Save
Apply
Delete
Login
Upload
Run
~~~

必须立即出现至少一种状态：

~~~text
disabled
loading
progress
navigation
modal
result state
~~~

不能出现：

~~~text
点击后长时间完全没有视觉反馈
~~~

### 12.2 防重复提交

提交期间按钮必须 Disabled 或等价防重。

快速双击不得产生：

~~~text
2 records
2 ChangeSets
2 credentials
2 uploads
2 mutations
~~~

### 12.3 Loading 状态

异步请求期间不能展示会让用户误认为已经完成的 stale success state。

### 12.4 Focus

Modal 打开：

~~~text
focus → dialog / first meaningful control
~~~

关闭：

~~~text
focus → 原触发控件
~~~

### 12.5 Escape

普通 Modal：

~~~text
Esc → Close
~~~

危险操作确认框是否允许 Esc 必须符合产品语义，并通过测试固定行为。

### 12.6 Keyboard

基础路径必须支持：

~~~text
Tab
Shift+Tab
Enter
Escape
Ctrl/Cmd+K
~~~

### 12.7 操作完成后的状态同步

操作成功后不得要求用户手动 Refresh 才看到结果。

例如：

- 创建 Record 后列表立即同步；
- Apply 后状态立即变为 Applied；
- revoke 后 Session 状态立即更新；
- grant/remove capability 后页面立即一致。

## 14. User Stories

1. As an operator, I want to bootstrap a fresh Modelry instance so that I can begin using Admin without manual database configuration.
2. As an operator, I want to log in and restore my session so that Admin remains usable across browser reloads.
3. As a developer, I want to create a Collection through the Admin workflow so that my Backend Model can evolve safely.
4. As a developer, I want proposed model changes to produce visible Diff and Risk so that I understand what will be changed.
5. As a developer, I want applied changes to appear in Migration History so that the Backend remains reproducible.
6. As a developer, I want to create, edit, query and delete Records so that I can operate application data.
7. As a developer, I want Relations to behave correctly across Collections so that related application data remains consistent.
8. As a developer, I want Auth Collections and credentials to work through real runtime behavior so that application users can authenticate.
9. As an operator, I want Control Plane principals, credentials and sessions to be visible and manageable so that administrative access is controlled.
10. As an operator, I want Secrets to reveal plaintext only when appropriate so that secret material is not accidentally exposed.
11. As a developer, I want Lifecycle Hooks and Domain Events to be observable so that runtime extensions can be audited.
12. As an operator, I want Activity and Audit views to reflect real actions so that important mutations can be traced.
13. As a developer, I want browser interactions to remain responsive and understandable so that Admin can be operated reliably.
14. As a release owner, I want all critical browser journeys automated so that V0.1.0 can only ship when complete user workflows actually work.
15. As a release owner, I want browser failures to retain useful traces and runtime evidence so that failures can be reproduced without guessing.
16. As a developer, I want tests to run in isolated projects so that one test cannot accidentally make another test pass or fail.

## 34. Accessibility Basic Gate

V0.1 不要求完整 WCAG Certification，但基础浏览器可操作性必须通过。

检查：

- Button 有 accessible name；
- Input 有 Label；
- Dialog 有 role/name；
- Tab 使用正确 role；
- 当前 active tab 可识别；
- 主要功能能够使用 Keyboard；
- 不存在明显 focus trap；
- 图标按钮有 aria-label；
- 表单错误能够与字段建立可理解关联。

禁止把脆弱 DOM 路径作为长期 Selector，例如：

~~~text
div:nth-child(4) > span:nth-child(2)
~~~

优先顺序：

~~~text
getByRole
getByLabel
getByText
getByTestId
CSS selector
~~~

## 38. 操作流畅度专项测试

Playwright 测试应记录关键操作的状态变化，但避免把机器性能差异误判为业务错误。

重点检测异常，而不是追求 benchmark。

基本观察链：

~~~text
Click
↓
UI feedback
↓
Request
↓
Result
~~~

失败条件包括：

- 点击无响应；
- Loading 永不结束；
- Button 永久 disabled；
- Modal 卡死；
- Route 跳错；
- Toast 与实际结果不一致；
- 状态需要手动 Refresh 才更新；
- 请求成功但 UI 仍显示旧数据；
- 页面更新导致明显错误闪烁；
- 同一操作必须点击两次才能生效；
- 快速重复操作造成重复提交；
- 返回/前进后页面状态与 URL 不一致。

对于需要时间预算的关键交互，可以记录 duration 作为诊断数据，但 V0.1 不设置跨机器严格性能阈值，除非后续有独立 Performance Spec。

Failed Requests
Test Name / Case ID
Runtime Logs
Project Root path or retained diagnostic bundle
~~~

诊断工件不得包含应被保护的 Secret plaintext；涉及 Secret 的测试输出必须主动 redact。

---

## 41. Flaky Test Policy

严禁使用固定 sleep 解决状态同步问题，例如：

~~~text
sleep(1000)
sleep(3000)
~~~

必须等待：

~~~text
DOM state
URL
network response
specific visible state
enabled state
public API visible business result
~~~

测试允许 Retry 用于诊断偶发环境问题，但：

~~~text
Retry 后通过 ≠ 正常通过
~~~

持续 flaky 必须创建 Issue。

Release Gate 应单独报告：

- first-attempt pass；
- retry-pass；
- failed。

不得把 retry-pass 静默统计为完全健康。

---

## 42. Test Data

每个测试使用唯一前缀：

~~~text
pw_<worker>_<test>_
~~~

例如：

~~~text
pw_2_relation_posts
~~~

禁止测试依赖：

~~~text
测试执行顺序
前一个 Case 创建的数据
开发环境手工数据
固定数据库 ID
~~~

Business Closure Test 可以在单个 Case 内连续创建业务状态。

测试数据必须由 Case 自身或 Fixture 明确创建，并能够定位其生命周期。

---

## 43. 并行策略

Feature Tests 可 parallel。

Business Closure Tests 使用独立 Runtime / Project Root。

不得让 test A 和 test B 修改同一个 Project。

同一 Closure Flow 内允许 serial steps，但应保留为一个业务 Journey，避免通过跨 Test Case 隐式共享状态制造顺序依赖。

## 49. Definition of Done

该 Spec 只有同时满足以下条件才算完成。

### 49.1 Infrastructure

- Playwright Test 已加入仓库。
- Chromium 可自动安装/发现。
- Runtime fixture 可独立启动真实 standalone。
- 支持 dynamic port。
- 支持 isolated project root。
- 支持 restart。
- HTML report 可生成。
- Trace / Screenshot / Video 可保留。
- Windows / POSIX 不存在硬编码路径依赖。
- 测试子进程与临时目录能够可靠清理。

### 49.2 Quality

- 无固定 sleep。
- 无测试顺序依赖。
- 无 Mock 替代 Mandatory Runtime。
- 无直接内部 Repository 注入。
- Browser Console 默认 clean。
- Unexpected 5xx 默认失败。
- Selector 优先使用用户可见语义。
- Secret 不进入 report/trace 明文工件。
- Flaky retry 被显式记录。

## 51. 最终测试模型

完成后 Modelry 的质量证明链应为：

~~~text
Unit
  ↓
Integration
  ↓
Contract
  ↓
Standalone
  ↓
Browser Smoke
  ↓
Playwright Feature Tests
  ↓
Playwright Business Closure
  ↓
Playwright MCP Exploratory QA
  ↓
Release
~~~

最终原则：

> **任何被认为是 Modelry V0.1.0 核心能力的功能，都必须至少存在一个真实浏览器路径证明用户能够使用它；任何核心业务闭环，都必须存在一个从用户动作开始、以 Durable Runtime State 结束的 Playwright Case。**

以及：

> **Playwright 的目标不是证明按钮能点，而是证明 Modelry 作为一个产品真的能够工作。**
