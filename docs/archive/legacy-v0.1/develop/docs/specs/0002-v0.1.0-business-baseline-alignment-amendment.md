## 3. ChangeSet 与 Apply Attempt 分离

### 3.1 领域语义

固定：

- **ChangeSet** 表达 Backend Model / 受管配置的变更提案；
- **Apply Attempt** 表达针对一个 ChangeSet 的一次实际 Apply 执行尝试；
- 一个 ChangeSet 可以对应多个 Apply Attempt；
- 一次 Apply Attempt 失败，不得把 ChangeSet 永久定义为 `failed`；
- Retry 创建新的 Apply Attempt；
- 成功的 Apply Attempt 推动 ChangeSet 成为 `applied`。

因此 Spec 0001 主文 21.1 与 Review Amendment 5.1 中的 terminal `failed ChangeSet` 语义被本节覆盖。

### 3.2 ChangeSet 状态

产品状态固定为：

```text
Draft -> Ready -> Applying -> Applied
```

取消分支：

```text
Draft / Ready -> Cancelled
```

V0.1.0 Control Plane 若不提供服务端持久化 Draft，可在 `Propose` 成功时直接创建 `Ready` ChangeSet；这属于实现简化，不得改变领域语义。

`Applying` 是暂态。一次 Apply Attempt 失败后：

```text
Applying -> Ready
```

同时保留 Failed Apply Attempt 与错误原因。

`Applied` 与 `Cancelled` 是 ChangeSet 终态；`Failed` 不再是 ChangeSet 终态。

### 3.3 Apply Attempt 状态

每次 Apply 创建独立 Apply Attempt：

```text
Pending -> Running -> Succeeded
                   -> Failed
```

Apply Attempt 至少记录：

- Attempt ID；
- ChangeSet ID；
- 发起 Principal；
- 当前计算 Risk / impact；
- confirmation actor / confirmation context（需要时）；
- Preconditions summary；
- started / finished timestamps；
- result；
- structured error；
- 与 reserved Apply Plan / Migration Artifact 的关联。

### 3.4 Crash Recovery 与 Artifact Identity

Review Amendment 6 中“同一 ChangeSet 不得因为 retry 生成第二份 Migration Artifact”的安全目标继续有效。

规范调整为：

- ChangeSet 在第一次进入真实 migration apply 阶段时可以形成一个稳定的 reserved Apply Plan；
- reserved Migration ID、Artifact filename 与 exact Artifact bytes 属于该 ChangeSet 的稳定 Apply Plan；
- Runtime crash 后恢复同一个 Running Apply Attempt 时继续复用该 Plan；
- 一个 Failed Apply Attempt 后若允许重新 Retry，新 Apply Attempt 仍必须复用已存在且验证一致的 reserved Apply Plan，不得生成第二条等价 Project Migration；
- 如果失败发生在 Artifact/Apply Plan reservation 之前，则新的 Apply Attempt 可以重新执行 Risk / Preconditions 并首次创建 Apply Plan；
- Artifact 内容或 base hash 已不再适用时，必须拒绝 Retry 并要求重新 Propose，而不是偷偷重写原 Artifact。

## 4. Agent Apply 与 Human Confirmation

### 4.1 Apply 权限

`changeset:propose` 与 `changeset:apply` 继续严格分离。

Agent / Service Principal 只有显式拥有 `changeset:apply` 以及 ChangeSet 内容所需 Scope 时，才可以调用 Apply。

### 4.2 Risk Gate

V0.1.0 默认固定：

- `SAFE` 且没有额外 access-impact confirmation 要求：拥有 Apply 权限的 Agent 可以直接发起 Apply Attempt；
- `DATA_REWRITE`：必须 Human Confirmation；
- `DESTRUCTIVE`：必须 Human Confirmation；
- `IRREVERSIBLE`：必须 Human Confirmation；
- `expandsAccess=true`：即使 data risk 为 SAFE，也必须 Human Confirmation。

Spec 0001 21.5 关于 DATA_REWRITE 及以上需要 confirmation 的规则继续有效；本 Amendment 进一步固定：**这些高风险确认不能由发起 Apply 的 Agent / Service Principal 自己充当 Human Confirmation actor。**

Human Confirmation 必须来自具有相应管理能力的交互式 Admin Principal，并记录到 Apply Attempt / Audit。

### 4.3 MCP

`changeset_apply` 的行为固定为：

- SAFE：具备所需 Scope 时可直接执行；
- 需要 Human Confirmation：返回结构化 `CONFIRMATION_REQUIRED` 与 ChangeSet/Risk/impact 信息；
- Human 在 Admin/受控交互管理入口完成确认后，Agent 可以继续触发已获批准的 Apply Attempt，或者由 Human 直接执行；
- Agent 不能生成一个自我声明的 confirmation token 来绕过 Human Gate。

## 5. Administrative Data Mutation 不使用 ChangeSet

普通 Administrative Record CRUD 继续使用 `data:inspect` / `data:mutate`，并必须 Audit。

它不进入 Backend Model ChangeSet。

如果 V0.1.0 或后续 V0.1.x 暴露批量删除、批量更新或其他高影响 Administrative Data Mutation，必须遵循：

```text
Target Selection
-> Impact Preview
-> Human Confirmation
-> Execute
-> Result Summary
-> Audit
```

该安全链路不得通过创建伪 ChangeSet 实现。

当前 V0.1.0 若不提供 bulk mutation，则本节不要求为满足文档而提前扩 Scope；它只固定未来实现边界。

## 6. Admin Collections 任务顺序

Spec 0001 38.1 的 `Collections` 需求调整为业务优先级：

```text
Collections
-> Collection
   -> Records       (default)
   -> Schema
   -> Relations
   -> Indexes
   -> Policy
   -> Auth           (Auth Collection only)
```

要求：

- 单个 Collection 默认进入 Records；
- Schema Editor 不作为 Collection 默认首屏；
- Records 工作面必须能够感知会影响当前 Collection 的 Pending ChangeSet、Migration Risk 或 Drift；
- 具体提示形式属于 UI 设计，不在 Spec 固定像素或组件。

这不改变 Collection 同时承载 Model 与 Data 的领域模型。

## 7. API 采用 Project-wide Explorer

Spec 0001 38.1 的 API 页面进一步固定为 **Project-wide API Explorer**。

其核心视角覆盖：

- Data API；
- Auth API；
- OpenAPI 3.1；
- Realtime；
- V0.1.x 的 Custom API Route Contract。

Collection Detail 可以提供“查看此 Collection API”的上下文跳转，但跳转目标仍是 Project API Explorer 的 Collection-filtered view，不在每个 Collection 内复制一套独立 API 文档系统。

---

## 8. Changes 页面展示 Apply Attempt，而不是 Failed ChangeSet

Spec 0001 38.1 中：

`Proposed/Applied/Failed/Cancelled ChangeSets`

被替换为：

- Ready / Applying / Applied / Cancelled ChangeSets；
- ChangeSet Diff / Risk / impact；
- Human Confirmation Gate；
- Apply Attempt History；
- Failed Apply Attempts 与错误；
- Migration History / export state。

失败属于 Apply Attempt 历史，而不是一个新的 terminal ChangeSet 类型。

---

## 9. Reference Application 固定为 Blog

Spec 0001 User Story 50 中的 **Notes demo** 被本 Amendment 覆盖。

V0.1.0 Reference Application 固定为 **Blog**，至少包含：

```text
users       (Auth Collection)
posts
comments
categories
```

并通过 `posts` 或等价对象覆盖 File Field。

Reference Application 必须验证：

- Auth Collection；
- Record CRUD；
- Relation；
- File；
- Policy；
- Realtime；
- Lifecycle Hook；
- OpenAPI / API Usage；
- Agent Inspect；
- Human / Agent ChangeSet；
- Agent SAFE Apply；
- 高风险 Human Confirmation；
- Apply Attempt failure + retry；
- Migration；
- Drift / Doctor；
- Audit。

验收重点从“页面/能力分别存在”改为“Developer + Coding Agent 完成真实 Backend 建立、数据使用、API 接入、安全变更与诊断闭环”。

## 10. User Story 修正

Spec 0001 的相关 User Stories 按以下语义解释：

- User Story 27：`DATA_REWRITE / DESTRUCTIVE / IRREVERSIBLE` 都需要 Human Confirmation；DESTRUCTIVE / IRREVERSIBLE 额外要求 recovery checkpoint；
- User Story 37：Agent with apply permission 仅可对 SAFE、无需额外 access-impact confirmation 的 ChangeSet 自动 Apply；其他风险等级需要 Human Confirmation；
- User Story 50：Reference Application 为 Blog，不再是 Notes。
