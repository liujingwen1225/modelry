# Spec 0001：Modelry V0.1.0 Core Closure 技术规格

- **Status:** Proposed — Ready for Review
- **Date:** 2026-09-02
- **Phase:** `to-spec`
- **Target Release:** V0.1.0
- **Runtime Baseline:** Bun + TypeScript — Spike `GO`

## 1. 目的

本文档把已经 Accepted 的 Product Scope、领域语言、ADR 与 Bun Runtime Spike 结果综合为一份**可直接拆解为实现 Ticket** 的 V0.1.0 技术规格。

本文档不重新讨论产品方向，也不继承 Spike Prototype 的临时代码结构。

V0.1.0 的核心成功闭环是：

`init -> serve -> Admin 建模 -> Data API / OpenAPI -> MCP Inspect -> Propose -> ChangeSet + Diff + Risk -> Apply -> Migration Artifact -> Runtime Backend Model -> Schema Snapshot -> Git Diff`

只要该闭环在真实 Demo App 上稳定、明确、可审计、可复现，V0.1.0 即成立。

## 3. Problem / Solution

### 3.1 Problem

传统轻量 Backend 对人类开发者友好，但 Coding Agent 往往只能通过数据库、零散配置或非结构化代码猜测 Backend 状态；Agent 的 Schema 变更也容易成为不可审查、不可 Git Diff、不可安全确认的直接 Mutation。

### 3.2 Solution

Modelry V0.1.0 提供一个单 Binary、自托管、SQLite-first 的 Backend Runtime，并将 Backend Model、ChangeSet、Diff、Risk、Migration、Audit 与 MCP 设计成同一个控制面语义。

人类通过 Admin/CLI 工作，Coding Agent 通过 MCP 工作，但两者修改的是同一个 Backend Model，并产生同样的 Migration Artifact 与 Audit Fact。

## 4. User Stories

以下 User Stories 是 V0.1.0 的完整行为边界；后续 Ticket 不得遗漏失败路径与治理路径。

1. As an application developer, I want to initialize a Modelry project with one command, so that I can start a backend without assembling infrastructure.
2. As an application developer, I want to run the project with one standalone executable, so that deployment does not require a separate Node or Bun installation.
3. As a project owner, I want to create the first Control Plane admin through a one-time bootstrap flow, so that an uninitialized instance can become securely manageable.
4. As an admin, I want to create a Normal Collection through the Admin UI, so that I can model application data without editing the database directly.
5. As an admin, I want to create an Auth Collection with email or username login identifiers, so that business identities remain part of the application model rather than the Control Plane admin model.
6. As an admin, I want to define fields, relations, indexes, defaults and validations, so that the Backend Model explicitly describes application data constraints.
7. As an admin, I want to configure separate list/view/create/update/delete Record Policies, so that each Data Plane operation has an explicit authorization rule.
8. As an application developer, I want a generated OpenAPI 3.1 document after model changes, so that clients and Coding Agents can understand the current Data API contract.
9. As an application user, I want to create, read, update and delete authorized records, so that the backend supports a real application workflow.
10. As an application user, I want filtering, sorting, pagination and relation expansion, so that normal application screens do not need custom query endpoints.
11. As an application user, I want unauthorized records to remain undiscoverable, so that Record Policy failures do not leak record existence.
12. As an application user, I want relation expansion to respect the target Collection view policy, so that expansion cannot become an authorization bypass.
13. As an application user, I want to register and log in using an enabled Auth Collection identifier and password, so that the application can establish a revocable business identity.
14. As an authenticated user, I want to list and revoke my sessions, so that lost or unwanted sessions can be invalidated server-side.
15. As an authenticated user, I want to upload a file and bind it to a File Field, so that files remain part of the Record model instead of a separate asset permission system.
16. As an authorized user, I want file download authorization to follow the owning Record view policy, so that file URLs cannot bypass data authorization.
17. As an application user, I want to receive SSE changes for records I am currently allowed to see, so that the UI can update in real time without treating Realtime as a durable queue.
18. As an application user, I want a realtime removal signal when a previously visible record becomes invisible to me, so that my client does not retain stale unauthorized data.
19. As a project developer, I want a synchronous Lifecycle Hook to validate or deterministically modify a pending mutation, so that simple business logic can live beside the project.
20. As a project developer, I want a bad or runaway Hook invocation to fail the mutation without killing the Core Runtime, so that project-code bugs do not take down the backend.
21. As a project developer, I want Hook reload to keep the last known good generation when a new version is invalid, so that editing project code does not unnecessarily break a running instance.
22. As a project developer, I want in-flight Hook calls to finish against a stable generation while new calls move to the new generation, so that reload behavior is predictable.
23. As an admin, I want to create and replace Secrets without reading their plaintext back through normal Inspect APIs, so that sensitive configuration has an explicit exposure boundary.
24. As an admin, I want every Backend Model edit to first become a ChangeSet with a structured Diff and Risk, so that I can understand the change before applying it.
25. As an admin, I want stale ChangeSets to be rejected when the Backend Model changed after proposal, so that an old proposal cannot silently overwrite newer model state.
26. As an admin, I want risky migrations to report Preconditions and impact before Apply, so that unsafe data changes fail before mutating Runtime state.
27. As an admin, I want destructive or irreversible migrations to require explicit confirmation and a recovery checkpoint, so that data loss is never an implicit side effect.
28. As an admin, I want Apply to produce an immutable Project Migration Artifact before the Runtime mutation becomes durable, so that a successful schema change never exists without reproducible history.
29. As an application developer, I want Schema Snapshot to be regenerated from the applied Runtime Backend Model, so that Coding Agents can inspect the current model without starting the server.
30. As an application developer, I want Modelry to detect pending migrations and hard Drift instead of silently guessing, so that repository state and runtime state cannot diverge invisibly.
31. As an operator, I want hard Drift to put the runtime into a diagnostic-safe state, so that inconsistent schema state does not continue serving normal application traffic.
32. As an operator using a read-only Project Source, I want applied generated artifacts to remain durably exportable, so that production runtime changes can still be reconciled back into Git without being misclassified as unexplained drift.
33. As an admin, I want a durable Audit trail for Control Plane changes, administrative data access, security-sensitive actions and migration Apply, so that I can identify who changed what and with which result.
34. As an admin, I want to create Agent / Service Principals and one-time-visible API Keys with explicit scopes, so that Coding Agents can use least-privilege Control Plane access.
35. As an agent, I want to inspect the project, schema, migrations, ChangeSets, runtime status and audit through MCP, so that I can reason about the backend without scraping UI text.
36. As an agent, I want to propose a Collection or Policy change without mutating runtime state, so that my suggested change can be reviewed before Apply.
37. As an agent with apply permission, I want to apply a non-stale accepted ChangeSet through MCP, so that machine-driven changes use the same migration path as human changes.
38. As an agent without apply permission, I want `changeset_apply` to be denied even when I can propose changes, so that proposal authority does not imply execution authority.
39. As an agent with `data:inspect`, I want to query business records administratively without pretending to be an Auth Principal, so that debugging remains explicit and auditable.
40. As an agent with `data:mutate`, I want to create or update business records administratively, so that controlled maintenance tasks do not require a Record Policy impersonation hack.
41. As an agent, I want Secret Inspect to return only name and presence metadata, so that machine access does not accidentally disclose secret plaintext.
42. As an agent, I want no generic SQL, shell or arbitrary filesystem MCP tool, so that Modelry remains a bounded Backend collaborator rather than an unrestricted host administrator.
43. As a CLI user, I want status, schema, diff, migrate and doctor commands to use the same Modelry semantics as the Admin and MCP paths, so that the CLI cannot create an alternative schema-management model.
44. As a Git user, I want each applied Backend Model change to appear as a reviewable migration/snapshot diff, so that backend evolution participates in the same PR workflow as application code.
45. As a developer using optimistic locking, I want stale record updates to fail deterministically, so that concurrent clients do not silently overwrite each other.
46. As a developer using soft delete, I want normal Data Plane queries to exclude deleted records by default, so that deletion semantics stay consistent without physical data removal on the request path.
47. As a TypeScript developer, I want an official TypeScript client and generated project types, so that application code can consume the current Backend Model with static types.
48. As an API consumer, I want stable structured error codes and request IDs, so that clients and Coding Agents do not depend on parsing natural-language error strings.
49. As an operator, I want the same project to pass release smoke tests on Linux x64 and Windows x64, so that the validated Single Binary model is preserved in production packaging.
50. As a project owner, I want a Notes demo to exercise Auth, Policy, Relation, File, Hook, Realtime, MCP ChangeSet, Migration, Drift and Audit, so that V0.1.0 is accepted through a real end-to-end application rather than isolated feature tests.

## 5. Production Architecture

### 5.1 Architecture Style

V0.1.0 is a **modular monolith** compiled into one Bun standalone executable.

Production code has one composition root and explicit deep modules. It must not introduce microservices, Redis, Kafka, a plugin host, or a generic database abstraction layer.

Logical modules:

1. **Runtime** — process lifecycle, configuration, listener, runtime modes.
2. **Backend Model** — canonical model types, model hash, validation.
3. **Change Engine** — ChangeSet, Diff, Risk, Apply coordination.
4. **SQLite Runtime Store** — concrete V0.x persistence and physical schema execution.
5. **Migration** — artifact validation, planner, ledger, drift, checkpoint.
6. **Expression / Policy** — parser, AST, type checking, SQL compilation and policy evaluation.
7. **Data Plane** — Record API, query, relation expansion.
8. **Auth** — Principal, Credential, Session, Auth Collection lifecycle.
9. **Control Plane** — Admin/Agent management APIs and Capability checks.
10. **Files** — Upload Session, File metadata, Local object storage, file cleanup.
11. **Hooks** — Lifecycle Hook registration, generation loading and fault boundary.
12. **Realtime** — SSE subscription projection and in-process replay window.
13. **Audit / Durable Work** — required Audit Fact and internal transactional outbox jobs.
14. **Admin Web** — embedded React application using Control Plane APIs.
15. **CLI** — local bootstrap/diagnostic commands and Control Plane client commands.
16. **MCP** — stdio adapter to a running Control Plane.
17. **TypeScript Client** — official Data Plane SDK plus generated project types.

These are module boundaries, not a requirement to publish separate npm packages.

### 5.2 No Speculative Database Adapter

SQLite implementation may use SQLite-specific capabilities directly inside the SQLite Runtime Store.

Backend Model types and public product contracts must not expose SQLite-only concepts, but V0.x must **not** create a `DatabaseAdapter` interface merely for a hypothetical PostgreSQL implementation.

### 5.3 Narrow File Object Store Seam

Files may define one narrow `FileObjectStore`-style port covering object put/read/delete/health operations.

This is not speculative database abstraction: Local Storage is V0.1.0 and S3 Compatible Storage is already an Accepted V0.1.x implementation. The seam must remain specific to file object storage and must not become a generic provider framework.

### 5.4 Validated Runtime Decisions

- Bun standalone compilation is required for release artifacts.
- Linux x64 and Windows x64 are V0.1.0 release targets.
- Admin assets are embedded into the executable.
- Worker is the preferred Lifecycle Hook fault boundary.
- A self-spawned copy of the same executable remains the fallback if a production Worker limitation is discovered.
- macOS release support is not a V0.1.0 acceptance requirement.

## 6. Project and Runtime Layout

Default project layout is fixed for V0.1.0:

```text
<project>/
├── modelry.config.json
├── .modelry/
│   ├── migrations/
│   ├── hooks/
│   └── schema.snapshot.json
└── data/
    ├── modelry.db
    ├── storage/
    ├── uploads/
    ├── checkpoints/
    └── master.key
```

Git rules:

- commit `modelry.config.json`;
- commit `.modelry/migrations/`;
- commit `.modelry/hooks/`;
- commit `.modelry/schema.snapshot.json`;
- never commit `data/`.

`dataDir` may be overridden by Runtime Config, but Project Source semantics do not change.

`modelry.config.json` is versioned declarative JSON. It contains no plaintext Secret.

Minimum config areas:

- config schema version;
- server host / port;
- Data Plane CORS allowed origins;
- data directory;
- Local Storage root;
- Hook registrations and timeouts.

Default listener: `127.0.0.1:8090`. Remote exposure is explicit through config/CLI host override.

## 7. Runtime Modes and Locking

The same executable supports:

- `serve` — Project Runtime + HTTP Data/Control Plane + embedded Admin;
- `mcp` — stdio MCP adapter that connects to a running Control Plane;
- CLI commands.

A running `serve` process owns a Project runtime lock under Runtime Data. No second process may directly perform a competing Runtime write against the same Project.

Schema/data mutation from Admin, CLI or MCP must ultimately enter the running Instance application services; CLI must not contain a second independent schema mutation engine.

## 8. Backend Model

### 8.1 Canonical Model

The canonical in-memory `BackendModel` contains at minimum:

- model schema version;
- model revision;
- stable `modelHash`;
- Collections;
- Fields;
- Relations;
- Indexes;
- Defaults / validations;
- Record Policies;
- Auth Collection capability configuration;
- Collection options such as soft delete / optimistic lock.

`modelHash` is SHA-256 over canonical JSON with deterministic key ordering. It is used for stale ChangeSet detection, migration before/after verification and snapshot validation.

### 8.2 Stable Identity

Collection, Field, Index and Policy definitions have stable opaque UUID identifiers in addition to human-readable names.

Rename preserves the stable ID. Rename must never be represented as delete + add.

### 8.3 Naming Rules

V0.1.0 Collection and Field API names use lowercase ASCII identifiers:

- begin with `a-z`;
- continue with `a-z`, `0-9` or `_`;
- max length 63;
- `_modelry` prefix is reserved.

Names are unique within their natural scope.

### 8.4 Built-in Record Metadata

All Records expose server-owned metadata:

- `id` — UUIDv4 string;
- `createdAt` — UTC RFC3339 datetime;
- `updatedAt` — UTC RFC3339 datetime.

If optimistic locking is enabled, Record also exposes `version` starting at `1`.

If soft delete is enabled, Runtime maintains `deletedAt`; normal Data Plane responses do not expose deleted Records by default.

System metadata is read-only through normal Data Plane mutation payloads.

## 9. Field Semantics

### 9.1 Common Properties

Every user Field has:

- stable ID;
- name;
- type;
- required flag;
- optional literal default;
- type-specific declarative validation.

Arbitrary JavaScript validators are not part of declarative validation; business logic belongs in Lifecycle Hook.

### 9.2 Types

#### text

JSON type: string. Supports min/max length and optional regular expression validation.

#### integer

JSON type: number restricted to JavaScript safe integers. Out-of-range or non-integral values are rejected.

#### number

JSON type: finite IEEE-754 double. `NaN` and infinities are rejected.

#### decimal

API representation: canonical decimal **string**, never JSON floating point.

V0.1.0 decimal requires explicit `precision` and `scale`:

- precision: `1..18`;
- scale: `0..precision`.

SQLite stores the normalized value as a scaled signed 64-bit integer. Runtime uses integer/BigInt arithmetic for conversion and comparison so decimal filters remain exact within the declared precision.

#### boolean

JSON boolean.

#### date

Canonical string `YYYY-MM-DD`.

#### datetime

Canonical UTC RFC3339 string. Input with an offset is normalized to UTC before persistence.

#### json

Any valid JSON value. Stored as canonical JSON text; maximum request body limits still apply.

#### relation

References another Collection by stable Collection ID.

Properties:

- cardinality: `one | many`;
- required;
- `onDelete: restrict | setNull`.

For `many`, `setNull` means remove the deleted target from the relation set. Cascade delete is not supported in V0.1.0.

Data Plane relation writes require every referenced target to be valid and viewable by the current Auth Principal; failure must not reveal whether a forbidden target exists.

#### file

Represents one or many committed File References owned by the Record Field.

Properties:

- `multiple`;
- maximum file count;
- maximum bytes per file;
- allowed MIME patterns.

#### select

Contains one or many values from an explicit finite option list. Option values are stable strings.

#### email

String with normalized email syntax validation. When used as an Auth login identifier, login identity uniqueness is enforced on a normalized identity key.

#### url

String requiring an absolute `http` or `https` URL in V0.1.0.

### 9.3 Defaults

V0.1.0 user-defined defaults are literal values only.

Automatic `id`, `createdAt`, `updatedAt` and optional `version` are system metadata, not user defaults.

## 10. Index Semantics

V0.1.0 supports normal and unique indexes over one or more scalar Fields.

Not supported:

- expression indexes as a public Backend Model concept;
- partial indexes;
- full-text indexes;
- vector/GIS indexes.

Unique Index creation performs a full precondition check before any schema mutation. Existing duplicates cause a machine-readable precondition failure.

## 11. SQLite Runtime Persistence

### 11.1 Runtime Backend Model

Runtime persists a materialized Backend Model state internally with:

- current model revision;
- current model hash;
- canonical model JSON;
- current applied migration identity.

This internal state **is the Runtime Backend Model**, not a fourth manually editable Source of Truth.

### 11.2 System State

SQLite internal system state covers at minimum:

- System Migration ledger;
- Runtime Backend Model state;
- Project Migration ledger and artifact hash;
- generated-artifact export state;
- Admin/Auth/Agent Principals;
- Password/API Key/Session credentials;
- Audit Facts;
- File metadata and Upload Sessions;
- durable cleanup/outbox work;
- Runtime Hook error/status metadata;
- recoverable Config Apply journal.

Exact physical table names are internal and are not a compatibility contract.

### 11.3 Business Records

Business Collection physical table/column mapping is private implementation detail. Public code uses Backend Model identities and names, never SQLite table naming.

SQLite schema changes execute inside transactions whenever SQLite supports transactional execution. Table rebuilds required by SQLite remain an internal Migration Executor concern.

### 11.4 System Migration

Runtime internal schema evolution uses a **System Migration** ledger fully separate from Project Migration History.

At startup:

1. binary checks internal System Schema version;
2. required System Migrations run before Project Drift evaluation;
3. System Migration never creates a user Project Migration Artifact;
4. failure places Runtime in diagnostic-safe mode rather than partially starting normal Data Plane service.

V0.1.0 only needs the framework and initial schema history necessary to support later V0.1.x upgrades; it does not implement self-update or arbitrary downgrade.

## 12. Expression Engine

### 12.1 One Language

The same parser, AST, type checker and execution semantics are used by:

- Data API filter;
- Record Policy;
- Realtime subscription filter;
- Administrative data query filter.

No path directly concatenates user expressions into SQL.

### 12.2 V0.1.0 Operators

Supported baseline:

- `==`, `!=`;
- `<`, `<=`, `>`, `>=`;
- `&&`, `||`, `!`;
- `null` comparison;
- `contains`;
- `in` against literal lists;
- scalar Field access;
- single Relation one-level Field access;
- many-Relation ID membership through `contains`;
- explicit auth and policy context references.

Unsupported:

- arbitrary JS;
- raw SQL;
- arbitrary database functions;
- recursive/deep relation traversal;
- user-defined functions.

### 12.3 Context

Policy context exposes only declared values:

- `auth.id` — Auth Collection Record ID or `null`;
- `auth.collection` — Auth Collection name or `null`;
- `record` — the current evaluated Record;
- `before` — pre-mutation Record when applicable;
- `after` — candidate post-mutation Record when applicable.

Bare Field names are aliases for `record.<field>`.

Admin/Agent Principal is never mapped into `auth.id`.

## 13. Record Policy Evaluation

### 13.1 Default

Data Plane Record Policy is **deny by default**.

A Collection must explicitly allow each required operation.

### 13.2 Operation Semantics

#### list

List Policy is compiled together with the caller Filter and executed in SQLite. Records must not be fetched wholesale and filtered afterward.

Returned rows must satisfy both `list` and `view` policy, so enumeration cannot return a Record that the same principal cannot view.

#### view

Evaluated on the persisted Record.

Unauthorized single-record requests return `404 NOT_FOUND`, not a distinct existence-revealing forbidden response.

#### create

Flow:

1. parse candidate;
2. basic type/field validation;
3. run `beforeCreate` Lifecycle Hooks;
4. validate final candidate;
5. evaluate create Policy against the final `after` candidate;
6. persist transactionally.

This allows a Hook to deterministically populate an owner field before Policy is evaluated.

#### update

Flow:

1. load existing `before` Record under a non-leaking lookup path;
2. evaluate the update Policy against `before`;
3. build candidate;
4. run `beforeUpdate` Lifecycle Hooks;
5. validate final candidate;
6. evaluate the same update Policy against final `after`;
7. persist transactionally.

Both before-side and after-side evaluation must pass. This prevents a caller from moving a Record across an authorization boundary through update.

#### delete

Delete Policy evaluates on `before`, then `beforeDelete` Hook runs, then the delete/soft-delete transaction executes.

### 13.3 Relation Expand

Expand depth is capped at **2** in V0.1.0.

Each expanded target is independently evaluated against the target Collection `view` Policy.

- denied single target expands as `null`;
- denied entries in a many Relation are omitted;
- the parent Record’s raw relation ID value remains governed by the parent policy and is not treated as the expanded target body.

### 13.4 Failure Model

Expression parse/type/evaluation errors fail closed and return structured errors to authorized model authors; Data Plane callers never receive an accidental allow because a Policy failed to execute.

## 14. Data Plane HTTP API

Namespace: `/api/v1/*`.

Business Access Token is sent as `Authorization: Bearer <access-token>`.

### 14.1 Record Routes

- `GET /api/v1/collections/:collection/records`
- `POST /api/v1/collections/:collection/records`
- `GET /api/v1/collections/:collection/records/:id`
- `PATCH /api/v1/collections/:collection/records/:id`
- `DELETE /api/v1/collections/:collection/records/:id`

No `PUT` replacement semantics in V0.1.0.

### 14.2 List Query

Query parameters:

- `filter` — Expression Engine string;
- `sort` — comma-separated Field names, `-field` descending;
- `page` — positive integer, default `1`;
- `perPage` — default `30`, max `100`;
- `expand` — comma-separated Relation paths, depth <= 2.

Response envelope contains:

- `page`;
- `perPage`;
- `totalItems`;
- `totalPages`;
- `items`.

### 14.3 Optimistic Lock

If a Collection enables optimistic locking:

- every returned Record contains `version`;
- `PATCH` and `DELETE` require `If-Match` for the expected version;
- mismatch returns `409 OPTIMISTIC_LOCK_CONFLICT`;
- a successful update increments version exactly once.

### 14.4 Soft Delete

If enabled, Data Plane `DELETE` sets `deletedAt` and the Record disappears from normal list/view/relation expansion.

Data Plane has no `includeDeleted` escape hatch. Administrative Data Access may inspect deleted Records.

### 14.5 Body Limit

Default non-file JSON request body limit is **1 MiB**. Larger business payload requirements belong to explicit future configuration, not accidental unlimited parsing.

### 14.6 CORS

Data Plane uses explicit configured allowed origins. Control Plane is not exposed through Data Plane CORS configuration.

## 15. Auth Model

### 15.1 Principal Types

Production V0.1.0 uses the three Accepted principal types:

- Admin Principal;
- Auth Principal;
- Agent / Service Principal.

Credentials never become Principals.

### 15.2 Business Auth Collection

An Auth Collection maps each authenticated business Record to an Auth Principal.

Auth configuration declares one or both login identifiers:

- email login bound to an `email` Field;
- username login bound to a `text` Field.

Normalized login identities are unique inside the Auth Collection.

`auth.id` exposed to Policy is the Auth Collection Record ID, not the internal Principal metadata ID.

### 15.3 Registration and Login Routes

- `POST /api/v1/auth/:collection/register`
- `POST /api/v1/auth/:collection/login`
- `POST /api/v1/auth/refresh`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/sessions`
- `DELETE /api/v1/auth/sessions/:sessionId`
- `POST /api/v1/auth/logout-all`

Registration must be explicitly enabled in Auth Collection configuration.

Registration creates the Record, Principal, identity mapping and Password Credential as one logical transaction. Failure must not leave a partially registered identity.

Login identity lookup is an Auth subsystem operation and does not require Data Plane `view` Policy on the Auth Record; post-login business data access still uses normal Record Policy.

### 15.4 Password

Password is not a Collection Field and is never returned by Record APIs.

Production password hashes use **Argon2id** with versioned hash parameters so future rehash can be performed after successful login.

Default business password minimum is 8 characters; Auth Collection may raise it. Maximum accepted password length is 128 Unicode characters.

No composition rules are required by default.

### 15.5 Sessions

V0.1.0 uses opaque, revocable server-side sessions:

- Access Token default lifetime: **15 minutes**;
- Refresh Token default lifetime: **30 days**;
- both tokens are high-entropy opaque values;
- persistent state stores token hashes, not plaintext tokens;
- refresh rotates the Refresh Token;
- logout/revoke invalidates the server-side session;
- deleting/soft-deleting an Auth Collection Record revokes its active sessions.

Session metadata includes session ID, principal ID, created/last-used/expires/revoked timestamps and bounded request device metadata.

### 15.6 Email / Username Normalization

Login identity values are trimmed and normalized for lookup. Email lookup is case-insensitive. Username lookup is case-insensitive in V0.1.0.

The business Record may preserve the display form; internal identity uniqueness uses normalized form.

### 15.7 Deferred Auth

Password Reset, Email Verification, OTP, OAuth and Anonymous Auth are V0.1.x and must not be partially implemented in V0.1.0.

## 16. Admin Authentication and Bootstrap

### 16.1 First Admin

When no Admin exists, `modelry serve` creates a cryptographically random one-time Bootstrap Setup Token and prints it to the local console.

The token:

- exists only for bootstrap;
- is invalidated immediately after first Admin creation;
- is replaced on process restart if bootstrap was not completed;
- never becomes a reusable API credential.

Admin UI provides a setup route under `/admin` using this token.

### 16.2 Admin Credential

V0.1.0 Admin uses email + password and the same underlying revocable session machinery, but Admin is stored in Control Plane system state, never in a business Auth Collection.

Bootstrap Admin receives all V0.1.0 Capability Scopes. Additional Admins may be created only by a Principal with `access:manage` and receive an explicit scope set; role templates are not required.

### 16.3 Admin Browser Session

Admin SPA keeps short-lived access credentials in memory and uses a server-side revocable refresh session. Refresh material uses an HttpOnly cookie with `SameSite=Lax`; `Secure` is set whenever the request origin is HTTPS.

Control Plane mutation endpoints never accept unauthenticated browser requests.

Agent / Service Principal uses API Key Credential.

## 21. ChangeSet

### 21.1 State

V0.1.0 ChangeSet states:

- `proposed`;
- `applied`;
- `cancelled`;
- `failed`.

`failed` records an Apply attempt failure; it does not imply Runtime model mutation succeeded.

### 21.2 Required Data

A ChangeSet contains:

- immutable ID;
- kind: `model | config`;
- source Principal;
- reason;
- `baseModelHash` for model changes;
- typed operations;
- structured before/after Diff;
- single sortable Risk Level;
- impact flags;
- reversibility description;
- created/applied/cancelled timestamps;
- Apply result and error when relevant.

Caller-supplied Risk is never authoritative; Runtime computes Risk and Preconditions.

### 21.3 Staleness

A model ChangeSet can Apply only when current Runtime `modelHash == baseModelHash`.

Otherwise Apply returns `409 CHANGESET_STALE`. Caller must re-propose against the new model.

### 21.4 Risk

Single Risk Level:

`SAFE < DATA_REWRITE < DESTRUCTIVE < IRREVERSIBLE`

ChangeSet aggregate Risk is the maximum operation risk.

Impact flags include at minimum where applicable:

- `requiresBackfill`;
- `dropsData`;
- `changesCardinality`;
- `expandsAccess`;
- `requiresCheckpoint`.

A Policy change that expands access can remain data-level `SAFE` but carries `expandsAccess=true` and still requires explicit confirmation.

### 21.5 Confirmation

Automatic Apply is allowed only when:

- Risk is `SAFE`;
- `expandsAccess` is false;
- caller has all required scopes.

DATA_REWRITE, DESTRUCTIVE, IRREVERSIBLE or access-expanding changes require explicit Apply confirmation containing current ChangeSet ID and accepted computed Risk.

DESTRUCTIVE/IRREVERSIBLE also require a successful checkpoint before DB mutation.

## 22. Diff

Diff is a stable machine-readable structure, not only formatted text.

For each operation it records affected object stable IDs and relevant before/after values. Human-readable summaries are generated from this structured Diff.

Diff has identical semantic content whether ChangeSet was proposed from Admin, CLI or MCP.

## 23. Project Migration Artifact

### 23.1 Format and Naming

Project Migration is immutable declarative JSON.

Filename uses collision-resistant sortable identity:

`<UTC timestamp>_<short-id>_<slug>.json`

Example filename shape:

`20260902T054500Z_a1b2c3d4_add_priority.json`

Ordering is validated using artifact identity and `beforeModelHash`, not trusted from filename order alone.

### 23.2 Required Artifact Data

- migration ID;
- originating ChangeSet ID when generated from Control Plane;
- creation timestamp and source Principal metadata;
- `beforeModelHash`;
- `afterModelHash`;
- typed operations;
- computed Risk + impact flags;
- Preconditions;
- artifact format version;
- content hash.

No raw SQL or arbitrary TypeScript `up()` is accepted as a Project Schema Migration.

### 23.3 Apply Ordering and Crash Safety

For a ChangeSet-generated migration:

1. validate scopes and stale base;
2. calculate Diff/Risk/Preconditions;
3. obtain required confirmation;
4. generate immutable Migration Artifact;
5. durably write Artifact to Project Source or internal Generated Artifact Store before Runtime schema commit;
6. create required checkpoint;
7. execute SQLite schema/data rewrite + Runtime Backend Model update + Migration Ledger + required Audit Fact in one logical transactional Apply;
8. commit;
9. generate Schema Snapshot to Project Source or internal export store.

If Runtime crashes after Artifact write but before DB commit, the Artifact is simply unapplied; Apply can be retried after normal validation.

If Snapshot generation/export fails after DB commit, Runtime Backend Model remains authoritative and status reports the generated artifact state explicitly.

### 23.4 Read-only Project Source

When Project Source is not writable:

- Runtime persists the complete Migration Artifact bytes, filename, content hash and generated Snapshot bytes in an internal **Generated Artifact Store** before/around Apply as required by crash-safety ordering;
- Project Migration Ledger marks the applied artifact `exportState=pending`;
- Runtime may continue serving because the exact durable Artifact is known, rather than treating the state as unexplained Runtime-ahead drift;
- status/doctor expose `UNEXPORTED_ARTIFACTS`;
- subsequent model changes may proceed, but every generated artifact remains ordered and independently exportable;
- `modelry migrate --export <dir>` or equivalent Control Plane export writes all pending artifacts without re-applying them.

If Runtime is ahead of Project Source **without** a matching durable internal generated artifact, that state is HARD_DRIFT.

A successful model mutation may never exist without either the Git-workspace Artifact or its exact durable internal equivalent.

## 24. Migration Operation Baseline

V0.1.0 typed operations:

- `collection.create`
- `collection.rename`
- `collection.drop`
- `field.add`
- `field.rename`
- `field.drop`
- `field.type_change`
- `index.create`
- `index.drop`
- `policy.update`
- `collection.option.update`
- `relation.cardinality_change`
- `auth.config.update`

### 24.1 Risk Defaults

- create Collection: SAFE;
- rename Collection/Field: SAFE after reference validation;
- add optional Field: SAFE;
- add required Field with complete literal default/backfill: DATA_REWRITE;
- drop Field/Collection: IRREVERSIBLE and `dropsData=true`;

### 24.2 Supported Type Changes

- integer -> number;
- integer -> decimal with scale 0;
- email -> text;
- url -> text;
- select(single) -> text;
- text -> email when every non-null value passes email validation;
- text -> url when every non-null value passes URL validation;
- date -> datetime by UTC midnight normalization.

All other type changes return `UNSUPPORTED_TYPE_CONVERSION` in V0.1.0. No silent truncation/coercion is allowed.

## 25. Migration Checkpoint

Public Backup/Restore UI is V0.1.x, but V0.1.0 requires an internal recovery checkpoint for DESTRUCTIVE/IRREVERSIBLE migrations.

Checkpoint uses SQLite’s consistent backup mechanism and records:

- source DB model hash;
- migration/ChangeSet identity;
- creation time;
- local file manifest needed to understand File references.

Schema migration must not immediately physically delete committed file objects; file cleanup is asynchronous, so DB checkpoint remains useful for rollback/recovery.

V0.1.0 does not promise an automatic universal down migration. Recovery is checkpoint + forward-fix oriented.

## 26. Drift and Startup State

### 26.1 States

Runtime classifies Project startup as:

- `READY` — Project Source history, ledger, Runtime Backend Model and Snapshot agree;
- `PENDING_MIGRATIONS` — valid Project Migration files exist beyond Runtime ledger;
- `UNEXPORTED_ARTIFACTS` — Runtime contains applied migrations with exact durable internal Artifacts pending export to Project Source;
- `SNAPSHOT_STALE` — authoritative history/runtime agree but generated Snapshot differs/missing;
- `HARD_DRIFT` — applied artifact changed/missing without durable internal equivalent, unexplained Runtime-ahead state, ledger/model mismatch, divergent hash chain or incompatible history.

### 26.2 Behavior

- `SNAPSHOT_STALE`: Runtime may regenerate/export Snapshot and continue.
- `UNEXPORTED_ARTIFACTS`: Runtime continues serving with an explicit warning; additional generated artifacts remain durably queued for export.
- `PENDING_MIGRATIONS`: Control Plane/diagnostics start, Data Plane returns `503 MIGRATION_PENDING` until explicit migrate completes.
- `HARD_DRIFT`: Runtime enters diagnostic-safe mode; Data Plane is unavailable and model/data mutations are blocked.

`serve` does **not** silently auto-apply Project Migrations in V0.1.0.

`modelry migrate` or an authorized Control Plane Apply is explicit.

## 29. Transactional Outbox / Durable Work

V0.1.0 does not ship Webhook or Event Hook delivery, but it requires a minimal production durable-work primitive because File object deletion is an external filesystem side effect.

When a committed File becomes orphaned through Record update/hard cleanup:

1. business/file-reference transaction records an idempotent `file.object.delete` durable work item;
2. transaction commits;
3. post-commit worker performs Local Storage deletion;
4. success/failure/attempt state is persisted;
5. process crash before deletion resumes the pending item after restart.

Soft delete does not physically orphan the File while the soft-deleted Record still retains its File reference.

This is the V0.1.0 production consumer proving the ADR-0010 transaction boundary without prematurely implementing Webhook/Event Hook.

Delivery semantics are at-least-once; Local delete handler must be idempotent.

## 30. File and Upload Session

### 30.1 Upload Flow

1. Authenticated Data Plane caller requests an Upload Session for a target Collection/File Field with filename, MIME and declared size.
2. Runtime validates Field existence and size/MIME constraints.
3. Caller uploads bytes to the Local Storage upload endpoint.
4. Runtime verifies actual size, computes SHA-256 and marks Upload Session `uploaded`.
5. Record create/update refers to the Upload Session ID.
6. Successful Record transaction binds File metadata to Record/Field and marks it committed.
7. Failed Record mutation leaves upload temporary.

Default Upload Session expiry: **1 hour**.

### 30.2 Storage Key

Physical object key is generated from an opaque File ID, never from untrusted original filename.

Metadata stores original filename, MIME, byte size, SHA-256 and created timestamp.

Binding a previously uploaded object is a metadata state transition; Runtime does not require a non-transactional filesystem move to make the Record mutation valid.

### 30.3 Download

`GET /api/v1/files/:fileId` resolves owning Record/Field and evaluates target Record `view` Policy before serving content.

Temporary/unbound files are not publicly downloadable through this route.

### 30.4 Cleanup

Expired temporary uploads are deleted by basic background GC. Full GC administration UI is V0.1.x.

Committed orphan cleanup goes through durable work after DB commit.

## 31. SSE Realtime

### 31.1 Contract

SSE is a Data Plane best-effort live projection, not a durable queue.

Subscription endpoint is versioned under `/api/v1/realtime` and accepts:

- Collection selection;
- optional Expression Engine subscription filter;
- standard `Last-Event-ID` header for same-process replay when available.

### 31.2 Event Projection

For Record mutations:

- create: emit when `after` passes view Policy + subscription filter;
- update visible -> visible: emit `record.updated`;
- update invisible -> visible: emit `record.created` projection;
- update visible -> invisible/filter-miss: emit `record.removed` containing Collection + Record ID only;
- delete: when `before` was visible and matched, emit `record.deleted` containing Collection + Record ID only.

For visibility/filter transition decisions, dispatcher evaluates `before` against prior visibility/filter and `after` against current visibility/filter.

`record.removed` is a Realtime projection event, not a claim that the underlying Domain Record was deleted.

### 31.3 Replay Boundary

Runtime keeps a bounded in-memory replay ring, default **1000 events**.

If `Last-Event-ID` is no longer available or Runtime restarted, server emits a `modelry.reset` control event and client must refetch current state.

Persistent cross-restart event replay is explicitly out of scope.

## 32. Lifecycle Hook

### 32.1 V0.1.0 Events

- `record.beforeCreate`
- `record.beforeUpdate`
- `record.beforeDelete`

Auth Collection Record mutations use the same Record lifecycle hooks.

### 32.2 Registration

Hook source lives under `.modelry/hooks/`.

`modelry.config.json` contains explicit Hook registration metadata:

- stable Hook ID;
- lifecycle event;
- target Collection;
- module path relative to Project;
- exported handler name;
- enabled state;
- execution order;
- timeout.

Multiple Hooks execute sequentially by order then stable Hook ID.

### 32.3 Handler Context

Lifecycle Hook receives bounded context containing:

- lifecycle event;
- `before` / candidate `after` as applicable;
- current Auth Principal context when mutation came from Data Plane;
- request ID;
- read-only project metadata;
- controlled Secret getter.

V0.1.0 does not expose raw SQLite handles through supported Hook API.

Lifecycle Hook is for deterministic local validation/field mutation. It must not be used for email, payment or external HTTP side effects.

Because Hook is Trusted Project Code rather than a security Sandbox, Runtime documents this rule but does not claim to prevent every possible filesystem/network call from malicious code.

### 32.4 Return / Failure

Create/Update Hook may return a candidate patch. Delete Hook may allow or throw.

After Hook mutation, Runtime reruns type/validation and required final Policy check before persistence.

Throw/rejection/timeout aborts business mutation and returns a structured Hook error.

Default Hook timeout: **2 seconds**; configurable per Hook from 50 ms to 10 seconds.

### 32.5 Reload State

Runtime watches referenced Hook source and forms a candidate generation on change.

Required semantics:

- invocation binds one immutable active generation at start;
- successful reload affects only new invocations;
- syntax/import/load failure does not replace last-known-good generation;
- reload success/failure is observable and audited;
- runaway invocation can be terminated without terminating Core Runtime.

Exact snapshot/cache implementation is internal and must not copy the Spike Prototype merely because it used generation snapshots.

### 32.6 Dependency Boundary

V0.1.0 guarantees:

- TypeScript source;
- relative imports within Project Hook source;
- Modelry Hook API supplied by Runtime.

Arbitrary npm dependency installation/resolution is not a V0.1.0 compatibility promise. Modelry does not run `bun install` automatically for a deployed Project.

## 41. Config ChangeSet

Runtime Config is not Backend Model and does not generate a Project Schema Migration.

Admin/MCP-managed config mutations use ChangeSet `kind=config` and require `config:write`.

Apply semantics are recoverable across the SQLite/file boundary:

1. build candidate config and validate the complete config before mutation;
2. create a temporary file in the same filesystem and fsync/close it;
3. persist a Config Apply journal record containing ChangeSet ID, old hash and candidate hash;
4. atomically replace `modelry.config.json` with the validated candidate;
5. load/switch Runtime config;
6. finalize ChangeSet/Audit and clear the pending journal.

On restart with a pending journal, Runtime compares current config hash with old/candidate hashes and deterministically finalizes or rolls back the journal state before normal serving. Any unexplained third hash causes diagnostic-safe `CONFIG_APPLY_RECOVERY_REQUIRED`.

Config ChangeSet Apply is rejected with `PROJECT_SOURCE_READ_ONLY` if `modelry.config.json` cannot be atomically replaced. Unlike Project Migration, V0.1.0 does not support an applied-but-unexported Runtime Config state.

`hook_change_propose` is a typed config ChangeSet over Hook registration metadata; it does not write arbitrary Hook source code.

Coding Agents edit Hook source through normal repository coding tools, not through an unrestricted Modelry MCP filesystem tool.

## 42. Security Boundaries

V0.1.0 enforces:

1. Control Plane and Data Plane authentication/authorization are separate.
2. Agent API Key cannot become `auth.id`.
3. Admin/Agent administrative data bypass of Record Policy is explicit, scoped and audited.
4. Password/API Key/Session/Secret plaintext is never returned by Inspect endpoints.
5. Lifecycle Hook receives no raw DB handle through supported Modelry API.
6. Modelry does not claim Lifecycle Hook is malicious-code sandboxed.
7. Data API relation writes cannot use forbidden target existence as an oracle.
8. Model/schema mutations cannot bypass ChangeSet/Migration.
9. Applied Migration Artifact hash changes without exact internal equivalent cause hard Drift.
10. Destructive/irreversible migration cannot silently auto-apply.
11. Access and Runtime Config management use explicit `access:manage` / `config:write`, not unrelated model scopes.

Rate limiting, WAF and internet-facing abuse prevention are deployment concerns outside V0.1.0 core unless needed by a specific auth endpoint test; they are not a substitute for the above invariants.

## 43. Testing Strategy

### 43.1 Highest-tier seams

Production acceptance tests prefer real public seams:

1. compiled standalone executable in a temporary Project directory;
2. real SQLite database, not mocked DB adapter;
3. real HTTP Data Plane / Control Plane requests;
4. CLI subprocess invocation;
5. official MCP TypeScript client over stdio into `modelry mcp`;

### 43.2 Unit-test seams

- Policy operation matrix;
- ChangeSet Diff/Risk aggregation;
- Migration planner/preconditions/type-conversion matrix;
- canonical Backend Model hashing;
- Config Apply journal reconciliation state machine.

Do not introduce internal mock interfaces only to make unit tests easier.

### 43.3 CI matrix

**Linux x64**

- full typecheck/lint/test;
- compiled executable E2E;
- Admin browser E2E;
- MCP E2E;
- migration/drift/export/hook/file/realtime acceptance.

**Windows x64**

- install/build;
- standalone executable start/stop;
- SQLite persistence smoke;
- embedded Admin asset smoke;
- minimal HTTP + MCP/Hook smoke.

macOS is not a V0.1.0 release gate.

### 43.4 Required failure tests

At minimum:

- Policy deny/no existence leak;
- Update before/after boundary crossing;
- Relation Expand target deny;
- Realtime visible -> invisible removal;
- stale optimistic lock;
- stale ChangeSet;
- unique-index precondition failure;
- unsupported type change;
- destructive migration without confirmation;
- Artifact written but DB Apply interrupted;
- read-only Project Source with valid unexported artifact remains distinguishable from HARD_DRIFT;
- Runtime-ahead with no durable artifact is HARD_DRIFT;
- stale/corrupt Snapshot;
- applied migration file modified;
- Hook throw/rejection/timeout/runaway;
- invalid Hook reload preserves last-known-good;
- Runtime crash with pending durable file-delete job;
- revoked Access/Refresh Session;
- revoked Agent API Key;
- Secret list never returns plaintext;
- every Administrative Data Access request audited;
- Config Apply crash before/after atomic file replace recovers deterministically;
- unauthorized `access:manage` / `config:write` actions denied.

## 44. V0.1.0 Acceptance Demo — Notes

The final release gate uses one real Notes application.

### 44.1 Model

Auth Collection `users`:

- email login;
- password credential.

Normal Collection `notes`:

- `title`: text required;
- `body`: text;
- `status`: select(`draft`, `published`);
- `owner`: relation(one) -> users, required;
- `attachment`: file(single);
- optimistic locking enabled.

### 44.2 Policy

Notes policies demonstrate owner-only data access using `owner.id == auth.id`.

Acceptance proves another user cannot list/view/update/delete or expand a forbidden note.

### 44.3 Hook

`beforeCreate` deterministically normalizes title and/or populates a documented local field. It performs no external side effect.

Acceptance includes successful reload and invalid-reload last-known-good behavior.

### 44.4 Realtime

Two authenticated clients demonstrate:

- owner receives note create/update;
- unauthorized user receives nothing;
- visibility transition produces removal/reset behavior without leaking record body.

### 44.5 File

Owner uploads and attaches one file; authorized download succeeds; other user download is non-leaking denied.

### 44.6 Agent Change

A Coding Agent through MCP:

1. reads current schema;
2. proposes adding optional `priority` select Field to `notes`;
3. receives ChangeSet + Diff + SAFE Risk;
4. applies with allowed scope;
5. Runtime Backend Model changes;
6. Migration Artifact appears in `.modelry/migrations/` or exact generated-artifact export state when Project Source is intentionally read-only;
7. Schema Snapshot updates/exports;
8. Git diff shows the exported migration/snapshot artifacts;
9. Audit identifies Agent Principal and ChangeSet/Migration.

A second Agent lacking `changeset:apply` can propose but cannot apply.

### 44.7 Drift / Doctor

Acceptance intentionally modifies an already-applied migration copy or otherwise creates a hard Drift fixture; `doctor` and Runtime Status detect it, and normal Data Plane serving is blocked until restored.

A separate read-only fixture proves a valid internally persisted unexported Artifact is a warning/export state, not unexplained hard Drift.

## 45. Performance / Resource Boundaries

V0.1.0 is a single-node application backend, not an analytics engine.

Required protective limits:

- list `perPage <= 100`;
- Relation Expand depth <= 2;
- non-file request body default <= 1 MiB;
- Hook timeout bounded;
- Upload size bounded by File Field;
- SSE replay ring bounded;
- no cross-request open transaction API.

No headline throughput/latency benchmark is a V0.1.0 release claim. Performance regressions that make the Notes acceptance scenario unusable are blocking; synthetic scale targets are not invented in this Spec.
