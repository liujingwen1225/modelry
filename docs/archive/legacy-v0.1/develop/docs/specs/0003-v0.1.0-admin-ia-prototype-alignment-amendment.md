# Spec 0003：V0.1.0 Admin IA Prototype Alignment Amendment

- **Status:** Normative — Accepted
- **Date:** 2026-09-04
- **Applies to:**
  - `docs/01-v0.1-scope.md`
  - `docs/02-product-business-design.md`
  - `docs/specs/0001-v0.1.0-core-technical-spec.md`
  - `docs/specs/0002-v0.1.0-business-baseline-alignment-amendment.md`
- **UX Reference:** `prototypes/admin-core-ui/index-v4-industrial.html`

> 本 Amendment 将已经确认的 V4 Admin 原型信息架构正式回写为 V0.1 Admin IA / UX 基线。若既有 Spec 对 Admin 页面层级、API Explorer 位置或 Access/Audit 页面职责的描述与本文件冲突，以本文件为准。

## 1. 目的

V0.1 的 Data Plane、OpenAPI、Auth API、Realtime 与后续 Custom API 能力没有因为本次调整而改变。本次只收口 Admin 信息架构与任务入口，避免实现阶段继续沿用早期“Project-wide API 一级页面”的设计。

已经确认的产品体验优先级继续保持：

```text
Data Usage -> API Usage -> Backend Modeling -> Change Management -> Operations
```

这里的 `API Usage` 表示核心产品体验，不要求 API 成为独立一级导航。

---

## 2. V0.1 Admin 一级信息架构

V0.1 Admin 一级入口固定为 7 个：

```text
Core
  Overview
  Collections

Governance & Security
  Changes
  Hooks & Events
  Access & Audit

Project
  Project Settings
  Activity
```

不新增顶层 `Data`，也不设置独立顶层 `API`。

本节覆盖 Spec 0002 第 7 节及其 Acceptance Override 中“API 是 Project-wide Explorer”的要求，也覆盖其他 Spec 中与上述一级 IA 冲突的 Admin 页面描述。

---

## 3. Collection 是 Data、API 与 Model 的共同工作入口

Developer 进入 `Collections -> Collection` 后，默认进入 `Records`。

单个 Collection 的二级能力固定为：

```text
Records       <- default
Schema
Relations
Indexes
Policy
Auth          <- Auth Collection only
API
```

其中：

- `Records` 是日常 Data Usage 工作面；
- `API` 是当前 Collection 的 API Usage 工作面；
- `Schema / Relations / Indexes / Policy / Auth` 是 Backend Modeling / Governance 工作面；
- `Auth` 仅对 Auth Collection 显示；
- `API` 不再跳转到独立 Project-wide API 页面。

Records、API 与模型能力必须保持 Collection 上下文连续，不形成三个相互割裂的信息岛。

---

## 4. API Admin 体验

### 4.1 Collection API

Admin 中的 API Explorer 归属于具体 Collection。

它至少可以呈现与该 Collection 直接相关的：

- Data API；
- OpenAPI Contract；
- Realtime 使用方式；
- Auth Collection 对应的 Auth API（适用时）。

Developer 从当前 Collection 查看 API 时，应保持 Collection context，不要求先进入 Project-wide API Hub。

### 4.2 Project-wide Contract 不等于 Project-wide Admin 页面

Modelry 仍可以生成 Project 级 OpenAPI 3.1 文档、机器可读 Backend Contract 或供 Agent/SDK 使用的统一接口描述。

这些机器接口的 Project-wide 性质，不推导出 Admin 必须存在一个 Project-wide API 一级页面。

### 4.3 Custom API

Custom API 完整产品化仍属于 V0.1.x，且 V0.1.0 不要求 Custom API Admin UI。

未来 Custom API 的具体 Admin 入口不由本 Amendment 提前固定；不得仅因为 Custom API 是 Project-level capability 就自动恢复独立顶层 `API` 页面。若需要改变一级 IA，应新增明确产品决策。

---

## 5. Access & Audit 与 Activity 职责

### 5.1 Access & Audit

回答：

> 谁能够管理这个 Backend、拥有何种能力，以及关键管理访问是否可追溯？

聚焦：

- Admin Principal；
- Agent / Service Principal；
- Credential / API Key；
- Capability Scope；
- 与管理访问、权限变化、关键 Control Plane 操作直接相关的 Audit Fact。

业务 Auth Collection User 仍通过 Collection 管理，不进入 Control Plane Access。

### 5.2 Activity

回答：

> Project 最近发生了什么，运行或异步执行哪里出现异常？

聚焦跨模块时间线与 Operations 事实，例如：

- Runtime 状态变化；
- Migration / Apply 结果；
- Hook Error；
- Delivery / Webhook 状态；
- 其他 Recent Activity。

Activity 可以深链到对应 Audit Fact，但不复制完整 Access 管理模型。

本节只定义 Admin 页面职责，不改变 `Audit` 的领域语义或持久化要求。

---

## 6. Accepted Prototype 的地位

`prototypes/admin-core-ui/index-v4-industrial.html` 是 V0.1 Admin 的 **Accepted IA / Interaction / Visual Reference**。

其含义是：

- 一级导航与页面分组作为后续前端实现基线；
- Collections master-detail、Collection 默认 Records、Collection API、Changes 审核方式等核心交互作为实现参考；
- 视觉方向作为正式 Admin 设计输入；
- Prototype HTML/CSS/JS 仍是 throwaway implementation，不具备生产代码继承权；
- Prototype 中用于探索的 Agent Copilot / 自由输入等 affordance 不自动扩大 V0.1 Feature Scope，正式能力仍受 `docs/01-v0.1-scope.md` 约束。

原型尚未完整实现的 `Indexes`、Auth Collection `Auth` 以及其他占位页面，应在后续 Frontend Completion 中按本 Amendment 补齐，而不是借机重新设计一级 IA。

---

## 7. Prototype Fixture 与 Reference Application

V4 Prototype 当前使用电商 fixture，例如：

```text
orders
customers
products
refund_requests
```

这些数据只用于验证 Admin 页面密度、Records、Relation、ChangeSet 与 API 交互。

V0.1 正式 E2E Reference Application 继续固定为 Blog：

```text
users       (Auth Collection)
posts
comments
categories
```

Prototype Fixture 的变化不构成 Reference Application 产品决策。

---

## 8. Acceptance Override

进入 Frontend Completion / implementation tickets 前，Admin 相关要求以以下结论验收：

1. 一级导航不包含 `Data`；
2. 一级导航不包含独立 `API`；
3. `Collections -> Collection -> Records` 是默认工作路径；
4. `API` 是 Collection 二级能力并保持 Collection context；
5. Collection 二级 IA 包含 `Records / Schema / Relations / Indexes / Policy / Auth(conditional) / API`；
6. Governance 使用 `Access & Audit`，Activity 保持独立 Operations 时间线职责；
7. V4 Accepted Prototype 是 Admin IA / Interaction / Visual Reference；
8. Prototype affordance 不自动扩大 V0.1 Feature Scope；
9. 电商 Prototype Fixture 不替代 Blog E2E Reference Application。

**Result: PASS — V0.1 Admin IA 已收口，可进入 Frontend Completion。**
