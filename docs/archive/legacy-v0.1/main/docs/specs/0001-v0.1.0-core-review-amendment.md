## 2. `modelHash` Canonicalization

主 Spec 8.1 中的 `modelHash` 是 **derived metadata**，不能参与自身 hash 输入。

V0.1.0 固定以下语义：

- `modelHash = SHA-256(canonicalSemanticModelPayload)`；
- canonical payload 只包含影响 Backend Model 业务语义的内容；
- 明确排除：
  - `modelHash` 自身；
  - `modelRevision`；
  - generated timestamp；
  - Runtime-only status；
  - Migration Ledger 执行时间等非模型元数据；
- stable IDs、名称、Field/Relation/Index/Policy/Auth Collection 配置、validation/default、Collection options 等语义内容必须参与 hash；
- JSON object key 使用确定性排序；
- 对语义上属于有序列表的结构保持规范顺序；对语义上无序的集合必须先按 stable ID/规范 key 排序后再编码；
- string/number/boolean/null 的 canonical encoding 必须跨 Linux/Windows 一致。

因此：

- 单纯 Runtime 重启不能改变 `modelHash`；
- 单纯 `modelRevision` 增长不能改变相同语义模型的 `modelHash`；
- Rename 因名称发生语义变化会改变 hash，但 stable ID 保持不变；
- Snapshot、ChangeSet stale detection、Migration before/after hash 全部复用同一 canonicalization implementation，不允许分别实现三套 hash 规则。

## 3. Required 与 Container Field 语义

主 Spec 9.1 的 `required` 对各 Field 类型固定为：

- scalar Field：值不得为 `null`/missing；
- relation(one)：必须存在一个 target ID；
- relation(many)：集合至少包含 1 个 target；
- file(single)：必须绑定 1 个 committed File Reference；
- file(multiple)：至少绑定 1 个 committed File Reference；
- select(single)：必须有一个合法 option；
- select(multiple)：至少有一个合法 option；
- json：`null` 是否允许由 `required` 决定；required json 不允许 JSON `null`。

空字符串不是通用的“missing”替代值；是否允许空字符串由 text/email/url/select 的类型与 validation 规则决定。

### 3.1 Relation `onDelete`

为避免 `required` 与 `setNull` 自相矛盾：

- relation(one) + `required=true`：只允许 `onDelete=restrict`；
- relation(one) + `required=false`：允许 `restrict | setNull`；
- relation(many) 的 `setNull` 语义仍是从集合移除被删除 target；
- relation(many) + `required=true` 时，如果移除后集合将为空，则 target delete 被阻止，等价于对该 referencing Record 执行 `restrict`；
- Backend Model validation 在 ChangeSet propose/apply 前拒绝非法组合，而不是等到数据库执行阶段失败。

Relation 写入中“target 不存在”和“target 存在但当前 Auth Principal 不可 view”对 Data Plane 返回同一类非泄漏 validation failure，不得通过错误码、message 或 timing contract 暴露目标是否存在。

## 4. Auth Registration Pipeline

Auth Collection `register` 是 Data Plane 的显式创建路径，**不能成为绕过 Collection create Policy 的旁路**。

`POST /api/v1/auth/:collection/register` 固定执行：

1. 确认目标是 Auth Collection 且 `registrationEnabled=true`；
2. 解析 Record candidate 与独立 Password Credential 输入；
3. 执行基础 Field/type validation；
4. 执行 `record.beforeCreate` Lifecycle Hook；
5. 对 Hook 后 candidate 再执行完整 validation；
6. 以当前请求 Auth context（未登录注册时 `auth.id=null`）执行目标 Auth Collection 的 `create` Record Policy；
7. 计算并校验 normalized login identity uniqueness；
8. 在同一逻辑事务中创建 Auth Record、Auth Principal、identity mapping 与 Password Credential；
9. 成功返回安全的 created identity/record metadata，不返回 Password/hash。

V0.1.0 **注册成功不隐式创建 Session**。客户端随后调用 `login` 获取 Access/Refresh Session。这样 Register 与 Login 是两个明确、可审计的认证状态转换。

`registrationEnabled=true` 只是额外产品 Gate，不替代 Record `create` Policy。

Login 的内部 normalized identity lookup 继续不要求业务 Record `view` Policy；登录成功后的 Data Plane Record 访问仍完整经过 Record Policy。

## 5. ChangeSet State 与 Staleness

### 5.1 State Machine

V0.1.0 ChangeSet 的持久状态扩展为：

- `proposed`；
- `applying`；
- `applied`；
- `cancelled`；
- `failed`。

合法转换：

```text
proposed -> cancelled
proposed -> applying
applying -> applied
applying -> failed
```

`applied` / `cancelled` / `failed` 是 terminal state。

`applying` 是**恢复状态**，不是 UI 上的长期业务队列状态。它用于跨 Project Source 文件写入、Checkpoint 与 SQLite Apply 的 crash recovery。

若 Apply 在进入 `applying` 之前因 scope、stale、confirmation 或 precondition 失败，请求失败但 ChangeSet 仍保持 `proposed`；调用者可以修复前置条件后重新请求 Apply。

只有已经进入 `applying` 后发生且无法安全自动恢复的执行失败，才进入 terminal `failed`。

### 5.2 Model / Config Stale Detection

- model ChangeSet 必须记录 `baseModelHash`；
- config ChangeSet 必须记录 `baseConfigHash`；
- Apply 时分别要求当前 hash 与 base hash 完全一致；
- 不一致统一返回 `409 CHANGESET_STALE`，不得用旧 Config ChangeSet 覆盖后续 Config 变更。

Config canonical hash 对完整声明式 `modelry.config.json` 的规范化内容计算，排除纯格式差异，但不排除任何具有 Runtime 语义的配置值。

### 5.3 Policy Access-impact

V0.1.0 **不实现 Policy 逻辑蕴含/权限集合差异证明器**。

为了避免实现者自行猜测 `expandsAccess`：

- 任意有效的 `policy.update` 默认设置 `expandsAccess=true`；
- 因此任意 Policy 语义修改都需要显式 Apply confirmation；
- byte-for-byte/canonical semantic no-op 不生成 `policy.update` operation；
- `auth.config.update` 若开启 Registration 或扩大可登录标识能力，也设置 `expandsAccess=true`；
- 未来版本可以引入可证明的 access-diff engine 后再缩小确认范围，但 V0.1.0 不做启发式“看起来更严格”的自动判断。

该规则只影响确认要求，不把 Policy change 错误归类成数据破坏性 Migration。

## 6. Migration Artifact Identity、Retry 与 Risk Revalidation

### 6.1 Apply Plan Reservation

model ChangeSet 从 `proposed -> applying` 时，Runtime 必须一次性持久化 immutable Apply Plan，至少包含：

- ChangeSet ID；
- reserved Migration ID；
- reserved Artifact filename；
- exact Artifact bytes/content hash；
- `beforeModelHash` / `afterModelHash`；
- typed operations；
- computed Risk / impact flags；
- evaluated Preconditions summary；
- required checkpoint identity when applicable。

随后所有 retry/recovery **复用同一 Migration ID、filename 与 exact Artifact bytes**。

禁止因为进程重启或 Apply retry 为同一个 ChangeSet 生成第二个 Migration Artifact。

### 6.2 Crash Recovery

关键状态：

- `applying` + Artifact 尚未落盘：按 reserved exact bytes 重试原子写入；
- `applying` + Artifact 已存在且 hash 匹配 + Ledger 未 Apply：复用该 Artifact 继续 checkpoint/SQLite Apply；
- `applying` + 同名 Artifact 存在但 hash 不匹配：进入 diagnostic-safe failure，禁止覆盖；
- Ledger 已记录 Migration applied 时，ChangeSet 必须已经在同一 Runtime transaction 中成为 `applied`，不得存在“Ledger applied 但 ChangeSet 仍 proposed”的正常状态。

如果 Project Source 中出现一个来自 ChangeSet Apply Plan、尚未进入 Ledger 的 valid Artifact，`modelry migrate` 可以继续应用它；若 Artifact 包含 originating ChangeSet ID，成功事务同时将该 ChangeSet 完成到 `applied`。

### 6.3 Project Migration Risk 不能信任 Artifact 声明

Project Migration Artifact 中的 Risk/impact 是生成时历史事实，但 Apply Runtime 不能把它当作唯一授权依据。

对任何尚未 Apply 的 Project Migration：

1. 重新验证 operation schema 与 `beforeModelHash`；
2. 基于当前 Runtime 数据重新执行 Preconditions；
3. 基于当前 Runtime 版本重新计算 Risk/impact；
4. `effectiveRisk = max(artifactDeclaredRisk, recomputedRisk)`；
5. confirmation/checkpoint 依据 `effectiveRisk`；
6. 任何新发现的 precondition failure 在数据库变更前终止。

Runtime 不允许一个手工编辑或旧版本生成、但宣称 `SAFE` 的 Artifact 降低当前执行器实际识别出的风险。

Applied Artifact 仍由 content hash immutability 保护；对已 Apply 文件的修改继续属于 HARD_DRIFT。

## 7. Domain Event 统一语义骨干

主 Spec 29 的 Durable Work 只是 V0.1.0 首个可靠消费者，不能让 Realtime、Audit 与未来 Event Hook/Webhook 各自重新解释数据库状态。

V0.1 固定一个内部 Domain Event semantic envelope。每次成功业务 Mutation 在 application-service 边界只构造一次语义事件，至少具有：

- stable event ID；
- event type；
- occurred-at timestamp；
- aggregate/Collection stable ID；
- Record ID；
- source Principal type/ID when known；
- request ID when request-driven；
- mutation before/after context sufficient for policy/realtime projection；
- related durable-work/audit correlation IDs where applicable。

### 7.1 V0.1.0 Dispatch

顺序固定：

```text
Validation / Policy / Lifecycle Hook
        ↓
BEGIN SQLite Transaction
  ├─ Business Mutation
  ├─ Required Audit Fact（如该操作要求）
  ├─ Durable Work Task（如存在可靠提交后工作）
  └─ Domain Event durable fact（仅当可靠 consumer 需要持久化事件本身）
COMMIT
        ↓
Post-commit Domain Event Dispatch
  ├─ Realtime best-effort projection
  └─ Durable Work worker wake-up
```

Realtime 读取的是这一个 Mutation Domain Event 的 post-commit projection，不允许另起数据库 watcher 再推断“发生了什么”。

V0.1.0 不要求为了纯 Realtime 永久保存所有 Record Domain Event；如果没有任何可靠 consumer 需要事件 payload，本次 event 可以只在 transaction/app-service 生命周期与 bounded replay ring 中存在。

### 7.2 V0.1.x Compatibility

Event Hook/Webhook 后续加入时：

- 继续消费同一 Domain Event type/envelope；
- reliable Event Hook/Webhook 的 Durable Event Fact/Delivery Task 与业务 Mutation 同事务写入；
- at-least-once delivery；
- stable Event/Delivery ID；
- retry/backoff/max-attempt/final-failure 可查询；
- 不允许通过独立 DB polling 重新定义另一套 event semantics。

因此 V0.1.0 的内部 event type、ID/correlation 与 commit boundary 不能设计成只服务 SSE 的临时格式。

## 8. Custom API Route Contract Compatibility Boundary

Custom API 完整产品化仍属于 **V0.1.x**；V0.1.0 不实现 Custom API runtime registration、UI 或 MCP mutation tool。

但为满足 ADR-0013 与防止 V0.1.0 架构把未来 Custom API 逼成 Router 黑盒，V0.1 的 Route Contract 固定如下。

### 8.1 TypeScript Definition

Custom API 使用 Modelry 提供的 typed `defineRoute(...)` contract，概念字段固定为：

- stable `operationId`；
- HTTP `method`；
- relative `path`；
- `auth` requirement；
- input schemas：path/query/header/body；
- success response schema；
- declared error response schemas/status；
- handler reference。

Handler 不是 Contract 本身；Runtime/Agent/OpenAPI 不从任意 Handler 源码反向猜测契约。

### 8.2 Schema Representation

Route Contract schema 使用 **JSON Schema 2020-12 compatible TypeBox schema** 作为 TypeScript authoring model：

- static TypeScript type 与 runtime schema 来自同一 TypeBox definition；
- Runtime validation 与 OpenAPI mapping消费同一 schema object；
- Contract 只接受能稳定映射到 JSON Schema/OpenAPI 3.1 的 JSON-compatible types；
- TypeBox 的 JavaScript-only/不可 OpenAPI 表达扩展类型不属于公共 Route Contract；
- 具体 package version 在实现 Ticket 中 pin，但不允许替换成需要维护第二套 runtime/documentation schema 的方案。

当前 TypeBox 官方实现以 JSON Schema type builder + TypeScript static type resolution 为核心，并提供 JSON Schema 2020-12 的 runtime validation 能力；该方向与 OpenAPI 3.1 schema 兼容目标一致。

### 8.3 Namespace / Conflict

Custom API public path 固定在：

`/api/v1/custom/*`

`defineRoute.path` 是该 prefix 下的相对路径。

因此 Custom API 不允许覆盖 Collection/Auth/File/Realtime/OpenAPI/Control Plane/Admin 等系统路由。

同 method + normalized path 冲突在 Route generation/load 阶段确定性失败；禁止“最后注册覆盖前一个”。

### 8.4 Auth / Principal / Policy

Data Plane Custom API `auth` 至少区分：

- `public`；
- `optional`；
- `required`。

Handler context 得到真实 Auth Principal context（或 null），不能得到伪造 Admin/Agent `auth.id`。

Handler 若访问业务 Record，只能通过受控 Runtime Record API，并继续执行当前 Auth Principal 的 Record Policy。

管理型能力不得伪装成 Data Plane Custom API；需要管理能力的扩展必须进入明确的 Control Plane extension boundary 并执行 Capability Scope。

### 8.5 Validation / Error / OpenAPI / Agent Inspect

- request path/query/header/body 在 Handler 前按 Contract runtime validate；
- declared success/error response 在开发/测试与正式 contract conformance test 中校验；
- undeclared error 被 Runtime 包装成稳定的 internal custom-route error，不把 stack trace 暴露给 Data Plane；
- OpenAPI 3.1 直接加入 `/api/v1/custom/*` Route Contract；
- Agent Inspect 在 Backend inspection projection 中暴露 operationId、method/path、auth 与 input/output/error schemas；
- TypeScript client generation复用同一 Contract schema；
- 不为 Runtime Validation、OpenAPI、Agent Inspect、SDK Types 分别维护结构副本。

### 8.6 Handler Runtime

Custom API Handler 与 Lifecycle/Event Hook 一样属于 Trusted Project Code，并继承 ADR-0005 的 fault boundary 原则；不因为 Route Contract 是 typed contract 就声称 Handler 是恶意代码 Sandbox。

V0.1.0 production modules只需要保持该边界可实现，不需要提前交付 Custom API Handler runtime。
