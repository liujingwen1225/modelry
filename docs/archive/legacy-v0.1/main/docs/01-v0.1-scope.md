# Modelry V0.1 范围收口

## 状态

**Accepted**

本文档是 V0.1 的正式范围边界，用于回答“V0.1.0 必须做什么、哪些能力可以在 V0.1.x 完成、明确不做什么”。

V0.1 的核心成功标准是：

`下载 Modelry -> init -> serve -> 打开 Admin -> 创建 Collection / Auth Collection -> 配置 Policy -> 获得 REST API / OpenAPI -> Coding Agent 通过 MCP Inspect -> Agent 提出 Schema Change -> ChangeSet + Diff -> Apply -> Migration Artifact -> Git Diff`

只要这条闭环稳定、清晰、可复现，Modelry 的首个可用版本就成立。

## Release Layer

### V0.1.0 Core Closure

必须完整跑通 Modelry 的产品差异化闭环。任何一项缺失都会破坏首版成立条件。

### V0.1.x Completion

领域模型和接口边界在 V0.1 设计中保持兼容，但具体实现可以在 V0.1.0 之后补齐，不阻塞首个端到端版本。

这不是删除能力，而是避免认证、存储和异步运行时扩展把核心 Agent Backend 闭环无限推迟。

## Policy

V0.1.0 Record Policy 必须按操作定义并测试：

- list
- view
- create
- update
- delete

Policy、Filter 与 Realtime Subscription Filter 共用 Expression Engine。

`to-spec` 必须固定：

- Create 对候选 Record 的求值语义；
- Update 对 before/after Record 的求值语义；
- Delete 对删除前 Record 的求值语义；
- Relation Expand 对目标 Collection `view` Policy 的二次校验；
- Realtime 不得绕过 Record Policy；
- List Policy 必须能够下推到查询，而不是先读取全部数据再内存过滤。

## Runtime Extension

### V0.1.0 必须包含

- Lifecycle Hook
- Secret
- Hook Fault Recovery 基线

Lifecycle Hook 只处理事务内、本地、确定性的验证和字段补全，不执行不可回滚的外部副作用。

### V0.1.x Completion

- Event Hook
- Custom API
- Simple Cron Job
- Webhook

Event Hook / Webhook 必须遵循 ADR-0010：可靠异步任务的耐久事实与触发它的业务 Mutation 同事务持久化；真正外部副作用在 Commit 后执行。

Cron 只负责 `Cron Expression -> Hook`。

### V0.1 不包含

- Workflow Engine
- DAG
- Task Dependency
- Distributed Queue
- Job Orchestration
- 可视化 Retry Pipeline Builder

- Principal / Credential 基线

这些能力属于 Modelry 的核心差异化，不作为首版可随意删除的“高级功能”。

### Administrative Data Access

Control Plane 对业务 Record 的管理型读取/修改与普通 Data Plane 明确分开：

- `data:inspect` —— 管理型读取；
- `data:mutate` —— 管理型写入。

该路径不伪装成业务 `auth.id`，默认不经过 Record Policy，但必须经过 Capability Scope 并进入 Audit。

普通应用/SDK/Data API 请求仍严格经过 Record Policy。

## Migration Safety

V0.1.0 Migration Engine 不能只会生成 DDL，必须具备最小安全模型。

主风险级别至少区分：

- SAFE
- DATA_REWRITE
- DESTRUCTIVE
- IRREVERSIBLE

当一个变更同时符合多个条件时，按**最高风险级别**归类；可以附加更细的影响 Flag，但不得通过多个并列主级别制造歧义。

`to-spec` 必须覆盖：

- precondition
- impact preview / dry-run
- explicit confirmation
- backup/checkpoint requirement
- atomicity
- failure recovery
- field rename/drop/type change
- unique index creation
- relation cardinality change

Backend Model 的持久化真相层级固定为：

`Project Migration History -> Runtime Backend Model -> Generated Schema Snapshot`

不引入需要人工维护的第四份 Backend Model Source 文件。

## Admin UI

V0.1 一级页面控制在 8 个以内：

1. **Overview** —— Runtime Status、Database、Storage、Migration、Drift、Recent Activity
2. **Collections** —— Collection、Schema、Indexes、Policy、Records、Auth Config
3. **API** —— REST、OpenAPI、Realtime、Custom APIs
4. **Changes** —— ChangeSets、Diff、Risk、Migration、Apply History
5. **Hooks & Events** —— Hooks、Cron、Webhook、Event Delivery
6. **Access** —— Admins、Agents / Services、API Keys、Capability Scopes、Sessions
7. **Project Settings** —— Secrets、Storage、OAuth、Email、Runtime Config
8. **Activity** —— Audit、Runtime Logs、Webhook Delivery、Hook Errors

V0.1.0 只要求实现与 Core Closure 对应的子页面；V0.1.x 再补齐后置能力 UI。

业务 Auth Collection 用户仍通过 `Collections -> <auth collection> -> Records` 管理，不进入 Control Plane Access 页面。

## MCP

V0.1 MCP 不是 HTTP API 镜像，而是少量、稳定、意图明确的领域工具，目标规模约 15~20 个。

### Inspect

- `project_get`
- `schema_get`
- `collection_list`
- `collection_get`
- `changeset_list`
- `migration_list`
- `runtime_status`
- `audit_query`

### Propose

- `collection_change_propose`
- `policy_change_propose`
- `hook_change_propose`
- `config_change_propose`

### Apply

- `changeset_apply`
- `changeset_cancel`

### Administrative Data

- `records_query`
- `record_get`
- `record_create`
- `record_update`

这些 Tool 属于 Administrative Data Access，分别要求 `data:inspect` / `data:mutate` 并必须 Audit；它们不是普通业务 Auth Principal 的 Data API 代理。

### Secret

- `secret_list`
- `secret_set`
- `secret_delete`

MCP V0.1 不提供：

- `execute_sql`
- `exec_shell`
- 任意文件系统读写
- 不受约束的数据库管理员入口

HTTP API 是 Resource Oriented；MCP 是 Task / Intent Oriented，两者不要求名称一一镜像。

## AI Native 边界

V0.1 **不内置 Admin AI Chat**。

Modelry 的 AI Native 能力来自：MCP、Machine-readable Backend Model、ChangeSet、Diff、Risk Classification、Structured Error、Schema Snapshot、Doctor、Audit。

目标是让 Coding Agent 安全操作 Modelry，而不是用聊天框证明“支持 AI”。

---

## V0.x 明确不做

除非新的 Accepted ADR 明确改变方向，V0.x 不实现：

- PostgreSQL Runtime
- Multi-project / Workspace
- Cluster / High Availability
- Distributed Lock / Leader Election
- Redis / Kafka 等外部基础设施作为核心依赖
- Plugin Marketplace
- Untrusted Code Sandbox
- Cloud Platform
- 多套官方 SDK

继续坚持：SQLite Only for V0.x、One Instance One Project、Single Node、Single Binary First。

## Bun Runtime Spike Gate

正式 `to-spec` 前必须执行 `docs/spikes/0001-bun-runtime-validation.md`，并对关键项给出 `PASS / RISK / FAIL` 与 ADR-0003 的 `GO / CONDITIONAL GO / NO-GO` 结论。

至少验证：

1. Standalone Executable
2. SQLite Persistence / minimal Migration
3. Embedded Admin UI
4. REST API
5. SSE
6. MCP through ChangeSet Core
7. External Dynamic TypeScript Hook
8. Hook Fault Recovery
9. Hook Reload / Concurrency Boundary
10. Minimal Transactional Outbox

出现阻塞性 `FAIL` 时必须重新评估 Bun，必要时切换 Go fallback。

最终使用一个真实 Demo App 做端到端验收，推荐 Todo / Notes / Blog。

V0.1.0 至少覆盖：

- Email/Password Auth
- Collection
- Relation
- Local File
- Policy
- Lifecycle Hook
- Realtime
- MCP Schema Change
- ChangeSet / Risk
- Migration
- Drift / Doctor

V0.1.x 再扩展：OAuth / OTP / Password Reset、S3、Event Hook、Webhook、Custom API、Cron、Backup / Restore、Batch。

成功标准：开发者可以使用 Modelry + Coding Agent 从零完成真实小型应用，并且后端变更可理解、可 Diff、可审计、可进入 Git。
