# ADR-0005: File Values, Storage Providers, and Provider Migration

- **Status:** Accepted — Community V0.1.x
- **Date:** 2026-09-25
- **Scope:** Multiple File values, Local and S3-compatible Storage Providers, file constraints, reconciliation, and provider migration
- **Depends on:** [ADR-0001](./0001-runtime-storage-architecture.md), [ADR-0003](./0003-extension-runtime-lifecycle-secrets.md), [Local File Values and Storage Providers](../product-model/0002-files-and-storage.md)
- **Issue:** [#25](https://github.com/liujingwen1225/modelry/issues/25)

## Context

V0.1 implemented Local Storage with a single File Field: a staged upload in `.modelry/files/tmp`, an atomic rename into `.modelry/files/objects`, and an opaque object key stored in the Record column. That design already separates the SQLite transaction from the byte write, but it hard-codes the filesystem as the only provider and one file per Field.

V0.1.x must add Multiple File values and an S3-compatible Provider without letting the Provider leak into Backend Model semantics, without pretending that an object upload participates in the SQLite transaction, and without breaking existing Local projects.

## Decisions

### Field capability

- File values remain a Collection Field capability. A `file` Field holds one File value; a new `files` Field holds an ordered list of File values. Both are ordinary Backend Model Field types with the same Change/Access/API lifecycle as every other Field.
- A Record stores only opaque object references generated by the Runtime (`obj_` followed by 32 lowercase hex characters). A `file` value is one such reference; a `files` value is a JSON array of them, persisted with TEXT affinity and decoded in order.
- Field constraints live in the Field `validation` object: `maxBytes` (1 to 128 MiB), `allowedMimeTypes` (non-empty list of MIME types or `type/*` wildcards), and `maxFiles` (1 to 32, only for `files`). A caller may only narrow the constraint on upload; it can never widen it.
- The content type is always derived from the uploaded bytes with a bounded content sniff. A caller filename is never stored, never used as a key, and never used as a path segment.
- Existing `file` Fields and their stored values stay valid without migration, because the reference format and the Field semantics are unchanged.

### Provider-neutral object semantics

- The Runtime writes and reads objects through a Provider interface with a fixed contract: `Promote` (create an immutable object from a staged upload), `Open`, `Stat`, `Delete`, `List`, and `Health`. Records, Access Rules, the Application API, and the Admin Record surface never branch on the Provider.
- Object references are Provider-neutral. The Local Provider maps a reference to `<project>/.modelry/files/objects/<reference>`; the S3-compatible Provider maps it to `<keyPrefix><reference>` in the configured bucket. Moving Providers therefore does not rewrite a single Record value.
- The Provider interface receives a staged upload as a path plus size and content type, so the Local Provider keeps its zero-copy atomic rename and the S3 Provider streams from disk. Uploads are always staged in the Runtime-managed local staging directory first, which bounds memory, keeps MIME/size validation before any network call, and lets a failed or abandoned upload be collected locally.
- The active Provider is configured per Project in SQLite behind an expected-revision check, so two concurrent Admin changes cannot silently overwrite each other. Configuration changes are a Control Plane write; they never touch Record rows.

### No false transaction

- Upload stages bytes; binding writes the object outside the SQLite transaction and then commits the Record. If the transaction fails, the new object stays unreferenced and reconciliation collects it after a grace period. If the object write fails, the Record transaction never commits.
- Replacement and removal dereference the previous object instead of deleting it inline. A Record that still references an object always wins over reconciliation, which re-reads the durable references before deleting anything.
- Reconciliation is the only garbage collector. It runs on startup and on a bounded interval, keeps a grace period, and never deletes an object that is referenced, staged, or younger than the grace period. For the Local Provider it enumerates the object directory; for the S3-compatible Provider it lists the configured key prefix with pagination.

### Read path

- Reads are proxied by the Runtime. The Admin API and the Application API stream bytes with `Content-Type`, `Content-Length`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and `Cache-Control: private, no-store`, after the existing Owner session or Collection view Access Rule check.
- A `files` Field is read by 0-based index. An out-of-range index is a `NOT_FOUND` error, not an empty body.
- The Runtime never returns a filesystem path, bucket name, provider endpoint, object URL, or presigned URL. S3 requests are signed in memory with the Project Secret values, which are resolved per request, never cached in plaintext, and never written to SQLite or diagnostics.

### Credentials and endpoint safety

- S3-compatible credentials are Project Secrets referenced by ID. Deleting a referenced Secret disables the Provider (fail closed) instead of falling back to another Secret or to an anonymous request.
- The configured endpoint must be HTTPS, except for loopback, private, and link-local hosts, where HTTP is allowed so a self-hosted MinIO instance on the same machine or LAN remains usable. The endpoint must not contain user information, a query, or a fragment. Redirects are not followed, and the client never uses a proxy.
- Requests are signed with AWS Signature Version 4 for the `s3` service. Payload SHA-256 is always sent, path-style addressing is supported for MinIO-style endpoints, and every request has a bounded deadline.

### Migration

- A migration is a durable Control Plane operation with a stable ID, a target Provider snapshot, an object count, a copied count, and a terminal state (`completed`, `failed`, `cancelled`, `interrupted`). Only one migration may be active at a time.
- Migration copies only objects referenced by Durable Records. It reads from the active Provider and writes to the target Provider under the same object reference, then verifies size and readability. Already copied objects are reused, so a restart or a retry is idempotent.
- The Provider switch happens in a single SQLite transaction after every referenced object is verified in the target. A failure, a cancellation, or an interruption leaves the previous Provider active and the Project fully usable.
- Migration never deletes source objects. An Owner removes them by keeping the old Provider data outside Modelry, or by running reconciliation against the old Provider before switching, which is out of scope for V0.1.x.
- Migration is bounded: at most one object copy at a time, a per-object deadline, a bounded per-operation object count, and a bounded progress record size.

### Degradation

- The Runtime starts even when the configured Provider is unreachable. Runtime health reports the Provider state; File reads, uploads, binding, and migration fail closed with an actionable error, while Record mutations that do not touch File values keep working.
- Health probing is bounded and non-destructive: staging writability for Local, and a prefixed list plus a bounded `HEAD` for S3-compatible. Health never creates or deletes objects outside the staging area.
- Diagnostics and Audit never contain credentials, object bytes, request signatures, or a full provider URL with user information.

## Bounds

- 128 MiB maximum upload size, 10 MiB default Field limit, 1 MiB minimum staging block accounting, 32 File values per `files` Field, 64 concurrent staged uploads per Runtime, 15-minute staging grace period, 1-hour orphan grace period, 1,000 objects per reconciliation sweep, 1,000 objects per S3 list page, 2-second per-object S3 deadline, 5-second Provider health deadline, and one active migration with a 30-second per-object deadline.
- S3 request signing is in-memory only; Project Secret values are capped by ADR-0003 at 16 KiB.

## Rejected alternatives

- **Presigned URLs in the browser.** They leak the object location, bypass Runtime authorization on each read, and make revocation and provider switching visible to clients. Rejected.
- **Storing the Provider in the Field or the Record.** It would freeze implementation details into Backend Model semantics and make migration a data rewrite. Rejected.
- **Deleting objects synchronously with the Record.** Delete would then be able to destroy bytes that a concurrent read still needs, and a transient provider failure would block Record mutation. Rejected.
- **Treating the object write as part of the SQLite transaction.** SQLite cannot roll back a remote object write. Rejected.
- **Requiring an AWS SDK.** It brings a large dependency and an implicit feature surface for a single bounded object API; a small signing client keeps the Runtime auditable and dependency-free. Rejected.
- **Auto-migrating on Provider change.** A silent copy of every object during a configuration write would be unbounded and unobservable. Rejected in favor of an explicit durable migration.
- **A Content-Addressable store.** Content addressing would change existing object references, break Local compatibility, and complicate reconciliation. Rejected.
